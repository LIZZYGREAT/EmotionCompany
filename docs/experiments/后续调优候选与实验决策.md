# 后续调优候选与实验决策

## 使用规则

本文记录待验证的实验候选，不是已批准的执行清单。标准 Full B 和完整 Dev 配对基线现已完成，见[正式验收报告](E01-B_正式SFT与Dev对照验收报告.md)和[深度诊断](E01-B_Full_深度诊断与证据整理.md)。下表候选状态仍全部为 `idea`；既有结果不会自动批准或启动任何一项实验。当前阶段入口见[唯一交接](../context/E01_当前状态与后续交接.md)。

每项候选一次只改变表中所列的一个主要因素。对照尽量固定模型权重、数据版本、P0/F2/T1、Tokenizer/Chat Template、样本 ID、解码、后处理和评分口径。20 条 Smoke 只检查流程，不用于选优；需要判断模型质量时优先在完整 Dev 1,833 条上配对评测。官方 Val 不用于调参。

状态只使用 `idea / approved / running / completed / rejected`。每个已批准实验应另建 Experiment ID、配置与输入 Hash、运行记录、验收阈值、资源上限和停止条件；模型候选须先完成许可证、权重、Tokenizer 和部署兼容性审查，本文未启动下载或切换。

|---|---|---|---|---|---|---|
| `I-01` Greedy/Sampling | 当前 20 条结果不能冻结解码优劣；更大配对集合可能显示质量/延迟差异 | 每次只改一个解码参数；模型、Prompt、输入和评分固定 | 同一 Dev ID 配对比较字段指标、回复指标、EOS/上限和延迟分布 | 不增加权重显存；Sampling 可能增加时延/方差 | 需要确定部署解码策略，且可运行足量 Dev | P1 / `idea` |

| `I-04` BERTScore/官方指标对齐 | BERTScore 当前 `not_run`，官方画像计算细节尚需核实；补充可信离线评分可改善解释 | 只引入一个固定评分定义/离线模型版本；不改预测和训练 | 对固定夹具复核分数，记录模型 revision、依赖与 tokenizer；官方定义需获得可引用依据 | 可能需要下载/缓存额外模型、较多磁盘和 CPU/GPU 时间 | 有明确报告需求且模型、许可、算法可离线复核 | P2 / `idea` |

## 选择顺序

1. **当前动作：**先审阅 Full B 深度诊断和部署未验收项。E01-A/Pilot/Full B 训练门禁已有历史验收，不再把 micro-overfit 或 Full B 当作待启动阶段。
2. 若要继续，先审阅 Full B 深度诊断，再在 `P-01`、`P-02`、`T-04`、`I-02` 中选择一个可由独立证据触发的方向；状态保持 `idea`，不同时启动多项。Full Dev 本身不授权反复调参。
3. 更换模型、大幅调整上下文、改变任务架构或切换部署后端，需先完成兼容性与资源评估，再另行立项。

任何候选进入 `approved` 前，必须补全负责人、Run ID、唯一变量、基线、样本集合、评价指标、阈值、预算、停止条件和输出位置。若证据不支持假设，记录为 `rejected` 并保留实验记录，不删除负结果。
