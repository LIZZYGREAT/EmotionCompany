## 4. 实现与安全边界

- 训练更新使用 TRL `SFTTrainer` 和 D0.4.3 `SFTDataCollator`。运行时核对 `skip_prepare_dataset=true`、`max_length=null`、`packing=false`、`padding_free=false`，并逐批比较 `input_ids`、`attention_mask`、`labels`。
- D0.4.3 的 Completion 监督可能在模板 EOS 后包含尾随空白 Token；预检只要求受监督 Completion 中包含锁定 EOS，不要求 EOS 是最后一个 Token。Labels 不重建、不手工 shift。
- E01-A 和 E01-B 的 `init_adapter`、`resume_from_checkpoint` 均为空；A 的 one-step proof 必须来自不同 Run ID，B 配置只允许 preflight。
- Adapter 推理必须显式启用并同时匹配 Base 权重 SHA、Adapter 权重 SHA 和可选 Adapter 配置 SHA；默认配置没有启用 Adapter。Scorer 对 E00 仍要求无 Adapter，对 E01 快照核验 Base 与 Adapter 双身份。
- Base 权重只读；训练产物、Raw 生成和预检 JSON 均写入忽略目录 `outputs/training/`。没有修改官方数据、Schema、P0、`start.sh` 或默认推理配置。
- 每次 Dev Smoke 使用独立的 `evaluation/dev_smoke/<attempt-id>/` 目录，并在启动推理前写入 `run_manifest.json`。推理或评分失败会更新状态，旧版遗留的 `evaluation/dev_smoke/` 根目录不会阻止新尝试，也不会与新结果混写。

第一次预检 `E01-A-preflight-20261027-001` 暴露了“EOS 必须为最后 Token”的过严假设，已修正并增加回归。随后 one-step Run `E01-STEP-20261027-220539` 暴露 NF4 检查漏传 `quantization.enabled=true`，也已修复；之后 `E01-STEP-20261027-221949` 成功生成 proof，Loss 为 `4.4916`，LoRA 更新与 Base 不变检查均通过。A Run `E01-A-20261027-222025` 暴露 Trainer 释放后的 Manifest 最终化错误并保留为 failed。最终化顺序已修复；新 Run `E01-A-20261027-223703` 的 Manifest 为 passed。当前代码还会逐步写 `progress.json`，并在释放 GPU 模型前写 `training_evidence.json` 和更新 Manifest。完整的 optimizer/scheduler 状态续训 Checkpoint 尚未启用，因此这些记录保住进度和权重证据，但不能原样恢复 Adam 状态。
