# EmotionalCompany：竞赛技术概念与全流程协作指南

> **用途**：供两名参赛成员建立统一的技术术语、执行流程与工作边界。重点解释每项技术是什么、在什么阶段使用、接收什么输入、产生什么输出，以及如何与下一阶段衔接；不展开神经网络基础、梯度下降或低秩分解的数学证明。<br>
> **阅读顺序**：沿着“原始对话 → 规范化样本 → 模型输入 → 模型微调 → 验证 → 推理部署”阅读。文中的小型对话与数值均为教学示例，除明确注明外不是实际数据或实测成绩。

## 一、竞赛任务与整体技术流程

### 1. 从比赛输入到最终输出

本赛题是一个**文本多任务预测系统**。平台提供此前发生的用户—助手对话；我们需要在指定的目标用户轮次，预测用户情绪、用户画像并生成一条情感陪伴回复。现阶段没有语音识别、数字人动画或视觉建模要求。

| 预测任务 | 输入依赖 | 输出与技术性质 | 自动评测 |
|---|---|---|---|
| 情绪识别 | 当前用户消息及此前对话 | 16 类中选 1 类，**单标签分类** | Accuracy，25 分 |
| 用户画像 | 当前及历史中的个人特征线索 | 三个维度、共 33 个候选标签，**多标签预测** | 画像维度平均准确率，15 分 |
| 情感回复 | 当前诉求、历史语境与必要用户信息 | 开放式自然语言生成 | BLEU-4、ROUGE-L、BERTScore，20 分 |
| 推理性能 | 完整的模型执行流程 | 端到端延迟 | 10 分 |

另外 30 分来自技术方案完整性、代码规范及可复现性、训练/调优与平台运行记录。**自动得分不是单纯的回复自然度**；分类正确性、输出合法性、推理速度、技术过程留痕都应被纳入设计。

整体流程：

```text
官方 Train / Val 原始 JSONL
   │
   ├─ D0.1 数据审计：发现结构、时序、标签、重复等问题
   ├─ D0.2 处理政策：决定哪些隔离、去重或保留
   └─ D0.3 数据构建：按预测点展开、去重、Train/Dev 分组划分
   ↓
规范化样本：history + target
   │
   └─ D0.4 模型输入：任务 Prompt、Chat Template、Tokenizer、长度预算、训练 Label Mask
   ↓
   ├─ E00：原始 Qwen3-1.7B 直接预测，得到零微调基线
   └─ E01：QLoRA + SFT 更新 Adapter，再进行相同评测
   ↓
对比 Accuracy / 画像指标 / 文本指标 / 延迟 / JSON 合法率
   ↓
选择训练方案与权重版本
   ↓
自行构建 vLLM Docker 镜像，离线运行官方入口并提交结果
```

### 2. 已确定的 A0 架构

**A0** 是项目第一版架构名称，不是通用机器学习算法。其具体定义为：

- **一个模型**：`Qwen/Qwen3-1.7B`，而非额外训练独立情绪或画像分类器。
- **一种训练样本**：每个预测点对应一条“输入历史 → 完整 JSON 答案”的监督数据。
- **一种微调方法**：4-bit NF4 量化基础模型，使用 QLoRA 训练 LoRA 参数。
- **一个联合输出**：模型以固定顺序生成情绪、画像、回复；外部程序负责补充/透传提交 ID、校验 JSON。
- **两项核心实验**：E00 未微调模型与 E01 标准 SFT 微调模型的公平对照。

目前不采用：独立判别模型方案 B、字段损失加权 A0+、专项任务混训 A1、RAG、外部长期记忆库或多 Agent。它们是后续可能的实验方向，**不是当前默认架构**。

## 二、理解原始数据：Conversation、Turn、Prediction Point

### 1. 原始数据究竟是什么

官方数据采用 **JSONL（JSON Lines）**：一个文件由多行 JSON 对象构成；本项目里通常**每行是一整段对话**，不是一条训练问答。JSONL 与普通 JSON 数组不同，适合逐行读取并定位出错记录。

一段对话（**Conversation**）包含多个轮次（**Turn**），每轮记录讲话者 `role`（用户/助手）、文本 `content` 和轮次 ID `turn_id`。同一 Conversation 可以有多个 **Prediction Point（预测点）**，表示要在哪一条用户消息后执行一次三任务预测。

```text
Conversation
├─ conversation_id
├─ turns[]
│  ├─ turn_id
│  ├─ role: user / assistant
│  └─ content
└─ prediction_points[]
   ├─ target_user_turn_id         # 当前预测对象：哪条用户消息
   ├─ assistant_response_turn_id  # 对应哪条参考 Assistant 回复
   └─ target
      ├─ emotion_label
      ├─ user_profile              # 三个标签数组
      ├─ response_text
      └─ memory_refs
```

**History（历史输入）**：从对话开始，到目标用户消息为止、允许模型看到的消息前缀。**Target（监督目标）**：官方针对该预测点提供的正确标签和参考回复。

例如某段对话的第 5 条消息是目标用户消息，那么用于预测的 History 只含第 1～5 条消息。第 6 条及之后的助手回复属于未来信息，不能放进该次预测的输入。

这里的“预测点”才是训练和评测的基本单位；同一 Conversation 中不同预测点共享较早历史是正常现象，不能简单视为重复数据。

### 2. 数据泄漏、审计、清洗和规范化

**数据泄漏（Data Leakage）**：在训练或评测时使用了本不应该知道的信息，导致评价结果虚高。例如用目标用户消息之后的对话预测当前情绪，或让同一段对话的重叠样本分别进入 Train 和 Dev。

**数据审计（Audit）**：只检查和记录数据问题，不改原始数据。D0.1 审计了 JSON 解析、字段、时序、标签、重复和分布等。

**数据清洗（Cleaning）**：依据规则，在派生数据中隔离确定错误或移除确切重复监督。这里不等于删除口语、Emoji、少数类标签或不够长的回复。

**规范化（Normalization）**：把原始 Conversation 的各个预测点转成统一形式的一条记录，保留来源、合法 History 和 Target，供后续模型输入构建器使用。它不等于把用户原文改写为所谓“标准表达”。

**精确去重（Exact Deduplication）**：当合法历史和完整监督 Target 均相同时，只将其中一个作为训练样本，其余记录来源映射；“相似情绪表述”或“同输入但不同合理回复”不能简单删除。

D0.1～D0.3 已完成数据处理后的版本 `v1`，规模如下：

| 数据 | 预测点数 | 含义 |
|---|---:|---|
| 原始 Train | 18,657 | 初始监督点 |
| 隔离时序异常 | 4 | 无法安全对应监督回复 |
| 精确重复移除 | 508 | 不重复赋予训练权重 |
| 最终 Train | 16,312 | 用于模型参数更新 |
| 内部 Dev | 1,833 | 用于开发期评估、超参数选择 |
| 官方 Val | 2,354 | 独立阶段性验证，不参与训练 |

数量关系：`18,657 = 4 + 508 + 16,312 + 1,833`。上述为仓库 D0.3 审计报告记录，不是本文件再次运行原始数据得到的结果。

### 3. Train、Dev、Val、Test 的区别

**Train（训练集）**：模型使用这些样本计算训练损失并更新可训练参数。

**Dev（开发验证集）**：从官方 Train 中按完整对话/相同历史关联组划出的保留数据，用来比较学习率、训练轮数、输入策略等。Dev 不参与当前实验的梯度更新，但开发者会根据 Dev 结果选择方案。

**Val（官方验证集）**：主办方提供的另外一批数据，用于阶段性比较候选模型；不参与训练，也尽量避免反复针对它调整细节。

**Test（测试集）**：正式评测阶段平台使用的数据，标准答案通常不会提供给参赛者；最终成绩依赖其表现。

开发时执行 `Train → 训练模型 → Dev 选超参数 → 官方 Val 阶段性确认`。当配置已确定，可以将 Train+Dev 合并，重新训练最终提交模型；此时原 Dev 已用于训练，不能再当作该最终模型的独立评测集。官方 Val 仍应尽量保持独立。

**按 Conversation 分组划分（Group Split）**：同一完整对话及关联的重复历史不允许跨 Train/Dev，以免看似不同的预测点共享答案上下文。**分层（Stratification）**：尽量让训练/验证的主要类别分布接近，但不得为了类别比例拆开同源组。

## 三、D0.4：从规范化数据到模型输入

这一阶段必须重点区分：原始字符串、对话格式、Token IDs、用于训练的目标与用于推理的 Prompt，并非同一种东西。

### 1. Prompt 与 Completion

**Prompt（提示输入）**：本次预测提供给模型的**已知条件**，由任务指令（System Instruction）和截至目标用户轮次的 History 组成。任务指令说明要判断哪些标签、如何生成回复、遵守什么 JSON 格式。

**Completion（目标补全）**：模型读完 Prompt 后应该继续生成的内容；在 SFT 训练中，它就是监督答案。A0 选择完整 JSON 而不是只给一条回复。

教学示例：

```text
Prompt（模型已知）：
系统规则：请根据对话输出 emotion_label、user_profile、response_text，
仅使用合法标签，输出完整 JSON。
user：最近作业太多了。
assistant：是哪部分压力最大？
user：每天学习到很晚，但还是担心做不完。

Completion（训练阶段提供的标准目标）：
{"emotion_label":"anxiety",
 "user_profile":{"personality_traits":[],"interests":["study_exam"],"style":[]},
 "response_text":"听起来任务量让你一直处于紧绷状态……",
 "memory_refs":[]}
```

**训练**时同时有 Prompt 和真实 Completion；**推理**时只给 Prompt，让模型自己生成 Completion。绝不能把参考回复、真实情绪标签等放回推理 Prompt。

A0 的 Completion 中 `response_text` 使用原始监督回复；`memory_refs` 依据当前 A0 方案统一设 `[]`。D0.3 仍保留原始 `memory_refs`，两者用途不同。官方提交中的 `id` 由程序从输入透传，不由模型生成。

### 2. Chat Template：如何表示不同角色

**Chat Template（聊天模板）**：模型约定的消息序列化规则，把 Python 中的 `[{role, content}, ...]` 转换成带有角色、消息边界和特殊标记的对话输入。

Qwen3 的模板形式可以近似理解为：

```text
<|im_start|>system
任务规则……<|im_end|>
<|im_start|>user
最近作业太多了。<|im_end|>
<|im_start|>assistant
是哪部分压力最大？<|im_end|>
<|im_start|>user
每天学习到很晚……<|im_end|>
<|im_start|>assistant
```

最后的 Assistant 起始标记意味着“从此处开始生成助手回答”。`add_generation_prompt=True` 用于在推理 Prompt 末尾添加这一生成起始结构。**不能把以上文字直接视为手工拼接规范**；实际应通过 Qwen Tokenizer 的 `apply_chat_template` 执行，并避免特殊标记重复添加。

之前官方参考 `participant` 脚本采用类似 `user: ...` 的纯文本历史拼接；A0 已决定改为 **F2：Qwen 原生多轮 Chat Template**。这要求后续训练与推理适配都调用相同的输入规则。

**Non-thinking（非思考模式）**：Qwen3 可以在不同生成模式间切换。A0 采用 `enable_thinking=False`，减少额外思考文本和推理开销，更贴近只需输出 JSON 的比赛要求。此参数属于 Chat Template/生成接口的配置约束，不是删除推理能力或修改模型权重。

### 3. Token 与 Tokenizer：字符串如何进入神经网络

**Token**：模型内部使用的文本单位，不等于一个汉字或一个单词。**Tokenizer**：负责将文字、模板中的特殊标记编码成一串整数 `input_ids`，并把生成的整数还原为文本。

```text
历史文本 + Chat Template
       ↓ Tokenizer
input_ids = [整数 ID, 整数 ID, ……]
       ↓ 模型
后续 Token 的概率 / 生成结果
       ↓ Tokenizer 解码
JSON 字符串
```

不同模型的 Token 划分可能不同，所以**字数、字符数、Token 数不能直接互换**。D0.1 统计过字符长度，但 D0.4 必须使用本项目真实的 Qwen Tokenizer 统计长度。

**Tokenizer Revision**：模型仓库中某个确定的词表/模板版本。记录它是为了让队友在同一个 Prompt 下获得相同的编码，防止后来模型仓库更新导致长度或输入格式变化。

### 4. Token Budget、T1 截断与训练/推理长度

**上下文窗口（Context Window）**：一次模型执行可以参考的 Token 序列范围，受模型能力及硬件资源限制。**Token Budget（Token 预算）**：我们人为设定的训练或推理长度额度。

要区分以下三个参数：

| 参数 | 含义 |
|---|---|
| `max_train_seq_length` | 训练时 Prompt + 正确 Completion 的总 Token 上限 |
| `max_prompt_tokens` | 模型输入 Prompt 的最大 Token 数，包括任务指令、历史和模板 |
| `max_new_tokens` | 推理时最多生成多少新 Token，影响回复完整性与延迟 |

训练总长度必须满足：

$$
L_{\mathrm{prompt}}+L_{\mathrm{completion}}\leq L_{\mathrm{train,max}}
$$

例如 Prompt 为 1,500 Token、完整 JSON Completion 为 700 Token，总计 2,200 Token；如果本次训练上限为 2,048，就不能把 2,200 全部送入。优先减少更早的历史，不能静默截断目标 JSON 的末尾。

**T1（最近历史优先）**：项目约定的历史选择策略。从当前目标 User 消息开始向前保留最近的完整消息，直到预算不足，最终仍按原来的时间顺序组织消息。异常长的当前消息及过长 Completion 单独记录，不能随意截成半条后假装完整。

本地 8GB GPU 可能适合较短的训练长度；服务器允许更多显存时可以尝试 4,096 Token。但 **“以 2,048 训练”不等于“模型推理最多只能使用 2,048”**：较长的推理上下文技术上可以单独测试，其效果、成本和训练—推理分布变化需用实验验证。

### 5. P50 / P90 / P95 / P99：为何统计长度分位数

**百分位数（Percentile）**：把样本长度从短到长排列，找出某个累计比例对应的长度。P50 是中位位置，P90 表示大约 90% 的样本长度不超过该水平；P95、P99 用来观察更长的尾部样本。实际分位数可能因插值算法而略有差异，需记录统计方法。

假设 1,000 条样本的完整训练序列长度统计为：

| 统计量 | 示例 Token 长度 | 解释 |
|---|---:|---|
| P50 | 800 | 典型样本约 800 Token |
| P90 | 1,700 | 约 90% 的样本不超过 1,700 |
| P95 | 2,300 | 约 5% 的样本长于 2,300 |
| P99 | 4,100 | 约 1% 的样本长于 4,100 |
| Max | 7,600 | 极长样本上限 |

这些都是假设数据。**P90 不是要求固定采用 P90 的长度**，而是帮助比较 1,024/2,048/4,096 等预算的覆盖情况：多少样本无需裁剪、多少只需裁剪历史、多少连完整目标都无法容纳。

D0.4.2 在统计时分别计算原始 History、当前消息、Prompt、Completion、完整序列长度，并记录截断率和异常率。统计最终模板编码时，应以**整条实际序列编码**为准，避免仅把各部分分别编码后长度机械相加造成边界偏差。

### 6. Labels、Label Mask、Attention Mask、Padding、EOS

这组术语描述了**训练器怎样知道哪些 Token 是输入，哪些位置需要预测**。

**Labels（训练目标）**：与模型序列各位置对应的目标 Token IDs。对于自回归语言模型，框架会处理“根据前面 Token 预测下一个 Token”的位置对齐。

**Label Mask（监督掩码）**：通过将无需学习的位置的标签设为 `-100`（PyTorch 常见忽略值），只在指定目标 Token 上计算损失。A0 是 **Completion-only**：只监督完整 JSON 与正确结束标记，不监督重新生成原始历史。

**Attention Mask（有效输入标记）**：通常指示哪些输入位置有效、哪些为批处理补齐位。它与 Label Mask 不同；Prompt 虽然不参与损失，仍然要被模型读取。

**Padding（填充）**：为使一个 Batch 内不同长度样本能够统一处理，给短样本补上的占位部分；这些位置应被正确屏蔽。

**EOS / EOT（序列或消息结束标记）**：用于让模型知道何时停止生成。聊天模型可能存在不同的消息结束与回答结束 Token，具体必须以 Qwen 的模板及生成配置为准。

常见非 Packed（不拼接多条样本）的处理示意：

| 位置 | Attention Mask | Labels |
|---|---:|---|
| 有效 Prompt | 1 | `-100` |
| 有效 Completion + 正确终止标记 | 1 | 对应真实 Token IDs |
| Padding | 0 | `-100` |

**SFT 数据构建不能仅验证代码设置了 `completion_only_loss=True`**，还应抽检真实 `input_ids`、`labels`、完成边界、EOS 和没有全 `-100` 的样本。某些训练框架会自动截断长序列，因此必须事前审计，避免损坏 JSON 监督。

## 四、模型选择、SFT、LoRA 与 QLoRA

### 1. 预训练模型、后训练模型和微调模型

**Pretraining（预训练）**：在海量语料上学习通用语言模式的初始阶段。**Base Model** 通常强调这种基础语言建模能力。**Post-training / Instruction Tuning（后训练 / 指令对齐）**：进一步训练模型理解指令并按对话规范回答。**Fine-tuning（微调）**：我们使用赛题特定数据，继续适配模型。

`Qwen/Qwen3-1.7B` 是已经具备对话能力的模型，不等同于名称带 `-Base` 的纯基础版本。A0 以其为起点，目标不是从零训练语言模型，而是学习赛题的三任务标签、输出协议和回复风格。

### 2. SFT：模型在训练时实际做什么

**SFT（Supervised Fine-Tuning，监督微调）**：利用输入和正确答案组成的样本，让已有模型进一步学习任务。**Completion-only SFT** 则只在正确 Completion 位置计算训练损失。

一轮训练中的一条样本经历：

```text
Prompt + 正确 JSON Completion
   ↓ Chat Template / Tokenizer，生成 input_ids 与 labels
Qwen 前向传播：得到各位置下一 Token 的预测概率
   ↓
仅对 Completion 的有效 Token 计算损失 Loss
   ↓
反向传播：计算可训练参数需要怎样更新
   ↓
优化器更新参数
   ↓
下一个 Batch；多轮重复直到训练结束
```

**Teacher Forcing（教师强制）**：训练时已经有真实 Completion，因此预测某个目标 Token 时，使用其前面的**真实目标 Token**作为上下文；而推理时没有真实答案，只能使用模型之前自己生成的 Token。

这种差别解释了一个重要现象：模型训练时回复部分依赖真实情绪/画像标签，推理时则依赖它自身先生成的标签。前面的预测若有误差，后续回复也可能受影响；A0 先通过验证集分析，不引入额外纠错链路。

**Loss（训练损失）**：反映预测与标准答案之间差距的数值，是模型更新参数的依据。Loss 下降意味着更容易拟合训练目标，**不等于**情绪 Acc、画像准确率或 BLEU 必然提高。正式优劣仍以 Dev/Val 评测为准。

### 3. LoRA、PEFT 和 Adapter

**Full Fine-Tuning（全参数微调）**：更新基础模型的大部分或全部参数；对 8GB GPU 显存成本较高。

**PEFT（Parameter-Efficient Fine-Tuning，参数高效微调）**：只训练少量附加参数而冻结多数基础参数的一类方法。**LoRA（Low-Rank Adaptation，低秩适配）** 是其中一种：在选定线性层增加两组较小的可训练矩阵，用它们表示对原权重的更新效果。

**Adapter（适配器）**：LoRA 训练后保存下来的小型增量权重文件；不是一个独立可运行的完整大模型。推理时需要“基础模型 + 对应 Adapter”，或者先经过兼容性验证将 Adapter 合并至基础权重。

可以理解为：

```text
基础 Qwen3-1.7B 权重（冻结）
              +
      LoRA Adapter（训练更新）
              ↓
          任务适配模型
```

LoRA 常见可调参数：

| 参数 | 含义及影响 |
|---|---|
| `r` / Rank | 低秩矩阵的秩，影响 Adapter 的容量与可训练参数量 |
| `lora_alpha` | LoRA 更新的缩放因子 |
| `lora_dropout` | 训练时用于正则化的 Dropout 概率 |
| `target_modules` | 在哪些线性层上应用 LoRA，例如注意力层或其他投影层 |

这些值还未为 E01 最终冻结，必须在可运行的训练 Smoke Test 和 Dev 结果基础上选择。

### 4. Quantization、NF4、BF16 与 QLoRA

**Quantization（量化）**：用更低位宽的表示存储/计算部分模型权重，主要目的是降低显存或存储占用；可能引入精度和兼容性方面的代价。

**4-bit NF4（4 位 NormalFloat）**：一种适用于量化神经网络权重的四位表示格式。**BF16（Brain Floating Point 16）**：用于神经网络运算的 16 位浮点格式；与 4-bit 权重表示不是同一回事。

**QLoRA**：在量化加载的基础模型上训练 LoRA Adapter。其关键区分是：

- 基础 Qwen 权重主要以低比特形式存储并冻结。
- 通过合适的计算精度（项目使用 BF16）完成前向和反向相关运算。
- 更新的仍是 LoRA Adapter 参数，而不是把所有量化权重作为普通可训练参数更新。

**LoRA ≠ QLoRA**：LoRA 不要求基础模型必须量化；QLoRA 是“量化基础模型 + LoRA 微调”的具体组合。

截至早期环境预检，本机已通过 BF16、GPU 自动求导、bitsandbytes NF4 前向及 Qwen3-1.7B 4-bit 推理测试；当时完整 QLoRA 训练仍需单独验收。后续 E01-A 与 E01-B 已分别完成真实训练及 Adapter 保存/重载验收，Full B 的独立重载最终通过；真实 Run 与范围见[当前交接](../context/E01_当前状态与后续交接.md)。这不代表目标部署环境已经通过。

### 5. Batch、Epoch、Step 和训练超参数

**Batch（批次）**：一次送入模型计算的一组训练样本。**Micro Batch Size**：单设备一次前向/反向实际处理的样本数，直接影响显存。

**Gradient Accumulation（梯度累积）**：连续对多个小 Batch 计算并累积梯度，再执行一次参数更新；用较低的单次显存占用模拟较大的有效 Batch。

单卡、无特殊并行处理时：

$$
\text{Effective Batch Size}
=\text{Micro Batch Size}\times\text{Accumulation Steps}
$$

例如 Micro Batch=1、累积 8 次，则每次优化器更新累计利用 8 条样本的监督信息。多卡时还要考虑设备数量。

**Step** 需明确口径：可能指一次 Micro Batch 处理，也可能指一次优化器参数更新；实验日志中的 `global_step` 常指后者。**Epoch** 是对训练集完成一轮遍历，具体样本顺序受 Shuffle（打乱顺序）等设置影响。

**Learning Rate（学习率）**：控制每次更新幅度的超参数。**Optimizer（优化器）**：依据梯度实际更新可训练参数的软件组件。**Learning Rate Scheduler（学习率调度器）**：按训练进度调整学习率。**Warmup（预热）**：训练初期逐渐增大学习率的常见策略。这些本阶段只需理解其位置和作用，不需要推导优化算法。

**Gradient Checkpointing（梯度检查点）**：不保存全部中间激活，在反向传播时重新计算一部分，以计算时间换取更低显存。它与**模型 Checkpoint（模型检查点文件）**不是一回事。

**Training Checkpoint** 通常保存训练到某一步的状态（至少包含可恢复参数，可能包含优化器/调度器状态）；**LoRA Adapter** 是适配后的参数产物，未必包含可精确继续训练所需的全部状态。

### 6. Hugging Face 训练工具链的分工

| 组件 | 负责什么 | 位于何处 |
|---|---|---|
| **PyTorch** | 张量计算、反向传播与参数更新的基础框架 | 底层计算 |
| **Transformers** | 加载 Qwen 模型、Tokenizer、Chat Template、生成接口 | 模型及推理接口 |
| **Datasets** | 加载、变换、组织样本 | 数据接入 |
| **TRL** | `SFTTrainer`、`SFTConfig` 等 SFT 训练封装 | 训练流程 |
| **PEFT** | `LoraConfig`、LoRA Adapter 的创建、训练和保存 | 参数高效微调 |
| **bitsandbytes** | 4-bit NF4 等量化算子 | 量化基础模型 |
| **Accelerate** | 设备配置及训练执行管理 | 训练运行支撑 |
| **safetensors** | 常见的模型/Adapter 权重安全存储格式 | 模型文件 |

这些库并不代表八套独立模型。它们围绕一个 Qwen 模型组成训练工具链。最终 Docker 中也不一定需要把本地所有开发依赖原样复制过去。

## 五、实验、指标与模型选择

### 1. Baseline、E00、E01、Ablation

**Baseline（基线）**：对照实验中的参照方案，用于判断某项新方法到底有没有收益。

**E00**：未经本次比赛 SFT 的原始 Qwen3-1.7B，在统一 Prompt 和评测接口下生成完整 JSON，测量它原本的能力。这里的“零微调”不等于一定没有任务指令；Prompt 仍然需要说明比赛任务。

**E01**：同一个基础模型经过 A0 标准 Completion-only QLoRA SFT，再用与 E00 一致的输入与指标评测，观察净收益。

**Ablation（消融实验）**：保持大部分条件不变，只去掉或更改某个设计，例如 2,048 与 4,096 Token 历史预算比较。用以判断该因素是否真的有效。

比较 E00/E01 时，应固定数据版本、Prompt、Chat Template、历史截断、推理解码、指标实现及尽可能一致的运行环境；否则无法确定变化来自训练还是其他因素。

### 2. Accuracy、Precision、Recall、F1

**Accuracy（准确率，Acc）**：单标签情绪分类中，预测类别与正确类别完全一致的比例；比赛情绪任务公布使用该指标。

**Precision（精确率）**：模型预测成某类/某标签的记录中，有多少确实正确。**Recall（召回率）**：真实属于某类/某标签的记录中，模型找回了多少。**F1**：综合精确率和召回率的指标。

**Macro-F1**：先分别计算各类 F1，再平均，使少数类别也在平均时有明显权重。**Micro-F1**：汇总各类的预测结果再计算，通常更受常见类别影响。

例：如果 `anxiety` 很多，模型总是预测 `anxiety`，可能取得不低的总体 Acc，但对 `surprise` 等少数类几乎没有识别能力。因此还需要查看**混淆矩阵（Confusion Matrix）**，即真实类别与预测类别的交叉计数表。

画像是**多标签**任务，不能直接照搬情绪的单标签 Acc。需分别观察每个标签的正确预测、遗漏、误报与空数组预测。官方所称“画像维度平均准确率”的具体计算定义目前尚不能仅凭名称确认，应保留本地诊断指标而不假称它们等同于官方评分。

### 3. BLEU-4、ROUGE-L、BERTScore

它们比较**模型回复**与数据集**参考回复**，但关注点不同：

| 指标 | 大致衡量 | 需要注意 |
|---|---|---|
| **BLEU-4** | 生成文本与参考文本的最多四词元连续片段（n-gram）重合及长度惩罚 | 表述差异较大时可能得分不高；中文分词/Tokenization 规则影响结果 |
| **ROUGE-L** | 生成文本与参考文本的最长公共子序列（LCS）相似性 | 对文本顺序与词语重叠敏感 |
| **BERTScore** | 利用预训练语言表示比较生成文本与参考文本的语义相似性 | 受所选编码模型、语言、版本与计算配置影响 |

情感陪伴回复往往不只有唯一正确的表达，因此 BLEU/ROUGE 偏低不必然表示回复不合理；反过来，指标偏高也不保证回复在实际对话中足够安全或有共情。比赛仍要按官方指标优化，同时通过少量人工抽样检查质量。

**Reference（参考答案）**：数据集提供的标准回复；**Prediction（模型预测）**：模型实际生成的回复。指标由两者比较得到。

### 4. 延迟、吞吐、显存与 JSON 合法率

**Latency（延迟）**：一次从接收输入到输出完成所用时间。本比赛关注端到端平均推理延迟；需要明确计时是否包含加载模型、Tokenization、生成和 JSON 后处理，以官方测试脚本为准。

**TTFT（Time To First Token，首 Token 延迟）**：开始请求到第一个生成 Token 的时间；**Tokens/s（每秒生成 Token 数）**：生成速度。它们可用于性能诊断，但不等于比赛的端到端延迟。

**Prefill（输入处理阶段）**：模型处理已给定 Prompt，生成首 Token 前的主要计算；**Decode（逐 Token 生成阶段）**：之后不断生成新 Token。增加历史 Token 主要影响输入处理与缓存开销；增加回复生成长度会增加解码耗时。

**P50/P90 延迟**与此前的 **P50/P90 Token 长度**是相同的统计概念应用于不同对象：P90 延迟表示大约 90% 的请求用时不超过该值。比较延迟时要固定硬件、并发、输入长度分布和预热方式。

**VRAM（GPU 显存）**：存储模型权重、运行缓存和训练中间状态等。**Peak VRAM（峰值显存）**：一次运行期间的最大占用；要区分 PyTorch 的已分配显存统计与整卡实际占用。

**JSON 合法率**：模型原始生成结果能否按 JSON 解析并通过字段/标签 Schema 校验。应分别记录原始生成合法率与最终后处理提交合法率，不能用事后修补掩盖模型本身的问题。

### 5. 开发期调参和验证集过拟合

**Hyperparameter（超参数）**：训练前由开发者设置而非通过模型训练直接学习的值，例如学习率、Epoch、LoRA Rank、Batch Size、最大序列长度。

**Overfitting（过拟合）**：模型或整个开发过程对见过的训练/验证样本过度适配，以至于在新数据上表现下降。即使 Dev 没参与梯度更新，反复据此挑选 Prompt、参数和模型，也可能出现开发验证集过拟合。

因此日常调试以 Dev 为主，官方 Val 主要用于重要版本的阶段性确认。经过充分验证后可以考虑用 Train+Dev 重新训练最终版本，但须换用新实验 ID 并记录这次变化。

## 六、推理、模型文件与 Docker 提交

### 1. 推理和生成参数

**Inference（推理）**：给定新的历史对话，用已经训练好的权重生成 JSON，不再更新模型参数。

**Autoregressive Generation（自回归生成）**：模型一次预测下一个 Token，追加到上下文，再预测后续 Token，直到生成结束标记或达到长度上限。

**Decoding Strategy（解码策略）**：从模型预测的概率中选择下一 Token 的规则。**Greedy（贪心）**每次选最高概率；**Sampling（采样）**按概率随机选择；`temperature`、`top_p`、`top_k` 用于控制采样分布。E00/E01 对比应固定这些参数；确定性解码虽然利于复现，但不保证回复质量最优。

### 2. Base Weights、Adapter、Checkpoint 与模型合并

| 文件/产物 | 代表什么 | 用途 |
|---|---|---|
| **Base Weights** | Qwen3-1.7B 基础权重 | 推理/微调共同的起点 |
| **LoRA Adapter** | 比赛监督微调得到的小型参数增量 | 与基础模型一起推理或进一步处理 |
| **Training Checkpoint** | 某训练时刻可恢复训练的状态，可能包含优化器等 | 恢复中断训练、对照中间版本 |
| **Merged Model** | 将 Adapter 效果合并进兼容格式的模型权重 | 某些部署方案可直接加载，但合并/精度需检验 |
| **Tokenizer/Config** | 词表、模板、模型及生成配置 | 保证权重按照正确输入/结构运行 |

量化训练得到的 Adapter **并不意味着**能直接按相同方式被任何 vLLM 部署版本加载。要在实际版本上测试 Adapter 加载、权重合并、BF16/量化导出等路线，不能把“LoRA 保存成功”当作“镜像可提交”。

### 3. Docker Image、Container 和 vLLM

**Docker Image（Docker 镜像）**：封装操作系统依赖、Python 环境、推理程序、模型文件和启动方式的可交付包。**Container（容器）**：镜像启动后实际运行的实例。镜像不是一个模型名称，也不天然包含预训练模型权重。

**vLLM**：主要负责高效加载大语言模型并执行推理的运行框架；它不是 Qwen 之类的具体基础模型。我们在本地用 Transformers/TRL 训练，最后可以使用独立的 vLLM 推理容器交付。

主办方已确认：**数字人情感陪伴赛道没有统一基础 Docker 镜像**；队伍可以自行构建 vLLM 镜像；**导出的参赛镜像文件不得超过 50GB**。平台上的“vLLM 公有镜像”是可选的运行环境起点，不代表提供了比赛专用预训练权重。

**Offline Inference（离线推理）**：评测运行时不依赖从 Hugging Face 下载模型或访问外部 API。最终镜像必须包含需要的运行组件和模型文件，且满足参赛入口协议。

### 4. `participant/`、`start.sh` 与提交文件

仓库已有的 `participant/` 是主办方参考推理接口，不是日常训练代码目录。最终执行关系为：

```text
官方测试 JSONL + 结果目录
         ↓
participant/start.sh
         ↓
run_inference.py / 模型加载与统一 Prompt 构建
         ↓
Qwen + 已训练参数推理
         ↓
JSON 解析、合法标签校验、输入 ID 透传
         ↓
submission.jsonl + performance_report.json
```

- `submission.jsonl`：逐条保存比赛要求的预测结果（含情绪、画像、回复等）；字段名与 ID 必须符合官方协议。
- `performance_report.json`：推理运行的性能报告；具体字段以正式参考程序和规则为准。
- `start.sh`：供平台无人工介入调用的统一启动入口；在 Docker 内应能根据输入路径与结果目录完成任务。

**接口一致性**：D0.4 构建的 Prompt/Chat Template、字段顺序和生成停止逻辑应与最终推理程序一致。官方示例的内部拼接方式可以根据规则适配，但入口和输出格式不能被随意改变。

## 七、工程配置、复现与协作

### 1. YAML、Profile 和 Experiment ID

**YAML**：用于保存人类可读的配置（如模型路径、学习率、长度预算），避免将参数散落硬编码于 Python 文件。

**Profile（硬件配置档）**：用 `local_8gb.yaml`、`server_24gb.yaml` 等文件管理不同机器上的显存相关限制，如 Micro Batch、训练长度和梯度检查点设置。硬件 Profile **不应改变标签含义、Schema 或历史合法性规则**。

**Experiment ID（实验编号）**：例如 E00、E01，用来关联模型配置、训练日志、生成结果和评测指标。不能只靠“最新模型”“最后一次训练”等模糊描述区分实验。

本项目决定采用配置覆盖次序：基础配置 `base` → 硬件 `profile` → 实验 `experiment`；运行时输出最终实际生效的 `resolved_config.yaml`，避免以为改了配置却没有真正生效。

### 2. Reproducibility、Random Seed 和 Versioning

**Reproducibility（可复现性）**：别人拿到相同输入、代码、配置、模型及依赖版本，可以尽量复现数据处理、训练与指标结果。GPU 训练可能存在部分非确定性，因此对齐运行条件与记录差异比只宣称“完全相同”更重要。

**Random Seed（随机种子）**：控制数据划分、训练顺序、初始化或采样中的部分随机性。固定 Seed 有助于公平比较，但不等于覆盖所有硬件非确定性。

**Git Commit / Revision**：分别标识代码版本以及 Hugging Face 模型/Tokenizer 的特定版本。**requirements-lock.txt** 则记录安装的 Python 依赖版本；不能把某台电脑当时的环境推测为所有机器都完全一致。

**Manifest（数据/运行清单）**：记录输入路径、文件哈希 SHA-256、数据处理版本、样本数量及产物位置。**SHA-256** 是文件内容指纹，用于验证原始文件没有被意外修改。**Cleaning Log** 记录隔离与去重的来源，**Split Manifest** 记录 Train/Dev 划分。

### 3. 一次实验应保存什么

```text
Experiment E01
├─ 代码版本 + 基础模型/Tokenizer Revision
├─ 数据版本 / 清洗政策 / Train-Dev 划分
├─ resolved_config.yaml + 随机种子
├─ 训练日志（Loss、Step、显存、耗时）
├─ 模型 Adapter / 必要 Checkpoint
├─ Dev/Val predictions.jsonl
├─ metrics.json（分类、画像、回复、性能）
└─ 简明实验结论：本轮改变什么、观察到什么、下一步验证什么
```

记录的重点是**形成证据链**，不是为了看起来规范而制造大量不可维护的自动报告。源码、配置和结论摘要进 Git；原始赛事数据、完整模型、Checkpoint、大量中间产物通常不进入 Git。

## 八、把所有概念贯穿为一次实际执行

假设官方某条训练记录中，目标用户说“每天学很久，但还是担心自己做不完”，标准情绪为 `anxiety`，另有用户画像和参考回复。

**数据阶段（D0.1～D0.3）**：读取原始 JSONL，验证该预测点合法；依据 `target_user_turn_id` 截止 History；按政策清洗或去重；确保其 Conversation 所属组只进入 Train 或 Dev；生成带来源定位的规范化样本。

**模型输入阶段（D0.4）**：从规范化 History 创建 System 指令和多轮 Chat Messages，形成 Prompt；将情绪、画像和参考回复序列化为 Completion JSON；用 Qwen Chat Template 和 Tokenizer 编码；统计实际 Token 长度；如果超出预算，优先按 T1 缩短更早 History，不能截坏 Completion；训练时设置 Prompt 的 Label 为 `-100`，Completion 的 Label 为正确 Token ID。

**训练阶段（E01）**：加载 Qwen 基础模型及 NF4 量化权重，插入 LoRA Adapter；逐 Batch 前向计算目标 Token 的预测损失，反向传播更新 Adapter；通过配置控制 Epoch、Micro Batch、梯度累积、学习率和检查点；保存权重与日志。

**评测阶段（E00/E01）**：对同一 Dev/Val 输入，仅给 Prompt，不给真实标签；分别让原始模型和微调模型生成完整 JSON；进行合法性校验；计算情绪 Acc、画像指标、BLEU-4/ROUGE-L/BERTScore、延迟等；比较结果并记录实验结论。

**交付阶段**：选定模型及配置；验证 Adapter 或合并权重能被指定版本的 vLLM 正确加载；构建不超过 50GB、可离线推理的 Docker 镜像；通过官方 `start.sh` 输出 `submission.jsonl` 与性能报告。

至此，每个概念都对应实际执行中的一个环节、一个输入输出契约或一项可调参数，而不是孤立的术语表。
