## 一、先知道这个项目在做什么

### 1. 赛事目标与交付对象

项目参加「数字人综合情感陪伴对话模型」赛道。当前实现范围是**文本多轮对话预测**，不是数字人形象、语音或视觉系统。输入为截至当前用户消息的合法对话历史，输出三类结果：

1. **情绪识别**：从官方给定的 16 个情绪标签中选择一个主要情绪。
2. **用户画像**：在 `personality_traits`、`interests`、`style` 三个维度上预测标签集合，共有 33 个候选标签；证据不足允许空集合。
3. **情感陪伴回复**：根据上下文生成中文自然语言回复。

内部第一阶段使用单一自回归语言模型，一次生成完整 JSON，然后由推理程序补齐输入 `id`、校验与规范化。竞赛公布的自动项为情绪 Accuracy（25 分）、画像（15 分）、回复 BLEU-4/ROUGE-L/BERTScore（20 分）、推理性能（10 分）；另有技术/训练/实验/复现类专家评审项目（合计 30 分）。**本地评测实现是代理指标，不可直接当作官方最终得分**；官方画像与耗时映射的部分精确定义仍待核实。

主办方已明确：**不提供统一基础 Docker 镜像**；自行准备 vLLM 等部署环境，最终导出镜像文件不得超过 **50GB**。官方调用契约如下：

```bash
bash /root/participant/start.sh TEST_FILE RESULT_DIR
```

`start.sh` 保留固定 `conda_env` 激活和两个位置参数；需要输出 `RESULT_DIR/submission.jsonl`、`RESULT_DIR/performance_report.json`。`participant/run_inference.py` 是**可适配的实现**，但必须保持调用、Schema、ID 和性能记录契约。`participant/templates/submission_schema.json`、官方数据和既有版本化协议不得随意改写。

### 2. 已选主线 A0 与未实施候选

**A0 是第一轮标准训练/推理对照的架构原则**：

- 模型：`Qwen/Qwen3-1.7B`，官方已后训练版本，**不是**名称带 `-Base` 的仅预训练模型；E00 是“尚未针对赛题微调”，不是“模型本身没有经过指令后训练”。
- 训练：4-bit NF4 加载冻结主模型 + LoRA 参数更新，即 **QLoRA**；采用 **Completion-only SFT**，首轮标准 Token 交叉熵，不加字段损失权重。
- 预测：单模型、一次联合 JSON 生成、Non-thinking；不先引入独立分类器、额外模型、RAG、记忆库、DPO 等。
- 实验：E00 是同权重的零赛题微调基线与诊断；E01 是保持输入/输出评测条件尽可能一致的标准 QLoRA SFT。
- 备选架构与优化方向可以登记，但不能暗中混进 A0 首轮验证。

模型设计、原始数据结构、训练损失与交付边界见：[`docs/task/A0_技术架构与实验方案.md`](https://github.com/LIZZYGREAT/EmotionCompany/blob/e00-1-evaluation-infrastructure/docs/task/A0_技术架构与实验方案.md)。

## 四、数据如何从原始资料进入训练与评测

### 1. 原始结构与数据隔离

官方 Train/Val JSONL 的一行是一段完整对话，包含 `turns[]` 和 `prediction_points[]`。一个预测点定位某条用户消息、对应的目标 Assistant 回复和正确标注：

```text
官方 conversation + prediction_point
  → 依据数组时间顺序截出截至目标 user 的 history
  → 从 prediction_point 读取 target（训练与评分的标准答案）
  → D0.3 规范化为「history + target」的样本
  → 训练：history 作为输入、target 作为 Completion
  → 推理：只传 history；评分时才在另一个文件读取 target
```

**训练与评测的绝对约束**：不能把当前目标 Assistant 回复或未来轮次放进 history；Dev 不可混回 Train；官方 Val 不用于调参。按对话/历史关联分组切分以避免高度重叠预测点跨 Train/Dev 泄漏；相似样本及历史口径以 D0.3 版本化逻辑为准。

### 2. 数据阶段账本

## 五、冻结的 P0 / F2 / T1 与 S/P/G/K

P、F、T 是本项目自己的三个协议版本系列，不是框架术语：

| 协议 | 已确定的实现职责 | 当前版本 |
|---|---|---|
| P：Prompt | 定义模型任务、情绪与画像合法标签、JSON 输出要求 | **P0**：`configs/prompts/p0.txt` |
| F：Format | 系统指令 + 原生多轮 `system/user/assistant` 消息，使用 Qwen 自带 Chat Template 编码 | **F2** |
| T：Truncation | 以真实 Token 数量选取最近、连续、完整的 history 后缀，最后用户消息必保留 | **T1** |

完整主线：

```text
D0.3 history (+ 训练时持有 target)
   → P0 定义任务
   → T1 在 P=1280 内试探最近连续历史后缀
         （每次测长度时调用 F2/Tokenizer）
   → F2 / Non-thinking Qwen Chat Template
         → 与训练和推理完全一致的 Prompt Token IDs
             ├─ 推理：模型自由生成 JSON → 解析/归一化 → Submission
             └─ 训练：追加 Gold JSON Completion，labels 对 Prompt=-100
                          → Completion/EOS 位置受监督
```

`src/shared/prompting.py` 负责共享方法 `build_messages`、`select_recent_complete_suffix`、`encode_inference_prompt`、`encode_full_training_sequence`、`serialize_completion`。训练与推理需满足 `full_ids[:len(prompt_ids)] == prompt_ids`，不能另写一个近似模板。历史 Assistant 文本若包含字面 `</think>`，已有 `reasoning_content=""` 处理防止模板误拆原文。

四个预算变量：

- `S`：训练完整序列上限，Prompt + Gold Completion；候选 **2048**。
- `P`：输入 Prompt Token 上限；候选 **1280**（注意与版本名 `P0` 不同）。
- `G`：推理最多生成 Token；E00 联合任务参考 **1200**，单字段诊断另用 **64**。
- `K`：实际部署服务上下文窗口，目前 **未验收/未冻结**。部署应验证 `P+G≤K`，`S` 不等于 `K`。

**变更原则**：P0/F2/T1/Tokenizer 模板和 D0.3 数据划分均有版本与指纹，若是语义变更，要另建 P1/F3/T2 或数据版本，并重新检查训练/推理一致性、历史选择与指标；如果是 Bug 修复，给出复现和回归证明。不因某次分数低而直接覆盖 P0。

参考：`docs/knowledge/PFT_输入协议设计与版本演进笔记.md`。

## 六、E00 阶段已做过的实验及可得结论

### 1. E00.1：评测基础设施，不是模型成绩

从 D0.3 Dev **1,833** 条构建不含 Gold 的推理输入、独立 References、ID Map 和固定种子选出的 20 条 Smoke。完成 Mock/合成数据下的字段、ID、哈希、标注隔离、JSON 解析和指标链路验收。**Mock 模型分数不得当作模型能力。**

### 2. E00.2：真实基础模型 Greedy vs Sampling

运行身份 `E00.2-20261026-220635`。同一组 20 条 Smoke、相同 P0/F2/T1、同一 Qwen3-1.7B 权重（NF4/BF16）。Greedy `do_sample=false`；Sampling `do_sample=true, temperature=0.7, top_p=0.8, top_k=20`，按 ID 派生确定性随机种子。关键结果：

| 指标 | Greedy | Sampling | 如何理解 |
|---|---:|---:|---|
| 情绪 Accuracy | 1/20（5%） | 1/20（5%） | 两者均极低，但 20 条不代表全 Dev |
| 情绪 Macro-F1 | 0.0179 | 0.0179 | 固定 16 类平均，非“正确率” |
| 画像三维 Exact Match | 5/20（25%） | 5/20（25%） | 包含正确空集匹配，不能推断真实画像能力已达 25% |
| 33 标签画像 Micro-F1 | 0.0400 | 0.0417 | 预测质量很弱 |
| 字符级 BLEU-4 | 2.2406 | 1.9297 | 本地 `sacrebleu` 字符级分数，非准确率 |
| 字符级 ROUGE-L | 0.1290 | 0.1102 | 本地字符最长公共子序列分数 |
| Raw 严格 JSON | 10/20 | 9/20 | 格式本身不稳定 |
| Raw 完整 A0 Schema 合法 | 0/20 | 0/20 | 没有一条完整原文满足 A0 原始输出规范 |
| 归一化 Submission Schema 合法 | 20/20 | 20/20 | 由容错归一化得到；**不等于 Raw 合法** |
| 平均延迟（20 条） | 3.335s | 3.538s | 不代表官方 100 条性能结果 |
| BERTScore | 未运行 | 未运行 | 不得写成零分 |

两组都 EOS 停止，没有碰到 `G=1200`。采样并未显示可信的质量优势；**不能根据这 20 条冻结解码参数**。性能报告中 `required_rounds=100` 而实测仅 20，因此不属于官方完整性能轮次。

### 3. E00.2 离线错误归因：揭示真正的问题层次

在相同 Raw 上区分严格 JSON 与宽松对象提取：Greedy 宽松提取到 **11** 个合法情绪标签，**1** 正确、**10** 个合法但错判；Sampling 合法 **10**、正确 **1**、错判 **9**。Greedy 缺少有效情绪字段 9 条、Sampling 10 条（分别包括各 5 条根本提取不出对象）；画像常出现非法枚举和字段类型错误。

后处理会在画像维度非法时将该维度**整体清空为 `[]`**；有时连原本合法的标签也被丢弃。因此必须分开报告 **Raw 模型能力** 与 **Submission 后处理合规性**。目前没有证据表明 Parser 存在需要立刻修改的复现 Bug；合法标签仍频繁错判，不能指望只改 Parser 修复分类。

T1 在 20 条 Smoke 中实际裁剪 4 条；无裁剪组的分类也很差，**截断不能解释这次所有低分**。但小样本不足以作裁剪因果结论。

### 4. E00.2-D：只输出单个情绪标签的专项诊断

运行身份 `E00.2-D-emotion-003`，Prompt `Pdiag-E1`；复用 A0 实际选定的 20 条历史，模型和权重不变，Greedy，`max_new_tokens=64`。所有 20 条均以 EOS 停止，无生成失败或 Token 上限触发。结果：

- **15/20** 输出严格匹配一个合法英文情绪标签；其余 5 条不合格式。
- **0/20** 正确，Accuracy 和固定 16 类 Macro-F1 均为 **0**。
- 15 条合法标签分布：`relaxed=5`、`neutral=5`、`fear=4`、`anxiety=1`；没有命中任何 Gold。
- 该 20 条特意覆盖 16 类情绪（每类支持 1～3）；Train 多数类 `anxiety` 在这里能命中 2/20（10%）。

**解释边界**：任务说明和输出契约一起发生变化；A0 的 11/20 是“宽松提取合法字段”，单字段诊断 15/20 是“原文严格单标签合法”，分母相同但**判定条件不同**；正确数差 1 条不支持证明单字段 Prompt 更差。诊断说明问题不只是 JSON 解析，但不能确定标签边界、模型容量、数据标注或任务适配中的具体因果。

### 5. 当前 E00 可以写下的结论与不能写的结论

**有证据支持：** 数据与评测基础设施可运行；零赛题微调的 Qwen3-1.7B 在现有 20 条样本上输出格式和分类质量都差；后处理掩盖部分 Raw 结构错误；单字段化仍未获得可靠分类结果；4-bit 推理可运行。

## 八、接下来应该做什么：任务顺序与决策门槛

### 1. P1：先制定 E01 最小 QLoRA 可学习性方案，暂不大规模训练

**当前下一阶段首要技术任务**是编写并实施可控的 micro-overfit / 训练路径验收，而不是马上调几十轮 Prompt 或下载更大模型。建议拆成以下可核对阶段：

**E01-preflight：训练载入与参数边界**

- 从 D0.4.3 的有效 **Train** 小集合读取预编码样本；独立 Dev 只作验证，不参与更新。锁定样本 ID、配置、Seed 与数据 Manifest 指纹。
- 固定相同 Qwen 权重、Tokenizer、P0/F2/T1；核对已有 Collator 产出的 `input_ids/attention_mask/labels`，Prompt 为 `-100`，Completion/EOS 被正确监督。
- 用 NF4/BF16 加载真实 Qwen；加入 LoRA 后验证仅预期 Adapter 参数 `requires_grad=True`；保存参数计数和设备、版本、显存记录。

**E01-train-smoke：真正发生训练**

- 至少完成真实的 `forward → loss.backward → optimizer.step → zero_grad`；记录有限 Loss、有限梯度、Adapter 参数实际改变、每步用时和峰值显存。
- 进行有限步数、少量 Train 样本 micro-overfit：检查能否学习输出合法联合 JSON、正确情绪和画像；训练样本成绩不是泛化成绩。若 OOM，优先最小化 batch/梯度累计/激活策略并记录实际变更，不静默更换模型或 S/P。
- 验证 Adapter **保存与重新加载**，同输入的确定性推理可复现；模型指纹/训练配置/权重产物被正确归档（大文件只在忽略目录）。

**E01-eval-smoke：分开训练拟合与 Dev 泛化**

- 训练集 micro-overfit 和未参与训练的 Dev 分开打分；至少包括情绪 Accuracy/Macro-F1、画像、Raw JSON/A0 合法率、Submission 合法率及回复合理性。
- 发现错误先核对 Labels/Masks、Loss、参数更新、推理加载与文本生成，再判断是否值得修改 Prompt 或扩大训练；完整 Dev/E00.3 不是本次 micro-overfit 的前置条件，但后续公平对照须安排。

**E01 micro-overfit 完成门槛**：真实权重加载、LoRA 冻结范围、前反向梯度、Optimizer 更新、显存/日志、Adapter 保存重载、训练样本诊断和独立 Dev 小样本报告全有实际证据；**仅仅 Loss 下降并不能替代所有门槛**。仓库目前 `src/training/training_sft.py` 为空，不要误报训练代码已实现。

### 2. P2：E01 稳定后才挑选调优实验

已有候选池在 `docs/experiments/后续调优候选与实验决策.md`；它记录的是 **ideas，不是已批准执行任务**。重点方向：

- **Prompt/格式**：给 16 类情绪补定义及易混边界；强化 JSON 格式提示；从 Train 选择可追溯 Few-shot；在目标后端验证结构化约束解码。每项要额外衡量 Prompt 变长带来的 T1 裁剪和延迟成本。
- **训练**：LoRA Rank/LR/训练步数的单因素试验，字段 Loss 加权，专项样本混合比例，类别不平衡审查（Macro-F1 与少数类召回），必要时重审 Train 标签质量。
- **模型**：将 Qwen3-1.7B 作为稳定基线；Qwen3-0.6B 用于成本比较、Qwen3-4B 用于能力对照、Qwen3.5-2B 用于新架构候选；模型/Tokenizer/LoRA/vLLM/许可证兼容性和 8GB 训练/推理资源均先做预审，**不把备选视为已下载或已验证**。
- **推理/部署**：Greedy/Sampling、字段级后处理、不同 P/G/K、BERTScore 对齐、vLLM 服务端模板 Token ID 一致性、官方 100 轮性能与最终离线 Docker。

每次实验明确：**唯一主要变量、对照基线、输入 ID 与 Hash、训练数据来源、版本、指标、资源预算、停止条件和产物路径**。不要靠 20 条分层 Smoke 选模型或解码胜者，不用官方 Val Gold 调 Prompt，也不要把官方未确认的画像计算规则当已知。

### 3. P3：之后的正式评测与部署

E00.3 的完整 1,833 条 Dev 零赛题微调评测尚未执行；正式 E00/E01 比较需要相同输入、P0/F2/T1、解码与评分，并明确模型权重差异。BERTScore 尚未运行，必须选定离线模型、revision 和固定实现后才可填报；100 条性能测量尚未达到；vLLM、Adapter 与最终量化权重加载、服务端 Token ID 等价、官方启动入口及 ≤50GB 镜像均未验收。

## 九、新对话 / 新 Agent 开始时的工作准则

1. **先读本文件和当前仓库 HEAD**，再依次查 `docs/experiments/E00_阶段总结与E01交接.md`、`docs/knowledge/PFT_输入协议设计与版本演进笔记.md`、`docs/data/D0.4.3_监督数据构建与Batch验收报告.md`、`docs/knowledge/双人Git协作与PR操作规范.md`。新任务涉及的实现模块再读对应源码，避免一次读完整个仓库却没有形成真实调用链。
2. **理解真实流程，再写任务方案**：从当前拥有的 JSONL/Token IDs/Labels 出发，明确 DataLoader → Model → Loss → Optimizer → Adapter 保存 → Reload → 生成 → Scorer，各模块的输入、输出、状态、职责和验收点；不要只堆 LoRA/SFT 的定义。
3. 实施类任务优先交付可直接执行的 Markdown 方案，写清改哪些文件、如何验收、命令和预期结果；有语义选择时先解释选项。避免额外重构现有冻结协议、批量生成难维护的文档或引入无关的过度防御框架。
4. **任何完成性陈述要有边界**：区分 Mock 与真实 Qwen、CPU CI 与 GPU、Smoke 与完整 Dev、Raw 与 Submission、历史归档与新跑结果、候选值与冻结参数、Git 提交与服务端规则启用。
