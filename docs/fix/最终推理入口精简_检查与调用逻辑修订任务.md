# EmotionCompany 最终推理入口精简：检查逻辑与调用逻辑修订任务

> **执行对象**：Codex。代码基准 `feat/final-dual-adapter-delivery`，审查 HEAD `4934efd818841ce20ab742f1e520962f8d81c038`。实施时记录实际 HEAD，另建修复分支，不覆盖上一版可运行镜像及两份 Adapter。<br>
> **任务范围**：只修改推理运行时的检查逻辑和调用链。保持 Qwen3-1.7B Base、A8 P4504、E03-B Replay-1152、两份 Prompt、历史选择、字段解析协议与串行推理方式不变。不训练、不调整生成质量、不比较任何模型预测结果的一致性。

## 一、期望的最终运行链

官方固定入口：

```bash
bash /root/participant/start.sh TEST_FILE RESULT_DIR
```

容器内的最短执行链：

```text
start.sh(TEST_FILE, RESULT_DIR)
  → 使用 /opt/conda/envs/conda_env/bin/python
  → 启动一个 vLLM 服务（一个 Base + 两份 LoRA）
  → 读取 TEST_FILE 中各条 id/history
  → 每条先请求 profile，再请求 emotion-response
  → 按原协议解析，异常字段使用约定的空值/文本兜底
  → 写 submission.jsonl、performance_report.json
  → 释放服务，退出 0
```

只要整个文件处理完毕并写出两份结果文件，就按正常推理结束处理。模型回答质量、单字段错误、回复截断和不同运行之间的文本差异，都不得导致整批失败。确实无法执行（如缺少模型、启动服务失败、输入不可读、无法写入结果）时记录错误并返回非零。

## 二、方向 A：清除不必要的运行时检查

### A1. 从启动链删除资产与代码指纹硬门禁

修改 `participant/final_dual_inference.py`：

- `_verify_runtime_code_identity()`：从官方入口调用链移除。删除行为版本、运行代码 SHA、Git HEAD 与 Model Lock 的匹配阻断。
- `_verify_assets()`：改成最小化的 `load_runtime_assets()`（函数名可调整）：定位并加载 Base、Tokenizer、两个 Adapter 的真实文件以及四份 Prompt。仅检查必要路径是否存在、配置能否解析、依赖能否加载；不在正式运行时逐文件计算/匹配 Base、Prompt、Adapter、Tokenizer、Chat Template、配置文件 SHA。
- 如果底层 `run_inference.load_runtime_tokenizer()` 仍会根据传入 `expected_*` 字段主动做指纹比对，则改用不带此类检查的加载参数或最小加载函数，避免“删了上一层，下一层仍拦截”。
- `model_lock.json`、`package_manifest.json` 可以作为**离线打包记录**保留，但正式推理不能依赖它们与当前源码逐字节一致才准运行；不存在也不应成为阻断理由，除非实现仍需其中的 Adapter **路径**，此时将路径直接写入部署配置。
- 删掉每条 Prompt/生成文本的 SHA 计算等与基本调用无关的身份审计，不产生额外的质量判定。

修改 `src/inference/final_dual_vllm.py`：

- `_check_version()` 不再严格解析并要求 vLLM 版本字符串恰好等于 `0.11.1`；只要求可执行文件能启动、服务能接受请求。不要为了版本检查再启动额外子进程。
- 服务启动时的 `/v1/models` 可以用于判断服务已经就绪；不要把额外的别名列表比较、权重身份声明当成必须全部通过的运行门禁。真正请求的 `model` 名称保持 `profile` / `emotion-response`，HTTP 请求失败时按实际错误处理。
- `nvidia-smi`、显存采样、版本信息都作为可选诊断，不能因为诊断命令不存在或监控失败而退出。

### A2. 删除 vLLM 返回值的额外一致性约束

修改 `src/inference/final_dual_vllm.py::DualLoRAVLLMService.chat_completion()`：

- 请求保留 `model`、`messages`、`max_tokens`、`temperature=0`、`chat_template_kwargs.enable_thinking=false`。
- 删除 `return_token_ids=True` 对响应行为的依赖；不要求服务器一定返回 `prompt_token_ids`。
- 删除 `expected_prompt_token_ids` 与观察值的逐 Token 比较、SHA 计算及 `prompt_token_ids_exact_match` 字段。
- `usage`、`prompt_tokens`、`completion_tokens`、`response.model`、`response.id`、`finish_reason` 都只能作为**可选**返回信息，不得因不存在而抛异常。
- 正常响应只需可读取 `choices[0].message.content`；正文为空时按字段兜底，缺少 `choices` 或 HTTP 请求失败才作为一次真实请求错误。

修改 `participant/final_dual_inference.py`：

- 删除 `server_prompt_token_ids_mismatch`、`discarded_due_to_prompt_mismatch` 以及为它们触发的丢弃回复、重新请求与 `hard_failures`。
- 删除 `prompt_id_gate`、`aliases_gate`、`identity_gate` 及其对应分母、精确匹配次数等整套“输出匹配性”统计。
- 删除 `format_threshold`（95%）、`diagnostic_quality_gate`、`legacy_gate_passed` 等判定。**不再用任何质量阈值决定进程退出码**。
- 删除为诊断目的的逐条输出比较、重复文本检测、长度候选优劣比较；只保留原生解析器及必要的错误兜底。
- 若 `finish_reason=length`，优先使用已经生成的正文和现有字段兜底，不把上限命中作为异常退出。无需额外重复生成来“获得更好结果”。

### A3. 简化官方运行期间的输出管理

修改 `participant/final_dual_inference.py`：

- 官方默认执行中移除 `_resume_identity()`、`_new_transaction_dir()`、`_find_resumable_transaction_dir()`、`_sync_checkpoint()` 等与历史恢复、事务哈希一致性有关的复杂逻辑；不使用 `EVALUATION_RUN_ID`、`EVALUATION_RESUME` 作为正常运行前提。确实需要本地断点恢复可留在独立辅助脚本，不进入官方主线。
- 默认仅写官方需要的 `submission.jsonl` 和 `performance_report.json`，避免在 `RESULT_DIR` 创建 `.emotionalcompany_runs`、`run_progress.json`、`raw_outputs.jsonl`、大量诊断文件。必要的日志写 stdout/stderr 或临时目录。
- 允许 `RESULT_DIR` 已经存在；覆盖这两份官方结果文件，**不修改其他已有文件**。
- 不再进行旧结果文件 SHA、增量 Hash、文件身份和逐条生成结果一致性比较。
- 保留按前 100 条统计端到端时间；全部输入逐条写出 JSONL。写入可使用临时文件最后替换，失败时返回非零，不伪装为成功。
- 不再在正式运行循环中运行高成本的 `Draft202012Validator` 全量校验或任何历史结果比较。组装器仍须按官方字段与类型构建对象，异常字段依 `participant/README.md` 回退；**只在独立测试中检查最终官方 Schema**。

### A4. 最小检查保留清单

不要把必要操作也错误删除：

- `TEST_FILE` 存在、可读取、每行可解析为 JSON；`RESULT_DIR` 可以写入。
- Base、Tokenizer、两个 LoRA 和四份 Prompt 能加载；vLLM 服务可以启动并完成 HTTP 请求。
- 遵循原生历史构造，分别选择正确的两个 Adapter，且串行调用。
- `submission.jsonl` 含官方五个字段：`id`、`response_text`、`emotion_label`、`user_profile`、`memory_refs`。画像为三个数组，`memory_refs=[]`。对于格式不正确的某次生成使用字段级兜底，并继续处理后续样本。
- 输入无法读取、必需资产缺失、服务根本启动失败、结果文件无法写入时返回非零并打印原因。

## 三、方向 B：核对与简化 Docker/官方调用接口

### B1. Docker 入口兼容三种运行方式

需要修改 `docker/final_dual/entrypoint.sh`、`entrypoint_args.sh`、`Dockerfile`：

**官方真正固定的命令仅为容器内部** `bash /root/participant/start.sh TEST_FILE RESULT_DIR`。目前不能确认主办方使用 `docker run` 启动还是先启动容器再 `docker exec`；新镜像应兼容两类方式。

1. `docker run IMAGE TEST_FILE RESULT_DIR`：直接进入 `start.sh`。
2. `docker run IMAGE bash /root/participant/start.sh TEST_FILE RESULT_DIR`（或直接 `/root/participant/start.sh ...`）：参数转发给同一 `start.sh`。
3. `docker run -d IMAGE`：容器保持存活，使平台之后可以 `docker exec CONTAINER bash /root/participant/start.sh TEST_FILE RESULT_DIR`。无参数时仅进入空闲状态，**不启动模型、不生成结果、不消耗 GPU**。

同时支持 `docker run --entrypoint /bin/bash IMAGE /root/participant/start.sh TEST_FILE RESULT_DIR`。确保多种形式不会重复启动两次推理或重复执行一套启动检查。无参数空闲仅作为兼容入口，不把它推断为平台一定采用的方式。

### B2. `start.sh` 必须真正能独立执行

- Docker 内保留 `/root/participant/start.sh` 原位置、可读权限、`conda_env` 的真实解释器与依赖（使用 `/opt/conda/envs/conda_env/bin/python`）。
- 不依赖调用时的 `cwd`、Git、宿主机路径、额外 `EVALUATION_*` 变量。Docker 配置可以包含默认两 Adapter 路径；只凭两个位置参数就能运行。
- `start.sh` 的双 Adapter 分支应只负责**激活环境、调用唯一推理程序并原样传递退出码**。不要在 Shell 和 Python 两层都运行复杂资产预检，也不重复启动 vLLM。
- 正常完成后应终止 vLLM 子进程，并保留 `submission.jsonl`、`performance_report.json`。容器内临时日志不允许影响退出码。
- `TEST_FILE` 路径和 `RESULT_DIR` 可位于任意挂载位置，支持空格和已经存在的结果目录。不要根据路径是否在项目树内决定能否运行。

### B3. 测试文件读取容错

当前 `read_test_samples()` 使用 `set(row) == {"id", "history"}`，并严格限制历史消息字段。按照官方已给的 `id/history` 输入语义：

- 读取 `row['id']`、`row['history']`，忽略顶层其他字段；历史消息只取 `role`、`content`、必要的 `turn_id`，忽略其余元数据。**绝不将额外字段/target 放进 Prompt**。
- 可用的行应正常推理；某条历史内容不完整时，按既有字段级回退输出该条结果，而非整批崩溃。
- 无法解析 JSONL 或根本缺少两项必要输入时给出明确日志；不要凭空猜测另一种未确认的赛事输入 Schema。
- `id` 原样回填；要求正式输出符合官方 `submission_schema.json`，不从数据内容推断其他 ID 格式。

### B4. Docker 环境检查仅保留必要依赖

- `docker/final_dual/entrypoint.sh` 当前强制 `nvidia-smi` 存在且命令成功：取消这一前置门禁。`nvidia-smi` 仅用于可选日志；模型运行本身失败才报错。
- 可保留 CUDA 是否可用的简短诊断，但不要为诊断启动额外的大模型或 GPU 预占用。CPU/GPU 后端应按已冻结的 vLLM 部署配置调用，不能静默切成 Base-only。
- 移除其他外部命令探测、版本号严格比对、环境标识哈希检查；确保正式启动最先执行的是必须的加载与服务调用。

## 四、验收方法：只验证接口运行，不比较结果一致性

**仅进行以下运行测试：**

1. `bash -n`、Python `compileall`、定向 CPU 单测；只验证代码语法、调用和异常处理。
2. 无参数 `docker run -d --gpus all`（并预挂载输入及结果目录）后执行 `docker exec ... bash /root/participant/start.sh ...`；验证容器仍在运行、命令能执行。结束后清理容器。
3. 带两个路径的 `docker run` 和带完整 `bash /root/participant/start.sh` 的 `docker run`，分别验证能够调用成功。
4. 预建 `RESULT_DIR`，放入 `keep.txt` 和两份旧官方输出；执行后确认两份官方输出被覆盖，`keep.txt` 保留。
5. 使用 1～3 条合法输入，验证 `start.sh` 返回 0，并且提交文件逐条为可解析 JSON、具备官方字段；性能报告存在。另测试 1 条模拟模型格式异常，确认回退后继续下一条、进程不因质量问题失败。
6. 用附加顶层元数据的一条输入确认读取器不会提前拒绝；将一条错误输入单独测试，以便看到实际错误日志。允许在不影响基础接口的情况下补充更大规模运行，但**不要求任何模型预测相同**。

**明确不执行的检查**：不同运行结果逐字比对、LoRA 单独/联合推理 Token 结果比对、宿主/Docker 生成文本对比、Prompt Token IDs 对比、F1/Recall/Precision、格式成功率百分比门槛、完整输出 Hash 身份、强制 GPU 显存与版本锁一致性。

测试中若推理模型生成了错误标签，仍按官方回退协议输出；只有真正无法运行或没有生成官方所需文件时，才判为工程失败。
