## 三、任务 A（P0）：修复推理输入协议，复用唯一 P0/F2/T1

### A1. 统一 Prompt 数据源和历史选择

**现有事实：**

- `configs/prompts/p0.txt` 已有 P0 权威文本；`src/shared/prompting.py` 提供 `build_messages`、`encode_inference_prompt` 等逻辑。
- `src/data/token_stats.py` 已实现按真实 Qwen Tokenizer 长度选择最近连续历史后缀的 T1 规则 (`select_recent_complete_suffix`)。它目前处在审计模块里，不适合让正式 runner 导入上千行的审计脚本。
- `participant/run_inference.py` 仍保留独立 `SYSTEM_PROMPT` 和 `conversation_text()`，并把 `id` 塞入模型 Prompt；这些都不属于冻结的 P0。

**修改要求：**

1. 将可供运行时调用的 T1 选择逻辑提取/复用为一个**纯粹的小型公共函数**，建议放在 `src/shared/prompting.py` 或紧邻的 `src/shared/context.py`；原 `token_stats.py` 改为调用同一实现，保留长度审计缓存优化并通过直接实现对照测试。不要在 runner 中重新抄写 T1。
2. 运行时从 `configs/prompts/p0.txt` **原文加载** System Prompt；单一来源，禁止再次内嵌 `SYSTEM_PROMPT`，也不要通过 Python `set` 的迭代顺序拼标签（会带来输出不确定性）。
3. 读取测试 `history` 后按原始 `role/content` 保留独立消息；最后一条必须是 User；只根据固定 Prompt Token 上限 `P` 从当前 User 起向前选择**连续、完整**的历史消息；保留顺序、不修改正文、不插入测试 `id`、不跳过放不下的中间消息。
4. 使用与审计相同的 Qwen Tokenizer、固定 revision 与模板、`enable_thinking=False`，按真实 Token 数判断是否超过 `P`。不得用字符数、独立消息 Token 数简单相加估算。若 `System + 当前 User` 已大于 `P`，**明确标记 `prompt_floor_exceeds_cap`**；不得静默裁掉当前消息、偷偷放宽 P 或改写 Prompt。
5. 对无法满足配置上限的异常样本，采用**显式可配置、可记录**的处理路径。若进入正式提交模式，需要保障每条输入仍有一条符合官方 Schema 的结果，例如明确记录为失败并输出合法的兜底空预测（`emotion_label=""`、空画像等）；不得伪称该样本完成了按 P 的正常推理。不能把这类兜底算入成功生成率。
6. 共用一组 `messages` 用于两种推理后端。内部为模板兼容性而附加的 `reasoning_content=""` 不应被当成真实用户/助手文本；发送给 OpenAI-compatible API 时，需按服务端协议处理这个内部控制字段，并验证不会改写历史中出现的字面 `<think>` / `</think>` 等文本。若服务器不支持等价渲染，应显式报告阻塞，而不是隐式回退旧模板。

**数据流约束：**

```text
官方 TEST_FILE 中的 id、history
   ├─ id：只用于输出回填与日志，不进入 P0 模型 Prompt
   └─ history：保留多轮 role/content
          ↓
     同一 P0 文本 + T1(P, 真实 Qwen Tokenizer)
          ↓
     F2 原生多轮 Messages / enable_thinking=False
          ├─ Transformers：直接按同一模板输入 Token IDs
          └─ vLLM Chat API：传同一合法消息结构并明确关闭 thinking
          ↓
     生成并解析 JSON → 校验官方标签/字段 → 程序回填 id
          ↓
     submission.jsonl + performance_report.json
```

### A2. 修正 Transformers 路径

1. 不再通过 `apply_chat_template(..., tokenize=False)` 后未经严格控制又 `tokenizer(prompt)` 进行二次转换；改用公共构造器得到的**精确 `input_ids`**（与 D0.4.2 所测一致），并正确创建 `attention_mask`、张量批次和设备传输。
2. 显式使用 Non-thinking 模板参数，复用审计中的 Assistant 生成前缀。回归测试必须断言 runner 的输入 IDs 与 `encode_inference_prompt()` 对同一选中 History 的返回值逐 Token 一致。
3. 生成后只解码新增 Token，不解码 Prompt；保留现有 JSON 解析与 Schema 兜底语义。用官方训练 Schema 中的 16 类作为正常情绪集合，提交 Schema 中的 `""` 仅作为错误兜底。
4. 不改变本轮 `G=1200` 的实验参考属性；记下实际生成上限、停止原因、Prompt Token 数、生成 Token 数及无法构造样本数量（可添加到报告元数据）。

### A3. 修正 vLLM / OpenAI-compatible 路径

1. `messages` 必须是与 Transformers 分支**同源的 System + 原生多轮 User/Assistant**，不得把 History 打包成一个 User 字符串。
2. Qwen3 非思考模式对 vLLM Chat Completions 需要显式传：

   ```json
   "chat_template_kwargs": {"enable_thinking": false}
   ```

   通过现有 `api_options` 合法传入，或者代码将其作为**不可被默默覆盖**的协议字段；若用户的选项与冻结协议冲突，应报错而非静默改成 thinking。此字段是 vLLM 的扩展参数，不是所有 OpenAI-compatible 提供商都通用。
3. 客户端 T1 的 Tokenizer 必须与 vLLM 服务模型使用的 Tokenizer/Chat Template 实际版本相匹配；仅在客户端 `len(prompt_ids) <= P` **不足以证明服务端渲染长度相同**。首选通过目标 vLLM 版本提供的模板渲染/Token 诊断能力核验代表样本，至少记录服务端 `prompt_tokens` 并对边界案例进行对照。若版本未支持逐 Token 对照，必须将服务端等价性明确标为未验证，不得宣称通过。
4. 验证 Client/Server 请求能保留多轮角色、Non-thinking 标志、模型名、生成上限 `G`，并通过模拟 HTTP 请求检查 JSON Payload；若需要替代 API，只有经验证能提供**同一 Token 前缀**的方案才允许引入。
5. 维持现有请求超时、身份认证、`api_options`、`max_new_tokens → max_tokens` 的正常功能。

**技术依据：** Qwen 官方 vLLM 部署文档已展示 `chat_template_kwargs: {"enable_thinking": false}` 的非思考用法；实际语义仍以比赛镜像最终采用的 vLLM 版本为准。

### A4. 显式管理推理 P/G/K，但不抢先冻结实验方案

## 四、任务 B（P1）：补充 D0.4.2 报告，按 Split 呈现 S/P 结果

### B1. 从既有机器数据聚合，不重复大规模 Tokenization

优先使用：

- `outputs/token_audit/v1/budget_simulations.jsonl`
- `outputs/token_audit/v1/token_stats.json`
- `outputs/token_audit/v1/manifest.json`

请确认这些文件与当前 D0.3 版本、P0 哈希、Tokenizer revision 和候选网格相符；如果文件不存在或不兼容，再按现有命令重新审计，不得直接编造数据。

对**每个** `(S,P)` 分别生成 Train、Dev、Val 三组统计，并保留整体组仅供概览：

```text
Split | S | P | n_total | full_fit | trimmed_fit
      | prompt_floor_exceeds_cap | completion_overflows_train_budget
      | raw_full_fit_rate | usable_rate | truncation_rate | unusable_rate
      | mean_message_retention_ratio_proxy
```

**分母与定义（在 JSON 和报告中统一）：**

```text
N = 当前 Split（或 overall）中全部参与该候选模拟的样本数
n_full_fit + n_trimmed_fit + n_floor_fail + n_completion_fail = N
usable_rate     = (n_full_fit + n_trimmed_fit) / N
unusable_rate   = (n_floor_fail + n_completion_fail) / N
raw_full_fit_rate = n_raw_full_fit / N
truncation_rate = count(removed_history_message_count > 0) / N
```

最后一条**包含不可用但已经发生历史删除的样本**。它不是“有效可用样本中的裁剪率”，也不等于 `n_trimmed_fit/N`。如果将来希望额外报告后者，必须另起字段 `usable_sample_truncation_rate` 并注明不同分母；本次不强制新增该指标。

实现上优先新增小型**聚合函数**并由现有 `token_stats.py` 报告生成阶段调用；不建议为此再创建大型审计器。若只修改报告而未将生成逻辑同步更新，下次重跑会丢失修订，因此**必须修订自动报告模板**。
