## 一、首先对齐两种不同的“不能修改”

### 1. 赛事材料实际约束：**固定运行契约，而非冻结所有示例源码**

主办方原始 `participant/README.md` 约定，评测器执行：

```bash
bash /root/participant/start.sh TEST_FILE RESULT_DIR
```

- **`start.sh` 的绝对路径、两个位置参数和执行语义必须保持不变**。
- 脚本须完成所有输入样本预测；结果写到 `RESULT_DIR/submission.jsonl`、`RESULT_DIR/performance_report.json`；性能统计以前 100 条为准。

- 原始 `participant/start.sh` 明确注释“**启动虚拟环境 conda_env，名称固定，不要修改**”，并执行 `source activate conda_env`；必须保留正式提交入口这一行为。本地 WSL 若采用 `.venv`，使用外部测试包装/环境，不得改坏官方 `start.sh` 的固定约定。
- 输入 JSONL 的语义、官方输出 Schema、失败哨兵和错误容错等必须兼容。

**现有赛事资料没有给出 `participant/run_inference.py` 的源码禁止修改条款**。它是官方发放的参考/基础推理实现，但参赛者需要适配模型、Tokenizer、LoRA、量化及后端，所以应被标注为 **“允许修改、必须通过契约回归”**。切勿把整个 `participant/` 目录加入只读名单。若以后获得更高优先级的新官方说明，先更新本规则，再相应调整实现。

## 三、P1：修复真实 Dev Smoke 集合评分失败

**位置**：`src/evaluation/score.py`。当前 `prepare_dev.py` 确实创建完整 1,833 条与独立 20 条 Smoke，但 `score.py` 误把所有 `dataset_scope=D0.3_dev` 的集合都当成 1,833 条，并默认读取完整 `id_map.jsonl`。

### A. 数量校验正确区分完整集合和 Smoke

原逻辑概念上类似：

```python
if manifest.get("dataset_scope") == "D0.3_dev":
    if len(expected_ids) != config["data"]["expected_dev_count"]:
        raise ValueError(...)
```

**必须修改为**：

- 正式全量评测：`references.jsonl` ↔ `inference_input.jsonl` ↔ `id_map.jsonl`，预期 `1833` 条。
- Smoke：`smoke_references.jsonl` ↔ `smoke_input.jsonl` ↔ `smoke_id_map.jsonl`，预期等于 Manifest `smoke_selection.actual_count`（默认 `20`），且集合与 `smoke_selection.eval_ids` 完全一致。
- `source.dev_rows` 始终仍为 `1833`，只用于说明来源文件规模；不能拿它代替本次评分集合大小。
- 必须拒绝 Smoke 漏行、多行、重复 ID、错位映射、不同 Manifest 指纹；不能以“允许任意长度”来绕过防护。

### B. Smoke 必须自动选对 ID Map

当前默认 `id_map_path = references_path.parent / "id_map.jsonl"` 对 Smoke 错误。根据明确的评测集合类型，选择完整 `id_map.jsonl` 或 `smoke_id_map.jsonl`；显式 `--id-map` 也要验证与所选集合一致，而不是悄悄接纳全量映射。

### C. 真实数据形状的无 GPU 闭环测试

新增集成测试，不依赖本机官方 Dev 或 Qwen 权重：

1. 临时构造遵循 D0.3 契约的**人工样本与 Manifest**，分别生成全量适配文件和 Smoke 子集（测试可把 `expected_dev_count` 和 `smoke.count` 缩为小数字，但覆盖和集合选择语义必须相同）。
2. 由 Mock 生成与 Smoke ID 完全相同的 `submission.jsonl`、`raw_predictions.jsonl`、`performance_report.json`，所有输入 hash、run ID 与现有校验契约真实对应。
3. 直接调用 `score_files`/CLI，**不传 `--id-map`**，证明 Smoke 自动识别正确集合并评分通过。
4. 分别注入 Smoke 缺 1 条、混入完整 Dev 多余 ID、错 id_map、Manifest 的 Smoke ID 不一致，必须明确失败。
5. 验证完整集合仍校验它自己的精确行数，旧的 4 条 `synthetic_fixture` 验收仍通过。

**验收标准**：全量与 Smoke 两种合法集合均可评分；任何不一致均拒绝，相关测试可在 CPU 纯合成环境复现。

## 四、P1/P2：解除 Dev 输入与模型运行配置的不必要耦合

**位置**：`src/evaluation/prepare_dev.py` 与 `src/evaluation/score.py`，兼顾 `configs/evaluation/e00.yaml`。

**问题**：目前 Dev 适配 Manifest 的 `config_sha256` 直接覆盖整个 E00 YAML，而评分器要求它等于正在评分时的完整 YAML hash。这样只要 E00.2 为比较贪心解码与采样、NF4 与 BF16、BERTScore 开关而改变运行/评测配置，即使 Dev 输入和 ID 没有发生任何变化，也会被拒绝，需要重建同一份 Dev 数据。

**修订原则**：

- **数据集身份**只由原 Dev SHA/Manifest、规范化契约、ID 规则、Smoke seed/数量及适配器版本确定。保留可核验的 adapter 配置指纹；已有文件全量 SHA-256 校验不能删除。
- **模型运行身份**单独由模型权重、量化、P0/F2/T1/Tokenizer、P/G、解码设置和实际运行报告核对。
- **评分口径**单独记录 BLEU/ROUGE/BERTScore 实现与版本；评分配置改变不得伪装成同一份评分结果，仍要换新 `run_id`/`scored` 目录或拒绝冲突覆盖。
- 如果 P0/F2/T1 的内容或 Tokenizer 指纹被改变，仍需明确检查版本并阻断不兼容运行。

优先采用**最小修改**：从现有 Manifest 派生数据适配专用指纹，并将现有“全 YAML hash 必须一致”的校验改为“适配条件一致 + 真实 runtime 与当前实验运行配置一致”。不新增独立实验管理框架，不重写 Manifest 的全部结构。若升级 Manifest 版本，明确版本变化并重新构建 E00.1 适配文件，不能暗中复用旧格式。

**回归用例**：固定 Dev/Smoke 文件，改变 `generation.do_sample`（模型运行报告同步改变）、量化候选或 BERTScore 开关后，评测器不会因**数据适配 hash**阻断；如运行报告仍使用旧配置，必须由**运行兼容性校验**阻断。真正改变 Smoke 选择 seed/count 必须拒绝与旧适配文件混用。

## 五、P2：多数类基线与权重身份记录

### A. 多数类基线缺失时，不得用 0 冒充测量

**位置**：`src/evaluation/score.py::_load_train_majority` 及其调用点。

- 若 D0.3 Train 缺失：`status=not_run`，`emotion_label=null`，`accuracy=null`，明确原因。
- 若 Train 的 SHA 不匹配：继续报错，不允许用错误数据计算。
- 若存在且验证通过：依据 **Train** 统计多数类，使用 Dev 真值评价其 Accuracy；不能从 Dev 决定多数类标签。
- 新增“缺失文件 / 正常存在 / hash 错误”三个分支的测试。

### B. 不能把“声明 revision”当成“核验了模型权重”

**位置**：`participant/run_inference.py::_weight_identity`，及评测报告的模型身份检查。

- 当前配置填写 `model_revision` 后只回报该声明，未核验实际文件；状态 `revision_configured_file_hashes_not_computed` 应保持表示**未做哈希核验**的语义，不能算作 verified。
- 若读取模型文件摘要，优先对最终实际加载目录内的 safetensors（包括 HF snapshot symlink 指向的内容）逐文件做 SHA-256，留下聚合摘要；模型加载前的核验耗时应排除在逐样本推理延迟外。
- `model_revision` 可记录 HF snapshot 的 commit ID，但**不能仅凭本地目录名或配置字符串**就认定权重与对应提交一致。记录 `configured_revision` 和 `observed_weight_hash` 两种事实，必要时将无法确认官方 revision 的情况标成 `unverified_revision`。
- 实际 E00/E01 比较时要核对基础模型指纹（对 E01 另记录 Adapter 身份）；评测器区分 `not_run/mock` 与 `verified`，不能把 Mock 身份要求套到合成 fixture 上。
- E00.1 只做静态/临时小文件单测，不要求读取 GB 级真实权重，也不宣称已经加载 NF4。

注意不要在 E00.1 为此引入无必要的复杂模型登记系统。

## 六、缓存模型的使用规则与进入 E00.2 的边界

### 2. 在 README / workflow 中给出简短检查步骤

```bash
cd ~/projects/EmotionalCompany
source .venv/bin/activate

ls -ld participant/model 2>/dev/null || true
ls -lah ~/.cache/huggingface/hub/models--Qwen--Qwen3-1.7B/snapshots/ 2>/dev/null || true
find ~/.cache/huggingface/hub/models--Qwen--Qwen3-1.7B \
  -name '*.safetensors' -o -name config.json 2>/dev/null
```

若发现包含 `config.json` 与完整分片权重的本地 snapshot：

```bash
# 仅示意；实际目录由上面的 ls 结果确定，不要猜路径
export EVALUATION_MODEL_PATH='/真实存在的/.../models--Qwen--Qwen3-1.7B/snapshots/<revision>'

# 当权重 snapshot 附带的 Tokenizer 与 D0.4.2 锁定指纹不同，
```
