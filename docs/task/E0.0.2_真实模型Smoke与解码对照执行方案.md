## 三、最小工程改动任务

### A. 为实验提供独立运行配置（必要）

目前推理脚本只读取固定 `participant/configs/inference_config.json`；两组解码若反复编辑该文件，容易发生设置漂移和污染比赛默认配置。

实现**一个最小的配置覆盖入口**，例如新增环境变量 `EVALUATION_INFERENCE_CONFIG` 指向 JSON 文件：

- 默认未设置时与当前 `CONFIG_PATH` 行为**字节语义一致**，官方 `start.sh TEST_FILE RESULT_DIR` 不需要任何改动。
- 显式设置时读取指定存在的 JSON 文件，再沿用现有 `load_config()` 校验、模型加载、Prompt/Tokenizer 指纹等所有公共代码；不允许额外一套 generate 或 schema 处理实现。
- 为本阶段设置一份受版本控制的**实验配置档案**，包括 Greedy 与 Sampling 的差异、共同模型与协议条件、采样基准种子（如 `42`）。Codex 可选择：用小型脚本从当前官方运行 JSON + 两个 profile 合成两份完整 effective runner JSON，存入 `outputs/evaluation/e00_2/<run-id>/...`；不要把巨大且重复的 P0/Tokenizer 锁定字段复制出多份需要同步维护的正式源码配置。
- 每个运行同时生成供 `score.py --config` 使用的**独立完整评测 YAML 快照**，保持 `scoring` / `data` / `protocol` 内容与现有 `e00.yaml` 一致，只调整 `generation` 等该组必要参数；其 `generation` 键值需严格匹配 runtime `generation_config`，不可事后靠手动改文件骗过校验。
- 实验元数据记录 runner/evaluation 两份 effective 配置的内容 SHA-256、experiment/run ID、配置来源文件以及实际环境覆盖字段（不能记 API Key）。若复用的 `score.py` 已能提取其中部分信息，不重复封装。
- `EVALUATION_INFERENCE_CONFIG` 应仅用于本地研究；不要修改官方固定入口的含义。

**避免过度实现**：优先一个简短的 profile/config 构建入口（脚本可在 `scripts/`），而不是引入 Hydra、数据库、任务调度器或通用配置中心。

### B. 采样种子与可复现性（必要）

- Sampling 明确记录 `base_seed`、每条 `id` 派生的有效 seed、是否开启 `do_sample`。使用稳定的 `sha256(base_seed + ':' + id)` 派生整数，避免 Python 内置 `hash()` 的进程随机化。
- 每条生成开始前设置 PyTorch 随机种子，使抽样尽量不依赖样本排列顺序。**保留当前默认非采样行为**，不要求跨 CUDA/PyTorch/驱动版本逐 Token bitwise 完全一致。
- 若在当前 Transformers 版本中 `model.generate(generator=...)` 不能兼容，不强行传未支持的参数；允许在每条推理前采用 PyTorch RNG 显式设置种子的方式，并通过 Mock 验证。
- 除非确有必要，不增加 `raw_predictions.jsonl` 的额外字段；现有 `score.py` 对 Raw 字段有严格 allowlist。采样 seed 可放到 `performance_report.json` 的逐样本诊断 / run config 中。

### C. NF4、GPU 与显存实证（必要）

**注意：当前 `quantization_facts.applied=true` 主要来自创建了配置对象，不能单凭它证明真实量化已生效。**

在加载成功后增加必要的只读观测：

1. 记录模型身份：本地 `participant/model` 实际解析路径、revision 的配置声明、被索引引用的实际权重文件 SHA-256、聚合 hash；沿用现有 `_weight_identity`，不重新设计一套身份系统。
2. 核对实际存在的 `bitsandbytes.nn.Linear4bit` 模块数量（应 `>0`）；记录是否有 CPU/disk offload。主实验不接受未说明的 CPU/disk offload 作为正常单 GPU 基线。
3. 记录 GPU 名称，加载后 `torch.cuda.memory_allocated`、`memory_reserved`；生成前适时 reset peak 后记录单次或整轮 `max_memory_allocated` / `max_memory_reserved`，必要时记录 CUDA 设备总显存信息。清楚区分 PyTorch allocator 统计与整卡占用；不可把它们混成一个指标。
4. 明确计时：模型加载耗时与样本推理耗时独立；第一次推理是冷启动/预热特征，首 20 条 Smoke 的平均延迟仅作本地探索；不能称为官方 100 条成绩。
5. 保留目前 `synchronize()` 前后同步逻辑；不能变成 `perf_counter` 停止后才同步。
6. 真实硬件异常（OOM、NF4 不支持等）必须报告并停止；不许偷偷改成 CPU、BF16 全精度、另一模型或缩减 G 后仍将其标作同一配置。

### D. 阶段数据与结论（必要）

- **首次单样本**：仅证明权重 + Tokenizer/P0/F2/T1 + NF4 + `generate` + Raw + Submission 能连通。用 20 条 Smoke 输入复制首条到临时 JSONL **仅用于运行预检**；不要拿 1 条去喂要求 20 条的正式评分器。预检也用专属 run ID，不覆盖后续 20 条结果。
- **20 条 Greedy 和 20 条 Sampling**：同样完整的 `smoke_input.jsonl`，分别对应自己的 runtime config / evaluation config / 输出目录；真实生成的 `backend=transformers`，不得使用 `scripts/e00_mock_smoke.py` 代替。
- 评分结果记录 Emotion Accuracy/Macro-F1、画像 Micro-F1/Exact Match、BLEU/ROUGE、Raw strict JSON 合法率、A0 Schema 合法率、最终 Schema 合法率、生成结束原因、Token 长度、裁剪、耗时、峰值显存；BERTScore 没有下载好就按 E00.1 约定 `not_run`。
- 保留逐样本对照表（ID、两组状态、情绪是否正确、画像遗漏/误判、回复长度、生成停止原因、JSON 合规与错误类别），只在本地受忽略目录保存原始文本，Git 报告不复制真实对话。
- **20 条是代表性 Smoke 而非无偏评估集**。不能仅因为 1～2 条准确率高就宣称某策略更优；优先以协议稳定性、频繁长度上限、重复/损坏输出、与模型实际表现的定性证据决定 E00.3 候选。若没有充分证据，允许**明确标记尚未冻结**，不能自行扩大超参数搜索。
