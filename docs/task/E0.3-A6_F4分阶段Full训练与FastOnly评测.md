## 一、研究目标与现有证据

E03-A6 已完成两个同规模 1,024 Train / 256 Optimizer Steps 的独立格式对照：

| 固定 160 Dev 指标 | F3（短字段） | F4（完整字段名） |
|---|---:|---:|
| 情绪 Accuracy | 49.38% | **52.50%** |
| 画像 Micro-F1 | 0.0153 | **0.0300** |
| 画像 TP / FP / FN | 2 / 2 / 256 | **4 / 5 / 254** |
| 生成非空画像的样本数 | 4/160 | **6/160** |
| 严格格式解析 | 160/160 | **160/160** |

F4 在相同 ID、相同步数下有正向信号，且其 32 条完整生成 Smoke 全部通过严格解析和最终 Schema；独立 Adapter 重载也通过。但画像输出仍极其稀疏，**原 F4 Pilot 的“非空至少 16/160、TP 至少 5”质量门槛未通过**。该事实必须保留为历史结论，不能修改旧报告、回填为 `passed`。

E01-B 历史 512/128 Pilot 画像 F1 `0.007663`，最终 16,192/4,048 Full B 在完整 1,833 Dev 上达 `0.4223`。这个历史说明短程指标可能低估更长训练后的能力，但不同训练样本规模、数据顺序及模型协议不同，不能据此推断 **F4 必然会在 4,048 步收敛到同一水平**。F3 从 128 到 256 步的指标也曾下降。

本次只研究：在 **全量 16,192 条、相同 LoRA/优化器、相同 F4 协议**下，F4 随着训练步数增加，情绪与 33 标签画像的预测行为如何变化？能否摆脱近乎全空的画像输出，同时避免 FP 暴涨？

## 三、Step 定义、训练数据与公平性

### 1. 优化步数表

冻结微批大小为 1、梯度累计 `4`、`epochs=1`、16,192 条有效 SFT Train，每个 Optimizer Step 消费 4 条训练样本：

| 暂停节点 | 累计样本消费（每个一遍） | 训练进度 | 该区间新增步数 |
|---|---:|---:|---:|
| **512** | 2,048 | 12.65% Epoch | 512 |
| **1,024** | 4,096 | 25.30% Epoch | 512 |
| **2,048** | 8,192 | 50.59% Epoch | 1,024 |
| **4,048** | 16,192 | 100% Epoch | 2,000 |

**最后节点为 4,048，不能写成 4,096。** 4,096 在当前 Batch/Accumulation 配置下多消费 192 条训练样本，破坏与 E01-B Full 一 Epoch 的对照。每次执行都从同一个 Run 的训练状态继续，不创建新 Adapter，不重置 AdamW。这里只把“Optimizer Step”当作模型参数更新的计数，不能将 Micro-step 和 Optimizer Step 混用。

### 2. 全量 F4 Train 的构建和冻结

原 F4 Pilot 只确认了 1,024 条样本。训练前，必须对 D0.4.3 **同一批 16,192 个有效 Train ID**重新构建 F4 完整监督序列：

1. 读取 D0.3 `data/processed/v1/train.jsonl`、F2 `data/processed/sft/v1/train.jsonl` 及其 Manifest；检查逐 ID 一致、无重复。
2. 通过与 F2 原始 Token IDs 一致的 P0/T1 历史选择，得到 **原来的 selected_history**；F4 仅更换 Prompt/Completion，不因短 Prompt 私自保留更多历史。
3. 使用已存在的 `build_f4_training_item` 生成 F4 Prompt/Completion；逐条校验 `Emotion/Personality/Interests/Style/Response` Gold 往返无损、官方枚举顺序、`memory_refs=[]`、Prompt `labels=-100`、Completion 和 EOS 受监督。
4. 按原训练预算严格检查 `P≤1280`、`S≤2048`、right padding、`packing=false`、`padding_free=false`。**如果任一原 16,192 条超限，则记录 ID/原因并停止 Full 放行，不能静默丢样本、截断回复、增加序列预算或扩充新样本。**
5. 统计 F2/F4 在同一批 ID 上的 Prompt Token、Completion Token、总监督 Token 差异；保存完整 Manifest、样本身份、Tokenizer/Chat Template/Prompt/代码 Hash。保留 120 条 F2 历史排除样本的历史排除状态，不为了利用 F4 新空间而加入。
6. 新 F4 预编码 Train 放入独立版本目录，例如 `data/processed/sft/e03_a6_f4_full/`，绝不覆盖 F2、F3 或旧 Pilot 数据。

仍使用 **全部 Gold 回复作为训练监督**。用户本轮提出的“不生成 Response”专指**暂停节点的预测评测**。如在训练时也删掉 Response，实际研究对象就变为另一种监督方法，无法再把结果归因于“F4 完整字段名与更长训练”。

### 3. 固定训练条件

从原始 Base 权重初始化**全新 F4 LoRA**，不从 F4 256 步 Pilot Adapter 续训；严格保留 Base Revision/Hash、Tokenizer、P_A6_F4 Prompt、F4 协议、P0/T1 同一历史、Seed 42、`r=8`、`alpha=16`、`dropout=0.0`、七个 Target Modules、AdamW `lr=1e-4`、constant LR、无 Warmup、`weight_decay=0.0`、NF4/BF16、梯度检查点和 FP32 LoRA 保存/重载策略。

训练总计划 `max_steps=4048` 从 Step 0 就冻结，四个节点都是同一计划的**暂停和续训**，不可以先建 `max_steps=512` 的训练然后临时把配置改到 1,024/2,048/4,048：Trainer/Scheduler/Resume 语义应在最初就绑定最终计划。`epochs=1` 与实际 DataLoader 调度需前置核对。

**DataLoader 顺序必须可验证**：随机采样器虽保持 E01-B 的 random 策略，但训练恢复时必须确保每个样本在本 Epoch 中按同一确定性序列被消费一次。保存有序训练 ID 的 Hash、按区间的累计与新增 ID Hash，并在 CPU 合成/实际小规模演练中检查“不中断连续训练”与“保存、退出、恢复”消费序列严格一致。不要只检查总 Step，忽略重复或跳过样本。

## 四、训练执行：同一 Run 四节点暂停、审查、继续

### 1. CPU 与 GPU 预检

先完成不加载模型的全量 F4 数据核验、配置验证和 Checkpoint 机制单测。GPU 只做 **独立的 1 个 Optimizer Step Dry-run**，不写正式 Adapter、不改变正式 Run；检查模型在 CUDA、NF4/BF16、`micro_batch=1`、accumulation=4 下 Loss 有限、LoRA 梯度非零、参数确有更新、Base SHA 未变，记录显存预算和硬件身份。

新增 `training_scope=staged_full_train` 的**独立配置契约和显式 GPU Gate**；不把 A6 256 步 Pilot 的旧白名单改为允许任意步数，也不绕开 A4/仓库权限检查。目标是可重现的正式训练，而非手动拼装 Torch 脚本。

### 2. 暂停与恢复的必需状态

每个节点均需先写出可恢复的、完整的 Trainer Checkpoint：

- LoRA Model/PEFT 权重与配置；
- AdamW Optimizer 的动量、Step、参数映射；
- Scheduler 状态（即便是 constant 也记录）；
- PyTorch/CUDA/Python/NumPy 等 RNG 状态及采样器/数据次序恢复信息；
- `TrainerState`、`global_step`、已消费 Micro-batch/ID 的一致性记录；
- 配置与代码、训练数据、Prompt、Tokenizer、Base、阶段号及文件 SHA。

Checkpoint 必须能独立通过身份验证。明确区分 **可推理的 Adapter 导出**与**可恢复的训练 Checkpoint**：只有前者不能当作同一 Run 恢复依据。

暂停时：**先确认 checkpoint 完成且持久化，再退出训练、释放 GPU、加载对应 Adapter 开展只读 Fast-only 评测。** 评测不得更新模型或改变训练 RNG；报告写完后停在 `awaiting_manual_review`。下一阶段需检查相同 Run 的上一节点 `review/approval` 记录与 Checkpoint Hash，再恢复；没有放行则拒绝继续。

对于 4,048 最终点，须确保训练结束后也明确保存最终 Checkpoint。原 Pilot 的 `save_total_limit=2` 会使老 Checkpoint 被轮转删除，**新运行应明确固定保留四个里程碑的恢复 Checkpoint**；如需清理临时 Checkpoint，先验证并保留里程碑完整性，不能覆盖已评测的节点，也不能为了省磁盘删除唯一可恢复状态。若磁盘不足，先报告并暂停。

### 3. 中断与失败处理

- 同一节点训练意外中断：读取本 Run 实际存在、已验证的最近 Checkpoint；重新核验参数、数据顺序与历史身份后恢复。Checkpoint 之后丢失的更新不能被错误计数。
- 同一 Run 不允许把已经完成的节点从头再跑，不能迁移另一实验的 Optimizer 状态。
- 不允许为了恢复成功静默修改 Batch、Accumulation、Seed、Sampler、LoRA dtype 或 Train Cohort。
- 检查 `model.train()` 与 `model.eval()` 边界，训练中的 Dropout 配置保持一致；评测用独立加载，不能改变训练实例。
- 检测到权重损坏、参数身份错误、样本漏用/重复、Checkpoint 不一致、NaN/OOM、Base 改变或重要日志缺口时进入 `blocked`，不自动进入下一节点。
- Full 训练已开展但中途 Stop 的 Run 应能保留并读取中间结果，不把它改写成 Full `passed`。

## 五、阶段评测：只生成情绪和画像，不生成 Response

### 1. F4 Fast-only 的真实终止边界

F4 原始输出格式保持不变：

```text
Emotion=<合法情绪>
Personality=<标签或->
Interests=<标签或->
Style=<标签或->
Response=<完整回复>   # 仅训练与最终正式推理使用
```

**阶段评测**使用已有 `F4FastPrefixStopper`，Greedy 生成直到完整遇到 `\nResponse=`，在这个边界**立刻停止，不生成任何回复正文**。把 `Response=` 仅当作前缀终止标记，不统计回复质量、BLEU、ROUGE、EOS 率或最终完整输出合法率。四个预测字段全部严格解析后才允许评分；遇到 Token 上限、停止边界未出现、字段非法时按照固定分母计为失败，记录错误类型，不从完成的子集里剔除。

注意，严格的 `parse_f4()` 要求第五行 `Response=` 存在，因此简单地只解码前四行会产生 `incomplete`；不得临时放宽官方 Runner 的 F4 解析要求。快评沿用已验证的**“完整 Response 标记已输出，正文为零”**的前缀逻辑。`fast_max_new_tokens` 需要根据已观察的 F4 Pilot 长度保证不会频繁截断，预先冻结并记录，不能在某节点因为分数差临时上调后直接混比。

### 2. 固定评测 Cohort 与结果可比性

建议直接使用两套已冻结的 **Dev 无标签输入**：

- **160 个 Pilot Fast ID**：来自历史 E01-B Pilot 同一 Cohort，已有 F3/F4 256 步结果；每个节点都对这 160 条评分，用来画完整训练轨迹。
- **224 个 E03 Fast-only ID**：已用于 A3/A4 的开发代理评测。若当前 F4 评测器可准确复用相同输入和 T1 历史，则每个节点也评测这 224 条，便于与 E01-B Full 的 224 点冻结基线比较；必须使用相同 ID 集、References 和**一致的 Raw/标准化评分口径**。

两套集合可能重叠，**不能预设它们相互独立或直接将 F1 均值相加**。建议先核验两个 ID 集、会话 ID、来源 Hash、交集规模和同一输入的 Hash。可在每个节点评测二者的去重并集以减少重复生成，再按两个冻结 Cohort 各自独立计算指标和分母，保证同一条模型输出不因重复 ID 被算两次。

为防止 Gold 泄漏，生成阶段只读取无标签输入和 ID Map，完成并冻结预测文件 Hash 后再读取 Gold References 打分。固定 Seed 42、`do_sample=false`、Tokenizer、Max Prompt、F4 Prompt、T1 视图、生成边界与后处理口径；相同的 Cohort 在四个节点不能变更。Stage 间比较时分清 Full B F2 基线、F3 Pilot 和 F4 Pilot 的模型与阶段差异。

### 3. 每个节点输出的质量指标

至少包含：

| 分类 | 必须报告 |
|---|---|
| 运行身份 | Run ID、Global Step、Checkpoint SHA、Adapter SHA、模型/Tokenizer/数据/代码版本及实际评测样本数 |
| 协议 | Fast prefix 成功率、严格 F4 字段解析率、非法标签率、边界缺失/截断数、原始前缀长度 |
| 情绪 | Accuracy、Macro-F1、各类预测分布、最大单类占比、相同 ID 相比上一节点的正确/错误迁移 |
| 画像总体 | 33 标签 TP/FP/FN、Micro-Precision/Recall/F1、Macro-F1、三维 Exact、Gold 非空时的 Recall |
| 画像分维度 | Personality / Interests / Style 的 TP/FP/FN、Micro-F1、预测非空量；重点记录 Style 是否仍为全空 |
| 预测稀疏度 | 非空画像样本数、全空预测率、每样本预测标签数、真正发生的 TP/FP 增量 |
| 可比性 | 同 ID 的上一节点变化、固定 160/224 分母、会话簇 Bootstrap（可选）、历史 F4 256 步/Full B 基线的明确差异 |
| 资源 | Fast 生成 Token 总数、模型加载和生成时间、VRAM；**不伪称端到端官方延迟** |
| 训练 | 累计优化步、实际训练样本和监督 Token、SFT Dev Loss（若已有固定且独立的无训练 Dev 口径）、Checkpoint 恢复完整性 |

不能仅依据 Exact Match 提升判断画像进步：若全空预测增多，Exact 可能虚高。不能仅看 TP 或 Recall 增长：需同时核对 FP 与 Precision。可使用相同会话簇做配对区间评估，但样本复用较多，区间只能作为探索性证据。

### 4. 节点审阅与停止规则

在 Step 0 前冻结**同一套**用于全部节点的核心指标计算、生成预算、解析失败政策及质量报告结构；新节点的结果出来后不得更改 Gold/解析器或重新选样以追求更高分数。

本次采用“**硬工程安全门 + 趋势判读 + 人工放行**”而非把 256 步 Pilot 的旧 `16/160` 非空阈值直接套到所有节点：

- **硬工程门**：Run/Checkpoint 身份正确、数据消费连续、独立重载通过、Fast 评测固定 ID 全覆盖且解析/非法错误在预先冻结的合理范围、无异常参数或资源问题。建议严格 F4 前缀解析率至少 `98%`，但正式阈值应在 Step 0 前冻结，并对每个解析失败逐条记录。
- **Step 512**：重点判断输出是否仍可稳定解析、情绪是否明显崩溃、已有非空画像/TP 是否保留；画像仍稀疏时记 `inconclusive`，不把“未达到 Full B”当作直接否决原因。**报告后暂停，请用户决定是否允许走到 1,024。**
- **Step 1,024**：同时比较 Step 256、512、1,024 的相同 160 ID 轨迹及 224 固定集；如果始终无可解释的 TP/非空改善，或者 FP 无法控制，需明确列出继续的风险。**报告后暂停，请用户决定是否允许走到 2,048。**
- **Step 2,048**：这是核心止损点。如果仍接近全空，或画像 Micro-F1 明显落后于同 ID 的 Full B 且没有改善趋势，应建议终止而不是自动花完剩余 2,000 步。若 TP/Recall 改善且 Precision 与 FP 可接受，说明继续到终点更有意义。**报告后暂停，请用户决定是否走到 4,048。**
- **Step 4,048**：记录本次一 Epoch 最终准确率与学习轨迹、保存权重和可复现报告，状态为 `full_training_completed_awaiting_final_review`；**仅凭 Fast-only 不批准模型替换基线**。

用户可根据结果在中途决定继续或停止，但每次批准需记录节点、相应 Checkpoint Hash、理由与授权来源；**不可由于程序认为 F1 变好而自行继续下一阶段**。没有人工判断时状态写 `awaiting_manual_review`，评测结果始终可用。

## 六、实施步骤与阶段性交付

### 阶段 A：准备与回归（CPU）

执行人：创建新分支 → 审阅现有 F4 Pilot → 新建 Full 配置合同 → 全量 16,192 F4 重编码 → 解析与标签/Prompt/Mask/Token 守恒 → Run 身份 → Checkpoint 机制与采样顺序的合成测试 → 修复 CI 阻断项 → 提交 CPU 验收记录。

**当前 HEAD 的 CI 注意项**：GitHub Actions [run 42156756198](https://github.com/LIZZYGREAT/EmotionCompany/actions/runs/42156756198) 的 `Check syntax and pushed diff whitespace` 步骤因 `fatal: bad object 1792b093...` 失败，后续单测被跳过。该现象与 Git 历史基准对象不可达有关，尚不能认定 F4 代码测试失败。必要时仅对 `.github/workflows/ci.yml` 的 push 差异基准做安全回退：先检测 `github.event.before` 是否可读取，不可读取时使用可验证的当前基准/merge-base，必须真的执行 `git diff --check`，不能用 `|| true` 忽略错误。确保新的 HEAD 得到真实通过的 CI，且把新增 F4 Full CPU 合成测试加入 CI 覆盖。

完成前**不得启动 512 步**，CPU 产物需能核验 Train 全量身份、评测 ID 和计划步数。

### 阶段 B：独立 GPU Dry-step / Resume Smoke

在有限 GPU 预算内完成 1 Step Dry-run，并额外做小规模合成或真实小型训练 Run 的**暂停 → 完整 Checkpoint 保存 → 释放模型 → 恢复**一致性验证。训练接续前后 Token 消费顺序、Global Step、模型权重及 Optimizer 状态应与未中断参考路径在合理数值容差内一致；如因 CUDA 非确定性不能严格逐 Token 一致，需记录可重现的范围及差异，至少保证不漏/重复样本。

这是 Full 前置工程门禁，不将该小规模验证样本记入正式 Full 的训练进度。

### 阶段 C：正式同 Run 逐节点评测

按 **512 → 1,024 → 2,048 → 4,048** 运行，每到节点：

1. 保存完整训练 Checkpoint，校验训练数据与状态，发布节点身份与 SHA；
2. 执行固定 160 和 224 的 F4 Fast-only（去重生成、分别评分）；**不生成 Response 正文**；
3. 生成本节点聚合表、前后变化、错误分布、节省的生成 Token、风险判断；
4. 输出 `passed / inconclusive / failed / blocked` 与下一阶段建议，标记 `awaiting_manual_review`；
5. 停止。只有用户明确批准才从这个节点恢复继续，而不是重新初始化训练。

建议第一节点至少使用 `E03-A6-F4-STAGED-FULL-<date>` 形式的唯一 Run ID；所有后续阶段复用同一个 ID。不同节点的模型快照、生成结果与报告使用单独的 `step-0512/`、`step-1024/`、`step-2048/`、`step-4048/` 路径，拒绝覆盖已有文件。

### 阶段 D：归档与研究结论

最终交付 `docs/experiments/E0.3-A6_F4分阶段Full训练观察报告.md`，以及本地忽略目录中的完整训练状态、逐节点评测 JSON 和模型快照。报告只需覆盖 **本轮 Train Full 与 Dev Fast-only** 的进展和结果；不设计 Train+Dev 重训、不跑官方 Val、不对外发布模型。

每个节点应先产生一个**独立、可审阅的中间小结**，不要等到 4,048 才一次性汇报全部结果。只有最后节点真实完成才在报告中写 Full 完成；中止时保留实际已完成节点及原因。

## 八、验收决策与最终交接

**交付前应提供三个独立判断**：

1. **工程状态**：`passed / blocked / failed`；包括全量数据身份、Sample/EOS/Mask、同 Run Checkpoint Resume、重载、CI 等真实证据。
2. **节点质量状态**：对每个实际完成的 Step 独立报告 `passed / inconclusive / failed`，展示同 ID 的 TP/FP/FN、Micro-F1、Recall、Precision、非空数和情绪准确率。报告任何读不到的资产或未完成评测，不能填假数值。
3. **推进授权状态**：每个节点后 `awaiting_manual_review`；用户不放行则不继续，用户放行也不自动批准替换基线。

当前最重要的成功标准不是形式上跑完 4,048 步，而是能够可靠回答：**F4 在哪个训练进度开始有实际非空画像的 TP 增长？这种增长是否伴随可接受的 FP？是否出现峰值与退化？** 若 2,048 时仍几乎只输出空画像，这本身就是有价值的负面结果，可以及时停止。

**范围再次锁定：本次只执行 F4 全量 Train 的分阶段研究和 Dev Fast-only 准确率观察。Train+Dev 联合重训与 Val 测试均属于未来另行授权任务，本文件不展开、不预先安排。**
