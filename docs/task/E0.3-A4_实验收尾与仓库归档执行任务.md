## 一、任务背景与已确立结论

本轮 A4 包含两个阶段：

- **A4-1 评测口径对齐已完成。** 同一冻结开发代理集（224 个 ID / 101 个完整会话）上，E01-B 历史 Submission（S）画像 Micro-F1 为 `0.422323`，历史 Raw 的完整画像前缀（R）为 `0.425787`，新 Fast-only（F）为 `0.425787`。R 与 F 的画像、情绪均按 ID **224/224 一致**。S 与 R 的唯一画像差异来自 `test_000157_t0`：模型画像前缀已完整，但后续完整 JSON 无效，历史 Submission 发生回退。不得将两种口径的差异描述成模型能力提升。
- **A4-2 实际运行已完成。** 从只读 E01-B Full Adapter 出发，`AdamW / LR=2e-5 / 64 optimizer steps / 4 microbatches per step`，训练恰好消耗 256 条 Train 样本；模型保存、权重身份和 BF16 重载核验通过。冻结 224 点 Fast-only 画像 Micro-F1 从 `0.425787` 到 `0.434548`，TP `142→161`、FP `152→207`、FN `231→212`；Precision `0.482993→0.437500`，Recall `0.380697→0.431635`。按事先冻结的门槛，FP 相对增加 `36.18%`、Precision 下降 `0.045493`，结论为 **`stability_failed`（训练技术执行完成，候选质量未通过）**。
- **原 E01-B Full 仍是应保留的基线。** A4 Adapter 不应被标记为正式候选、部署版本或默认推理权重。
- 历史未执行项目保持 `not_run`：A4 候选的完整 JSON/回复 Smoke、完整 1,833 点 Dev 新生成与官方 Val；不补跑。

本任务只做实验收尾，不修改研究结论、阈值、原始评分或历史 Run 身份。

## 四、P1：A4 评分 CLI 明确区分“报告已生成”和“质量已通过”

### 现状与风险

`scripts/e03_a4_stability_evaluate.py` 的 `compare` 已返回包含 `status=stability_failed` 的诊断结果，但 `main()` 当前把 `stability_failed` 与 `stability_preliminarily_passed` 都视为正常退出码 `0`。这对人工生成报告是可理解的，但脚本化验收时，可能把“质量失败”当成“可以采用”。

### 要求

1. 保留原 `compare` 默认行为（成功写出完整诊断报告即可按旧约定退出），不破坏已有调用者与不可变 Run。
2. 增加明确可选的**严格质量门禁**，例如 `--require-quality-passed`：
   - `compare` 完成且 `stability_preliminarily_passed` → 退出 `0`；
   - `compare` 完成但 `stability_failed` → 非零退出；
   - 预检、身份、数据或评分失败 → 非零退出；
   - `prepare` 不应因为新增质量开关而触发训练、生成或自动比较。对于该开关在 `prepare` 模式中的行为，明确拒绝或明确忽略并在帮助文本中说明，优先拒绝以避免歧义。
3. 控制台 JSON 同时保留**原始计算结果**、`status`、`threshold_failures` 和报告路径。不要将 `stability_failed` 伪装成 `error` 或改写历史判定。
4. 添加合成测试，用模拟的比较结果覆盖门禁通过、门禁失败、默认兼容、异常失败。测试不得读本地真实模型/Run。
5. 在 `docs/workflow.md` 的 A4 相关说明中简要写明：默认退出码 `0` 表示报告生成成功；严格模式退出码 `0` 才表示质量门槛通过。**不加入运行新实验的操作指令。**
