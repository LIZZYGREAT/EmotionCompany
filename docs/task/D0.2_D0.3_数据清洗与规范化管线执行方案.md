## 二、D0.2：正式确定清洗政策

### 2.1 处理原则和动作定义

所有原始数据均只读；“处理”指对派生训练/评测记录采取动作，不直接修改 JSONL 源文件。

- `KEEP`：保留原始合法监督，不改变文本或标签。
- `QUARANTINE`：隔离**具体预测点**，不因此删除同一对话其他合法预测点；记明原因及位置。
- `DEDUPLICATE`：训练集内完全相同的监督预测点只保留一个代表；其余记录为重复副本，不能直接丢失来源映射。
- `NO_SAMPLE`：合法但 `prediction_points=[]` 的对话不产生 SFT 记录，仅纳入数据账本。
- `REVIEW`：记录供抽检的候选问题；没有明确证据时默认不改动。

### 2.2 具体处置矩阵

| D0.1 情况 | D0.2 处置 | 约束与说明 |
|---|---|---|
| 目标用户轮次、回复轮次无效；回复位于目标轮次之前或同位置 | `QUARANTINE` 错误预测点 | 当前已报告 4 个 `RESPONSE_NOT_AFTER_TARGET`。不自动重新定位回复，不重排 Turns，不删除整段对话。 |
| 目标引用不唯一、非法角色、关键监督缺失等确定性错误（若未来出现） | `QUARANTINE` 或阻断运行 | 不静默容错；报告新增异常类型及其数目。 |
| 训练集合法历史与完整 `target` 均完全相同 | `DEDUPLICATE` | 指纹包括历史消息 `role/content` 及**完整目标字段**；采用稳定的第一条来源为代表。不同回复或不同标注不当成同一条训练样本。 |
| 完整对话 `turns` 重复 | `REVIEW`＋分组约束 | 与预测点去重是两个不同概念；同内容对话不得被分到 Train、Dev 两侧。 |
| 同一历史对应不同情绪或画像 | `REVIEW` / 阻止无依据自动去重 | 本次 D0.1 未发现此类冲突；一旦发现须单独列明，不能任意保留一个标签。 |
| Train / Val 重复 | 审计并阻止训练泄漏 | 不改官方 Val；若发现新增重合，报告并停止自动处理。 |
| 短回复（Train 48、Val 4） | 默认 `KEEP`＋抽样人工复核 | `<5` 字仅是候选阈值，不是错误判定。 |
| 空预测点对话（Train 5） | `NO_SAMPLE` | 不生成训练目标，原始记录保留。 |
| 空画像数组、类别严重不均衡、稀少标签 | `KEEP` | 不填补空画像、不删除少数类、不做重采样或自动改标签。 |
| 非空 `memory_refs` | `KEEP` | 在 D0.3 中保留原始监督；A0 推理时是否固定输出 `[]` 是后续模型目标设计，不是清洗。 |
| 回复表达重复、标点、语气词、Emoji、换行等 | `KEEP` | 不做自动语义去重、改写或归一化文本。 |

本阶段 **不实施**：LLM 自动纠标、同义句合并、情绪类别均衡采样、画像负标签补全、参考回复重写、去除标点/Emoji、按字符数过滤长样本。

### 2.3 D0.2 的检查与阶段门禁

正式写清洗逻辑前，Codex 必须：

1. 根据 D0.1 的来源定位，逐一读取 **4 个时序错误预测点**，确认 `turns` 数组位置与报告一致；展示结构化定位及结论，避免在提交文档中复制敏感对话正文。
2. 聚合 202 个重复完整对话相关记录与 508 个预测点重复相关记录，说明**重复组数、各组规模、是否相互重叠**；抽查代表组，确认确实是完整监督重复，而不是“相同历史但不同回复”。
3. 抽查部分极短回复（保留原始文本，不自动删除），确认短文本候选没有系统性的解析错误；如果发现新问题，另列待决事项。
4. 固化 `docs/data/D0.2_数据处理政策.md`，明确每项政策、审计依据、预期动作，以及后续的准确计数由 D0.3 生成。

**门禁**：若发现与 D0.1 结论冲突、需要猜测性修复、或无法解释的同输入冲突监督，停止对应数据的自动处理，单独提出待决问题；其余确定性部分可以继续。

## 三、D0.3：规范化与划分管线

### 3.1 设计边界

D0.3 的核心输出是**模型无关的规范化预测点数据**，而不是 Qwen 的训练 Token。数据流程：

```text
官方 Train / Val（只读）
  │
  ├── 解析 JSONL、按官方 Schema 校验、定位 turn_id
  │
  ├── 按 turns 数组位置截取合法历史（包含当前目标 User）
  │
  ├── 执行 D0.2：隔离时序错误 → Train 精确监督去重
  │
  ├── 从 Train 建立对话关联组 → 确定性 Train / Dev 划分
  │
  ├── 生成 train / dev / val 规范化 JSONL
  │
  └── 输出守恒账本、来源映射、处理日志、划分清单和报告
```

禁止在此阶段完成：Qwen Chat Template、截断历史、限制 1024/2048/4096 Token、加入系统 Prompt、转换 Completion 为模型 Token、生成 `labels=-100`。这些留给 D0.4。`prepare.py` 不应依赖 `transformers` 或 GPU。

### 3.2 单条规范化样本协议

**格式示例（非真实数据）**：

```json
{
  "sample_id": "train:train_conv_000123:pp0",
  "conversation_id": "train_conv_000123",
  "source": {
    "split": "train",
    "source_line": 124,
    "prediction_point_index": 0,
    "target_user_turn_id": 5,
    "assistant_response_turn_id": 6,
    "target_turn_index": 4,
    "response_turn_index": 5
  },
  "history": [
    {"role": "user", "content": "最近学习压力很大。"},
    {"role": "assistant", "content": "最近发生了什么？"},
    {"role": "user", "content": "总觉得没有什么进步。"}
  ],
  "target": {
    "emotion_label": "anxiety",
    "user_profile": {
      "personality_traits": [],
      "interests": [],
      "style": []
    },
    "response_text": "听起来你最近一直在为学习结果感到焦虑。",
    "memory_refs": ["mem_000001"]
  }
}
```

规范要求：

- 一个**有效预测点**形成一条记录；`sample_id` 使用来源 Split、Conversation ID、预测点数组索引构造，必须唯一且稳定。不得把内部 `sample_id` 与正式提交要求的 `test_...` ID 混淆。
- 取 `target_user_turn_id` 在 `turns` 中的**唯一位置** `target_turn_index`。合法历史是 `turns[:target_turn_index+1]`；不依赖 `turn_id` 数值递增。
- `history` 仅保留每条消息的 `role`、`content`，保持原始数组顺序和 Unicode 文本**逐字不变**；最后一条必须是目标 User。
- `target` 保留官方原始情绪、画像、回复及 `memory_refs`，不得把空画像改成缺失值，也不得将原始记忆引用改成 `[]`。
- `source_line` 从 1 开始，`prediction_point_index` 和 Turn Index 从 0 开始；保留原始引用 ID。
- 不把正确助手回复或预测点后续 Turn 提前混入 `history`；不把 `target` 作为 Prompt 内容。
- Val 仅做同等的**合法性与规范化**转换；Val 的监督标签保持不变，不参与去重、重采样或清洗规则拟合。

### 3.3 Train 处理与准确计数

采用固定次序：**先结构校验和错误隔离，再训练集精确监督去重，再分组划分**。

1. 对每个预测点进行确定性合法性检查，错误点加入隔离日志；其余点进入候选池。
2. 针对 Train 候选点，用 `canonical JSON(history 的 role/content + 完整 target)` 生成 SHA-256。仅当指纹相同且规范化对象相同，才作为重复监督。
3. 同一重复组保留**源文件行号最小、预测点索引最小**的代表样本；其余点记录为 `duplicate_of: <sample_id>`。保留源映射，不修改代表文本。
4. 完全重复的合法历史但不同目标，**不合并监督**；另检查是否属于冲突标注或合理不同回复。
5. 后续报告分开统计错误隔离、重复移除、合法空预测点与最终生成样本，不重复计数。

以 `N_train_raw_points=18657` 为基准建立严格守恒关系：

\[
N_{\mathrm{raw}}=N_{\mathrm{quarantined}}+N_{\mathrm{deduplicated}}+N_{\mathrm{train}}+N_{\mathrm{dev}}
\]

这里每个原始预测点**恰好**对应四种结局之一。不要先认定 `N_deduplicated=508`；因为错误点与重复 Issue 可能重叠，必须按实际处理次序得出真实值。

Val 本轮预计保留 2354 个点；如果出现与 D0.1 不符的确定错误，直接失败并报告，不静默删除官方验证样本。

### 3.4 Train / Dev 分组与划分

**目标**：在官方 Train 内预留约 10% **Conversation 级** Dev，保证重叠内容不会跨 Train / Dev；官方 Val 永远独立。

**分组规则**：

- 基础单位是原始 Conversation；同一对话中的所有有效预测点必须进入同一 Split。
- 完整 `turns` 的 `role/content` 序列完全相同的对话必须归为同一组，即便 `turn_id` 或 `conversation_id` 不同。
- 不同对话若含有完全相同的合法历史输入，也需要检查是否在 Train / Dev 之间构成同输入泄漏；默认把这些对话并入同一个关联组。这些关联关系可用指纹索引和简单的并查集/等价组实现，不要写复杂的通用图框架。
- 不使用单纯的消息关键词相似性、模糊语义重复来强行合并组。
- 若短而通用的历史造成异常巨大的关联组，使划分无法兼顾约 10% Dev，先报告最大组规模和问题，**不得悄悄降低防泄漏约束**；可单独讨论短模板例外。

**划分规则**：

1. 使用固定 `split.seed`、按稳定键排序的组列表，不依赖 Python 随机化 `hash()` 或系统文件遍历顺序。
2. 以 **Conversation 组** 为单位近似选取 10% Dev；统计 Conversation 占比和有效预测点占比。
3. 尽量维持主要情绪的 Train/Dev 分布，但不追求完全相同；`surprise` 等稀有类至少要报告 Train 和 Dev 的数量，不能为了分层而拆开关联组。
4. 划分成功后固定输出完整的 `split_manifest.json`：包括 seed、组定义/指纹、Conversation → Split 映射、各组规模、Train/Dev 标签分布及版本指纹。
5. **同一对话不得跨 Split；相同完整对话及相同合法历史不得在 Train/Dev 两侧出现。** 如无法满足，构建失败，不输出貌似成功的成品。
6. 每条最终记录有 `source.split="train"`（表示来自官方 Train）；实际属于 Train 还是 Dev 由输出文件及 `split_manifest.json` 表明，不要覆写来源字段。

> 后续为了获得最终参赛模型，是否把 Dev 重新纳入训练应另开实验版本，不得改变 E00/E01 的冻结划分。

### 3.5 官方 Val 的处理边界

- 官方 Val `900` 段对话、`2354` 预测点全部按同一规范化 Schema 导出，并保留合法历史及真实监督。
- 官方 Val 不参与训练集清洗规则、去重阈值和 Train/Dev 分组算法选择；本轮所有处理政策事先固定。
- 不用 Val 的标签调节 Dev 划分；允许在最终报告中**只读统计** Val 标签分布和合法性。
- 后续 E00/E01 可以使用规范化 Val 做阶段性评测，但不在 D0.3 生成模型预测。

### 4.2 YAML 参数示例

建立 `configs/data_pipeline.yaml`（最终字段名可微调，但语义必须清晰、一致且测试覆盖）：

```yaml
inputs:
  train: data/train/train_public.jsonl
  val: data/val/val_public.jsonl

output:
  processed_dir: data/processed/v1
  artifacts_dir: outputs/data_pipeline/v1
  report: docs/data/D0.3_数据构建报告.md

policy:
  version: D0.2-v1
  invalid_prediction_point: quarantine
  exact_duplicate_training_point: keep_first
  short_response: keep_and_report
  empty_profile: keep
  empty_prediction_points: no_sample
  preserve_memory_refs: true

split:
  dev_ratio: 0.10
  seed: 42
  group_by_full_conversation: true
  group_by_exact_legal_history: true

validation:
  strict_official_schema: true
  fail_on_unexpected_val_error: true
  assert_raw_file_unchanged: true
```

- 所有资源路径相对仓库根目录；CLI 可从任意工作目录正确解析。
- 对输入、输出目录、配置结构实施最小必要校验；原始目录决不能被作为输出目标。
- 参数值不可在 `prepare.py` 中另行写死一份；如需默认值，应在 YAML 与运行记录中可见。
- 每次运行记录**实际生效配置**及其 SHA-256；首版无需实现配置继承框架。
- 输出目录允许受控重新生成，但禁止遗留旧版本 JSONL 或静默混写；对全量构建使用临时文件写入、校验成功后替换结果。

### 4.3 日志和可复现记录

`cleaning_log.jsonl` 每个被隔离/去重的预测点至少写明：

```json
{
  "sample_id": "train:train_conv_000628:pp0",
  "action": "QUARANTINE",
  "reason_code": "RESPONSE_NOT_AFTER_TARGET",
  "source_line": 628,
  "conversation_id": "train_conv_000628",
  "prediction_point_index": 0,
  "kept_as": null
}
```

`DEDUPLICATE` 记录还需要 `kept_as` 指向保留的规范化 `sample_id`；日志应具备稳定顺序。示例行号仅为结构示意，实际以 D0.1 文件的行号为准。

`manifest.json` 至少保存：

- Pipeline/Policy 版本、创建时间（时间不参与结果数据哈希）、Git Commit、工作区是否有已跟踪的修改。
- 原始 Train/Val 文件 SHA-256（执行前后）；官方 Schema 指纹。
- YAML 内容或文件 SHA-256、随机种子、划分比例、分组规则。
- 各生成 JSONL 的记录数、大小、SHA-256；清洗日志数量与分类、最终划分摘要。
