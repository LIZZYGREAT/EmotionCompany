## 一、研究问题、选择与边界

### 1. 当前已经知道什么

E01-B Full 在固定 224 点 Fast-only 上的画像基线为 Micro-F1 `0.425787`，TP/FP/FN=`142/152/231`，Precision=`0.482993`，Recall=`0.380697`，前缀情绪 Accuracy=`0.691964`。这与历史完整 Submission 的 `0.422323` 属于不同输出口径；A4 已确认差异源自完整 JSON 后段解析/回退，不能混用。在本任务的快速画像评分中使用冻结的 **E01-B Fast-only 224 点**作为统一参照。

A1/A3/A4 证明：改变完整 JSON 的 Loss、重采样或继续训练，可能增加正确标签，同时增加更多误报。A6 F4 从 Base 训练简化输出格式到 2,048 步后，Dev 224 画像 Micro-F1 `0.1029`，但 **A6 依旧在训练 Response 正文**，因此没有检验“纯分类监督”。A5 已有 33 标签目标审计、闭世界 Mask、BCE、Prompt-end 隐状态和 CPU 合成训练代码，真实 A5 GPU 阶段在所审查报告中仍是 `not_run`。

**本任务的核心因果对照是：在完全相同的初始化、输入、监督标签、训练数据顺序、优化器与步数下，增加 Emotion CE 是否提高 Profile F1？** 比较 `P` 与 `EP`，同时分别与 E01-B 的画像预测质量作实用性比较。不要把 A6 F4 的输出格式实验当成同一训练条件对照。

### 2. 冻结决策：采用真正的分类头

- 两路输入均为同一 `P0 + T1 已选用户历史 + Qwen assistant generation prefix` 的 **Prompt Token 序列**；不包含 Gold JSON、`response_text` 或答案标签文本。

## 二、数据、监督和评测口径

### 1. 源数据与样本身份

复用 A5.0 审计过的数据血缘与闭世界监督合同：

- `data/processed/v1/train.jsonl`：规范化 Train 标签来源；
- `data/processed/sft/v1/train.jsonl`：可用的 **16,192** 条 SFT Train 与确定的 `input_ids`、`prompt_length`；
- `configs/experiments/e03_a5.yaml` 与 `src/data/e03_a5_labels.py`：33 标签顺序、会话分区和监督目标；
- A5.0 冻结分区：Fit **11,304** 条 / Calibration **2,455** 条 / Internal Holdout **2,433** 条，严格按会话隔离。

源文件来源必须重新以 SHA 与 A5 Audit Manifest 核验，不能只相信摘要。分类输入直接取合法 SFT 样本的 `input_ids[:prompt_length]`，在 CPU 上验证它与同 P0/T1、同 Tokenizer 的 `encode_inference_prompt(...)` 完全一致。不能使用 `input_ids` 的 Gold Completion 后缀，也不能误取历史中 assistant 的上轮答案作为当前目标。

**训练只使用 Fit 11,304 条；Calibration 只用于阈值选择；Internal Holdout 只用于独立诊断。** 这三组均来自 Train 大分区，但会话彼此独立。固定 Dev 224 / 101 段会话仅用于各节点外部代理评分，不做梯度更新或阈值拟合。官方 Val 禁用。

### 2. 33 标签监督定义

从官方 Train Schema 确定唯一、可复现顺序：

```text
personality_traits: 10 labels
interests:           12 labels
style:               11 labels
------------------------------
Profile:             33 labels
Emotion:             16 mutually exclusive classes
```

对样本 `i`、标签 `j`，若该标签出现在 Gold 对应数组中，则 `y[i,j]=1`，否则 `0`。A5.0 已核验三维完整数组，**本任务所有 33 个标签默认 `mask=1`**，包括 Gold 全空时的 33 个负例。`0` 只表示官方 Gold 未列出，不声称真实世界中该特征不存在。只有原始来源有明确未标注证据且形成新合同，才允许 `masked_unknown`；不能借这个名字把所有负标签静默掩掉。

情绪通过官方枚举映射到 `[0,15]`，仅 EP 使用。Profile-only 训练器不创建情绪头，也不计算情绪 Loss。标签数、维度归属、顺序、正负频次与长尾支持数必须写进 Manifest。低频标签如 `style:low_emotional_expression`（A5 审计仅 3 个正例）单独报告，不能要求各类 F1 都可靠估计。

### 3. 分阶段样本调度与“4,048 步”含义

microbatch=1，gradient accumulation=4。因此 **1 个 optimizer step 消费 4 个样本曝光**，全程预冻结同一 Fit 样本调度、每轮独立可复现的随机排列：

| 累计 step | 累计样本曝光 | Fit 样本覆盖说明 |
|---:|---:|---|
| 512 | 2,048 | 第一轮 Fit 的前缀，无放回 |
| 1,024 | 4,096 | 第一轮 Fit 的前缀，无放回 |
| 2,048 | 8,192 | 第一轮 Fit 的前缀，无放回 |
| 2,826（内部 Epoch 边界） | 11,304 | 第一轮 Fit 恰好全部消费一次 |
| 4,048 | 16,192 | 第二轮又消费 4,888 次曝光；**只有 11,304 个唯一 Fit ID** |

这里保留与 A6 一致的 `512→1024→2048→4048` 节点，但**不能把 16,192 次曝光说成 16,192 个独立训练样本**。若审查更倾向完整单 Epoch，可在 Step 2,048 审阅时决定最终停在 2,826；配置中的 4,048 只代表潜在最大上限。对于已获批的 2,048→4,048 区间，在 Step 2,826 自动保存 Epoch 边界恢复 Checkpoint，但不擅自改变已冻结的采样规则。

两个训练 Arm 必须从同一个冻结 `schedule.jsonl` 读取完全相同的样本顺序、Token 长度和 4-microbatch 步分组。每次恢复记录已消费 ID 序列哈希及 Epoch 序号，不允许跑重、不允许漏样本、不允许 Resume 时重新 shuffle。

### 4. 分类评分协议

同一批 224 个 Dev 点（IDs SHA `d3c84beb6227e87c0fd09e425619635cd9fc6bac5b087e3f1010fb089f4ff8d2`），模型只做 Prompt 前向，得到 `profile_logits:[B,33]`、可选 `emotion_logits:[B,16]`。评估使用单 Prompt 前向；任何批量优化必须先证明与逐条 logits 的最大绝对差不超过 `1e-4`。禁止调用 `model.generate()`，禁止生成回复。评分前冻结每条预测最小结果及哈希，并在 Manifest 先记录 `gold_read_after_predictions_locked`，之后才读取 Gold。评分中断后，只能在校验冻结预测与 Calibration 哈希后从评分阶段恢复，不能重跑或替换预测。

画像分类头的阈值 **只能在冻结的 Train-Calibration（2,455 条）确定**。第一版本使用一个全局阈值，而非 33 个逐标签自由阈值：

- 固定阈值 `0.50`，作为可复核的原始输出口径；
- 校准阈值：使用预冻结阈值网格与规则，只看 Train-Calibration 的 Profile Micro-F1，在预先锁定的 Precision 安全约束内选择，平局时选较高阈值。若无阈值满足安全约束，明确报告 `threshold_constraint_unsatisfied`，不可按 Dev 结果重新调阈值。
- 每个节点按**同一阈值选择算法**重新使用 Calibration 计算该节点自己的阈值，但不能改阈值网格/算法/Precision 约束；同时报告 0.5 口径，区分“模型分类能力变化”和“阈值校准变化”。
- 推荐在正式 Run 开始前冻结网格 `0.05, 0.10, ..., 0.95`，Precision 约束为 **Calibration 画像 Micro-Precision ≥ 0.45**；这是工程防误报门槛，不是某种统计保证。若该约束影响可行性，应在 Start 前 CPU 方案审查修改，不允许见到 Dev 结果后改规则。

评分沿用 `src/evaluation/metrics.py::profile_metrics()` 的固定分母 TP/FP/FN 定义：全 33 标签 Micro/Macro-F1、Precision、Recall、三维独立指标、全空/非空、每样本预测标签数、长尾类支持、短长历史；EP 另用 `emotion_metrics()` 计算 16 类 Accuracy 与 Macro-F1。对同一 224 点和会话簇做配对统计：P vs EP、P vs E01-B、EP vs E01-B。**这是原始分类头结果与 E01-B 快速画像生成结果的任务质量比较，不是完全相同的推理实现或端到端输出协议比较。**

## 三、数学设计与真实训练数据流

### 1. 从 Prompt 到分类头

设样本 `i` 的 Prompt 长度为 `p_i`，Tokenizer 输出 `X_i=[x_0,...,x_{p_i-1}]`。以同一 Qwen Base 及某 Arm 的 LoRA 参数 `θ` 计算因果 Transformer 最后一层隐藏状态：

```text
Prompt IDs [B, L] + attention_mask
       ↓
Qwen3Model（NF4 Base 冻结、LoRA 可训练）
       ↓
last_hidden_state [B, L, H]
       ↓  index = prompt_length - 1
h [B, H]
       ├── ProfileHead: Linear(H,33) → z_p [B,33]
       └── EmotionHead: Linear(H,16) → z_e [B,16]  （仅 EP）
```

**关键实现：前向仅提供 Prompt Token，不拼接任何 Completion。** 因果 Mask 与 `prompt_length-1` 保证特征看不到当前 Gold。此处 `p_i-1` 是已编码 Prompt 的最后一个 Token，不能用整条完整 SFT `input_ids` 的最后 Token，也不能因右 Padding 改成 `L-1`。

优先直接调用 PEFT 模型内部经过 LoRA 注入的 `Qwen3Model` 主干前向，返回 `last_hidden_state`，绕开 LM `lm_head` 对整个词表的投影，以减少显存与计算。**必须通过模块路径/类与反向梯度合成测试证明调用后 LoRA 仍在计算图中。** 禁止通过 `detach()`、`torch.no_grad()` 或绕开 PEFT 包装导致 LoRA 不更新；如架构路径不一致，明确阻塞并做适配，不得静默退化为全词表 SFT 前向。

训练时为 LoRA 启用 Gradient Checkpointing，`use_cache=False`，输出隐藏状态通过索引进入 FP32 分类头。`model.train()` / `eval()`、LoRA dtype、量化事实与 2,048 Token 最坏情况的峰值显存必须记录。

### 2. Profile BCE

Profile 标签 `y_{ij}∈{0,1}`，Logit `z_{ij}`，Mask `m_{ij}∈{0,1}`。每个样本的标签 BCE：

$$
L_{p,i}=\frac{\sum_{j=1}^{33}m_{ij}\,\operatorname{BCEWithLogits}(z_{ij},y_{ij})}{\sum_{j=1}^{33}m_{ij}},\qquad
L_p=\frac{1}{B}\sum_{i=1}^B L_{p,i}.
$$

复用 A5 的 `masked_bce_with_logits()`，FP32 稳定运算、禁止空 Mask、NaN/Inf、负例静默丢弃。**首次主实验使用未加权 BCE，不加 `pos_weight`**；通过 Calibration 阈值与 PR 诊断判断是否出现全空预测。若后续需要类别加权，另立新版本，不改本次双 Arm 的任务差异。

### 3. EP 的情绪 CE 与多任务比例

EP 的情绪标签 `e_i` 是 16 类中的唯一整数，交叉熵：

$$
L_e=-\frac{1}{B}\sum_i \log \operatorname{softmax}(z_{e,i})_{e_i}.
$$

两组 Loss：

$$
L_{P}=L_p,\qquad
L_{EP}=L_p+\lambda_e L_e.
$$

**λ_e 在正式 Step 512 前冻结**，两组的 BCE 公式、目标、Mask、头初始化和数据顺序完全相同。初始待核验值为 `0.3`；用最长 Prompt dry-step 单独测量 `g_p`（Profile-only LoRA 梯度范数）与 `g_e`（未加权 Emotion CE 对 LoRA 的梯度范数），按 `λ_new = λ_old × target_ratio / (λ_old × g_e / g_p)` 标定，使加权情绪与画像梯度范数比接近 1.0，冻结容差为 `[0.9, 1.1]`。首次干跑实测 `g_p=2.327458`、`g_e=29.507095`，`λ=0.3` 时比例为 `3.803347`，所以正式配置在任何优化器更新前调整为 `λ_e=0.08`（估算比例 `1.013`）；同时记录 BCE `1.103897`、情绪 CE `4.012758`。必须在冻结 `0.08` 的配置下重新通过两路 GPU dry-step 和比例门禁，才能签发 Step 512 票据。不得在任何训练节点看到评分以后调权重；训练开始后的权重变更必须创建新实验版本/Run 并从头比较。

梯度累积每步 4 条 microbatch：每个 microbatch 单独计算 `L_p`（及 EP `L_e`），反向 `(L_total/4).backward()`，完成四次后 clip → AdamW step → scheduler step → 清零。优化器只包含 LoRA A/B 和当前 Arm 对应分类头。Base、LM Head、其他模块不得更新。P 中不存在情绪头；EP 中 P 头与 E 头同时可训练。需要验证 ProfileHead 与 LoRA 初始参数哈希在两 Arm 一致。

### 4. 两组的独立训练主流程（实现伪代码）

```python
# 伪代码：模型与数据调用名称按实际代码落地
shared = verify_and_freeze_sources_and_schedule()
assert shared.train_split == "fit"
assert shared.eval_ids == FROZEN_224_IDS

for arm in ("P", "EP"):
    base = load_frozen_qwen3_nf4()
    model = add_new_lora(base, init_seed=SHARED_INIT_SEED)
    profile_head = Linear(hidden_size, 33, init_seed=SHARED_PROFILE_HEAD_SEED)
    emotion_head = Linear(hidden_size, 16, init_seed=EMOTION_HEAD_SEED) if arm == "EP" else None
    optimizer = new_adamw(trainable_lora_and_heads, lr=FROZEN_LR)
    scheduler = new_constant_scheduler(optimizer)
    persist_run_identity_and_initial_hashes(arm)

    for step in range(1, 513):  # 初次仅批准至 512
        optimizer.zero_grad(set_to_none=True)
        for sample_id in shared.schedule.microbatch_ids(step):
            prompt_ids = frozen_prompt_ids(sample_id)  # NO Gold completion
            h = lora_backbone(prompt_ids).last_hidden_state[prompt_end_position]
            profile_logits = profile_head(h.float())
            loss = masked_bce(profile_logits, gold_profile_bits(sample_id))
            if arm == "EP":
                loss += frozen_lambda_e * emotion_ce(emotion_head(h.float()), gold_emotion(sample_id))
            (loss / 4).backward()
        verify_finite_gradients_and_trainable_parameter_whitelist()
        clip_grad_norm_(); optimizer.step(); scheduler.step()
        append_optimizer_ledger(step)

    save_full_resumable_checkpoint(step=512)  # LoRA, heads, optimizer, scheduler, RNG, sampler
    verify_independent_reload()
    set_run_state("awaiting_evaluation")

# 两路独立只读评测后：产出 Step 512 配对报告，awaiting_manual_review
# 用户分别批准对应 Arm 后，才允许 resume(512, 1024)；并依次 1024→2048→4048
```

注意：上面依次加载两个模型，**不要求在 8GB GPU 上同时驻留两份 Model**。完成 P 当前阶段训练后保存和释放显存，再运行 EP。Checkpoint 节点保留各自 Run 的独立训练状态，不得跨 Arm 恢复。

## 四、模型初始化与显存工程门禁

### 1. 同一 Base、独立且可比的 LoRA

冻结 Base `Qwen/Qwen3-1.7B`，NF4、BF16 compute、double quant，LoRA `r=8, alpha=16, dropout=0`，target modules `[q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj]`，seed 和初始化相同；Optimizer 建议先用 AdamW `lr=1e-4` / constant / warmup=0 / weight_decay=0 / grad_clip=1.0，**都属于 Run 前必须冻结的试验配置**，并非声称最优。A6 使用该学习率，但新分类任务 Loss 尺度不同；dry-step 只检验数值/显存和梯度，不借助 Dev 结果挑 LR。若预检发现发散/数值问题，应重新版本化配置并记录，不得同 Run 隐式改 LR。

每个 Arm 创建新 LoRA，不从 E01-B、A4、A5、A6 任何 Adapter 加载初始训练权重。LoRA 初始张量、ProfileHead 初始张量必须逐参数或规范哈希核验匹配；EP 的 EmotionHead 单独记录。Head 与训练 LoRA 使用 FP32，Base 使用 NF4 权重与 BF16 计算（LayerNorm 保持 FP32）。保存重载、校准和 Dev 评估都必须保留训练 LoRA 的 FP32 dtype；固定 Prompt reload 比较 logits，PEFT 加载时显式启用 `autocast_adapter_dtype`，不能把导出的 LoRA 静默降为 BF16。

### 2. 8GB GPU Dry-run

新增三个层次的预检：

1. **CPU**：原数据/Hash、模型配置、Prompt-only Token ID、分类目标、同 Arm 初始化、样本顺序、Checkpoint 合同和测试通过。
2. **GPU Prompt 前向**：最长真实 Prompt（不超过 P=1280），输出 `[1,H]` 及 33/16 logits，数值有限，观察显存；确认没有 LM 大词表 logits 全序列张量。
3. **GPU 最坏长度后向**：右填充到 **P=1280 的 Prompt 预算**并完成相应 BCE/CE backward，捕获 LoRA 和 Head 梯度有限且非零、Base 未变、没有 optimizer 更新。另对实际最坏 batch/梯度累积测试实际可行性。这里不必照搬 A5 完整 JSON SFT 的 S=2048 训练长度，因为本任务**只处理 Prompt**；但要证明运行代码不会越过 P=1280 的预算，并记录和 A5/A4 不同的预算定义。

OOM、梯度断开、参数错误、输入泄漏或显存超门槛时 `blocked`，不静默退化成 CPU offload、全精度 Base、截断新历史规则或缩小测试输入。P 与 EP 分别获得其自身 dry-step 通过记录。只有 Step 512 起始授权有效才允许更新模型。

## 五、可复现的分阶段训练与人工审批

### 1. 阶段状态机

每个 Arm 各自维护状态，不得将 EP 的通过自动用于 P，也不得将 P 的授权复制给 EP：

```text
prepared
  ↓ CPU/GPU preflight passed
ready_for_step_0512
  ↓ 初始授权允许仅训练至 512
training → checkpoint_0512_saved
  ↓ 只读评测 + 双 Arm 对照
awaiting_manual_review_step_0512
  ├── rejected/stopped → archived
  └── 用户批准 continuation[512→1024]
         ↓ 真正从 checkpoint-512 恢复
checkpoint_1024_saved → evaluate → awaiting_manual_review_step_1024
         ↓ 用户批准 continuation[1024→2048]
checkpoint_2048_saved → evaluate → awaiting_manual_review_step_2048
         ↓ 用户批准 continuation[2048→4048]
checkpoint_4048_saved → evaluate → awaiting_final_review
```

如果某 Arm 在某节点被用户停止，其历史 Run 必须可读取和归档，不允许用另一个 Arm 的模型或同名 Run 继续。**审阅可只批准一条 Arm**；此后同 Step 的严格 P/EP 对照不再成立，报告应标记缺少匹配节点，而不是填补虚构结果。

如果训练完成并已保存完整 Checkpoint，但 Adapter+Head 独立重载门禁失败，不启动另一 Arm。先修复加载路径，再用 `repair-reload` 从已保存的训练状态重算固定 Prompt logits、核验导出文件，并写入兼容回执；该恢复操作不得执行任何 optimizer step。兼容范围只允许推理重载精度处理，回执分别绑定基础模型 dtype、LoRA FP32 Adapter dtype、原训练代码、新兼容代码、Checkpoint 与零新增步数；之后才能开始配对的另一 Arm 或评测。

### 2. Checkpoint 的完整内容

按 A6 F4 机制复用成熟的状态保存/验证思路，但不要直接调用与 F4 Completion、F4 Prompt 绑定的训练函数：

- PEFT LoRA Adapter 权重和配置，以及当前 Arm 分类头权重和标签顺序；
- AdamW 每个参数的 `step/exp_avg/exp_avg_sq`，参数组名称/顺序/数量，Scheduler 状态；
- Python、NumPy、Torch CPU/CUDA RNG 状态，模型训练模式及 PEFT dtype；
- 固定 `schedule.jsonl` 与 cursor/epoch 信息、已消费 ID 哈希、实际 global optimizer step、4 microbatch/step 证据；
- Base、Prompt、Tokenizer、Train Fit/Calibration 分区、标注合同、源码、配置、软件版本与 Checkpoint 文件 SHA；
- 独立重载与恢复一致性检查；中断恢复时严格核对下一条样本 ID。

**保存可恢复状态与仅用于推理的 Adapter+Head 导出是两份不同产物。** 允许中间评测加载导出副本；评测和阈值校准后释放 GPU，不能改变训练 Run 的 RNG/Optimizer。新节点必须恢复同一套优化器动量与 Scheduler，禁止仅重新加载 LoRA 权重并把 Step 512→1024 写成连续训练。

### 3. 用户审阅后批准的票据

提供独立的只读 `review` 命令和 `authorize-resume` 命令，审批需要记录用户明确的自然语言指令、Arm、Run ID、已完成 Step、目标 Step、CheckPoint Manifest SHA、上个节点评测 Manifest SHA、代码/配置 SHA、审批日期及确认范围。

**不得由 Codex 代替用户签发下一节点许可**；CLI 参数 `--allow-staged-training` 只是执行保险，不能替代真正的审批记录。未批准时 `resume` 应在加载 GPU 模型前拒绝；出现新提交导致代码 SHA 不一致时先审查、形成有记录的兼容性决议，不得通过注释掉 Hash 校验继续。

阶段审批流程的交付口径：Codex 完成 Step 512 → 输出固定的报告及真实资产身份 → 停止并提交给用户/审查者 → 用户决定停止、继续 P、继续 EP、或继续两组 → Codex 按明确批准写票据 → 执行下一段。**不创建任何自动循环到 4,048 的脚本。**

## 六、每个 Checkpoint 应如何审查和决定

### 1. 固定输出

每个节点必须在两个 Arm 训练到**相同累计 Step**后分别评测：

| 评测 | P | EP |
|---|---|---|
| Profile 33 标签预测 | 必须 | 必须 |
| Emotion 16 分类 | 不存在；`not_applicable` | 必须 |
| Profile 0.5 阈值 | 必须 | 必须 |
| Profile Train-Calibration 阈值 | 必须 | 必须 |
| 224 Dev Profile F1 / P / R / TP / FP / FN | 必须 | 必须 |
| 画像三维、逐标签、Gold 空/非空、短长历史 | 必须 | 必须 |
| 数据消费/训练 Loss/梯度/CheckPoint/显存 | 必须 | 必须 |
| 与 E01-B Fast-only 的同 ID 对照 | 必须 | 必须 |
| Profile-only 的 Emotion 分数 | `not_applicable`，**不伪造** | 实测 |
| Response、完整 JSON、官方端到端延迟 | `not_run` | `not_run` |

必须附两组在相同 ID 上的差异分析：P 正确 EP 错误的标签、EP 正确 P 错误的标签、EP 新增 TP 与新增 FP 的数量、Precision/Recall-F1 变化、负样本误报数量、逐维标签折损。不要只报告一个 F1。

另计算排序质量（例如有可计算条件下的 micro Average Precision / PR 曲线）以区分“隐状态可分性不足”和“阈值不佳”；这只是诊断，不能用测试集搜索部署阈值。低支持标签的 PR-AUC 有不稳定或未定义情况，标注 `insufficient_support`。

### 2. 审阅逻辑（不自动替用户做决策）

- **Step 512**：确认真正有梯度、模型没有全空/全正塌缩、标签统计与长尾情况、两个任务的相对早期信号。不以无法立刻超越 E01-B 为自动停止条件；Base Fresh-start 与 Full B 的训练进度不同。
- **Step 1,024**：比较同 ID 的 512→1,024 变化；Profile TP 是否增长、Precision 是否受控、全空样本比例是否下降、EP 的情绪任务是否有正向或负向迁移。
- **Step 2,048**：核心审查节点。如果两组都接近常量预测、PR 排序质量没有改善、FP 激增或表现与 E01-B 差距巨大且趋势停滞，明确建议停止；如果持续改善且误报可控，可申请继续到终点。
- **Step 4,048**：观察峰值 Checkpoint 而非默认最后节点最好。选择最佳模型时**记录“观察多个 Checkpoint 后选择”的开发集选择偏差**；候选须另做完整交付协议/非代理评测才能替代 E01-B。

固定质量安全线以 E01-B 224 点作为参照：基线 Precision `0.482993`、FP `152`；当候选接近基线 F1 时，Precision 下降超过 0.02 或 FP 增加超过 10% 应显著警告，而不是仅因 F1 增长就通过。**这些是“建议停止/风险审阅”信号，不对 Fresh-start 的早期节点做无条件自动终止。**

报告必须给出三种不同状态：工程门禁 `passed/blocked/failed`、模型质量 `promising/inconclusive/underperforming`、继续授权 `awaiting_manual_review/approved/stopped`。绝不把 CI 通过、Checkpoint 有效、Loss 下降视为画像效果成功。

## 八、具体实施与 Codex 执行次序

### 阶段 G0：静态基线审查与冻结（CPU）

1. `git status`、分支 HEAD、远端最新提交和 CI；确认 A5、A6 两组代码来源，清理不得覆盖的历史资产清单。
2. 核对 E01-B、A4 224 Fast-only、A5.0 监督与分区 Manifest；必要时只读生成 A7 专属来源回执。
3. 生成 P/EP **同一** Prompt-only 数据索引和全 4,048 步 Schedule；检查 Epoch 边界与所有 ID/分区 Hash，禁止 Dev/Val 进入训练。
4. 冻结两组初始 LoRA 与共享 ProfileHead 的初始化 Seed、BCE、EP CE、λ、LR、阈值校准算法、阶段计划、固定 224 IDs、代码版本。
5. 新增 CPU 合成模型与分类头测试，验证前向维度、标签对齐、同 Arm 初始化、无 Gold 泄漏、P 无情绪梯度、EP 有情绪及画像梯度、Loss/Gradient 数学一致。
6. 验证 Resume 的全状态保存加载，至少使用小型合成训练：不间断跑 K 步 vs `K/2→Checkpoint→Resume→K`，比较参数、Optimizer、Scheduler、随机数及样本消费状态。
7. 完成语法、格式、老 A5/A6 非破坏性回归与 CI；产出 `G0_passed`，不能把 CPU 假数据测试记成 GPU 成功。

### 阶段 G1：真实 GPU 前置检查

1. P、EP 分别加载真实 NF4 Qwen3 Base 和新 LoRA；核对零时刻 LoRA 初始化一致及 Head 参数。
2. Prompt-only forward 输出正常；确认 LoRA 反向可达、分类 Head 梯度存在、Base 不更新。
3. 记录 FP32 分类头与 FP32 LoRA 的实际 dtype、NF4 Base 与 BF16 计算配置、CUDA peak allocated/reserved、模型实际参数计数、可用磁盘、最长输入。
4. Dry-step 不执行 optimizer.step()，且所有初始权重保持不变。若失败，先修复工程或另立配置版本，不得偷偷缩短 Prompt/改变输入数据。
5. 成功后产生绑定 `arm+config SHA+code SHA+data SHA+init SHA+dry-run SHA` 的单次启动票据。

### 阶段 G2：首节点 0→512（用户本次批准的范围）

1. 按冻结顺序先 P 后 EP，分别训练至累计 Step 512；每个 Arm 只能恰好 512 次 optimizer.step()。
2. 保存完整 Checkpoint、独立 Adapter+Head 导出，核验原 Base 未变、随机数/Optimizer state 完整、train ledger 无缺漏；独立重载并对小批固定输入比较 logits。
3. 只读执行 **Train Calibration → 冻结该节点阈值 → Dev 224 推理（不读取 Gold）→ 锁定预测 SHA → 读 Gold 评分**；同一节点两个 Arm 的推理设置一致。
4. 生成 Step 512 的配对差异表与状态评估；写 `awaiting_manual_review_step_0512`，停止、释放 GPU。
5. **向用户提交审查材料，等待用户批准**：是否 P/EP 都继续、只继续其中一组、或终止；没有回执绝不能运行 Step 1,024。

### 阶段 G3：批准后逐段恢复

- **512→1,024**：验证 `reviews/step-0512.json`、已评测结果与 Checkpoint 身份 → 同 Run 恢复到 1,024 → 按 G2 相同步骤生成报告 → 再暂停。
- **1,024→2,048**：同理，禁止从头重跑，必须延续优化器/RNG/样本顺序。
- **2,048→4,048**：仅获明确批准后执行；在 2,826 保存 Fit Epoch 边界 Checkpoint，按冻结第 2 轮样本顺序继续，4,048 完成后仍先报告，不自动替换基线。

### 阶段 G4：最终分析与实验归档

- 纵向曲线：P/EP 每节点 0.5 与 Calibration 阈值 F1、Precision/Recall、TP/FP/FN、全空比例、每维表现、EP 情绪性能；
- 横向对照：在相同 Step P vs EP，记录情绪 CE 对画像带来的正/负迁移；
- 基线对照：同样 224 ID 的 E01-B Fast-only；区分端到端完整 JSON 与直接分类口径；
- 峰值节点选择：报告多个节点筛选的偏差风险，不按最后节点自动选最佳；
- 保留/拒绝：真正提升画像且 FP/Precision 可接受才建议后续集成；否则保留 E01-B。

## 十一、关键风险与解释口径

1. **闭世界标注与长尾失衡**：未标注标签按负例会放大负样本数量，普通 BCE 可能输出大量空画像；不能以低 FP 掩饰 FN，必须报告 calibrated threshold 与 0.5 两种口径、AP 和长尾标签。
2. **任务拆分并非必然有益**：EP 的情绪梯度可能促进或妨碍 Profile，判定必须以 Profile 为主；Emotion Accuracy 即使提升也不构成接受 EP 的充分条件。
3. **Fresh-start 不可能通过一两个早期节点证明最终好坏**：Step 512/1,024 是趋势观测；只有足够长的结果及可接受误报才能考虑使用。
4. **直接分类与官方生成接口不同**：分类头结果本身不能直接提交。将来需要在满足赛事协议下从 E01-B 回复生成与该头合并，独立核对 JSON、情绪与回复一致性、延迟/显存和 vLLM 适配；这些属于本次训练实验以外的部署门槛。
5. **不可把原始 A6 F4 的性能直接映射到本任务**：A6 仍有完整 Response Loss，本任务无 Response，且分类头不生成文本。可复用阶段恢复思想，不把 A6 的优化进度当成当前分类曲线的理论保证。
6. **进度审核权限真实有效**：用户已明确授权本次实施 P/EP 至第一个 512 节点；后续继续训练必须在每个节点提交报告后得到新的明确指令。不要把其他实验的旧授权复制到本任务，也无需反复质疑用户对过去实验的授权。
