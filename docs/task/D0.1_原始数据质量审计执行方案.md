# EmotionalCompany · D0.1 原始数据质量审计执行方案

> **执行对象**：Codex（项目仓库根目录 `EmotionalCompany/`）  
> **阶段定位**：D0 数据工程的第 1 阶段，**只读、全量、可复现审计**。  
> **本阶段目标**：弄清数据中真实存在的结构问题、关联问题、分布特征和潜在风险，为 D0.2 清洗规则讨论提供证据。  
> **禁止事项**：不修改官方原始文件；不清洗、删除、修复原始样本；不生成 SFT 训练数据；不做 Train/Dev 划分；不训练模型；不擅自决定异常样本去留。

### 1.3 以原始数据为准的基本结构

```text
Conversation（JSONL 每行）
├── conversation_id
├── turns[]
│   ├── turn_id
│   ├── role
│   └── content
└── prediction_points[]
    ├── target_user_turn_id
    ├── assistant_response_turn_id
    └── target
        ├── emotion_label
        ├── user_profile
        │   ├── personality_traits[]
        │   ├── interests[]
        │   └── style[]
        ├── response_text
        └── memory_refs[]
```

- 一段对话可以存在**多个**预测点；它们不是天然重复数据。
- `target_user_turn_id` 标识当前应当预测的用户轮次；当前轮及其之前的合法消息才可进入未来的模型输入。
- `assistant_response_turn_id` 用于核对目标回复的来源和时序，**不能仅凭数值大小代表数组时间顺序**。
- `user_profile` 的三个空数组均为**合法值**；与字段缺失、`null`、类型错误严格区分。
- 原始数据中的非空 `memory_refs` 不应被判为脏数据。A0 后续推理固定输出 `[]` 属于训练/推理协议选择，不是 D0.1 的清洗理由。

### 2.2 预定命令行接口

Codex 实现下述 CLI 后，以以下命令完成一次全量审计：

```bash
cd ~/projects/EmotionalCompany
source .venv/bin/activate

python -m src.data.audit --config configs/data_audit.yaml
```

此命令应当：只读取 `train`/`val` 与相关 Schema；向指定产物位置输出 `manifest.json`、`summary.json`、`issues.jsonl` 和人类可读 Markdown；打印简短运行摘要；正常检测出数据异常时不视为程序崩溃。仅当输入缺失、无法完成审计或程序自身出错时返回非零退出码。

配置中使用相对项目根目录的路径；本地、队友、CI 不应需要手动改 Python 代码。

## 三、D0.1.1 文件级与结构级审计

> **检查范围**：训练集和验证集逐行全量检查。严重坏行也必须留下行号及错误原因，避免数据在统计时无声消失。

| 检查 ID | 内容 | 审计输出 |
|---|---|---|
| `FILE_PARSE` | UTF-8 解码；非空 JSONL 行能否独立解析成对象 | 文件、物理行号、解析异常类型 |
| `ROOT_SCHEMA` | `conversation_id`、`turns`、`prediction_points` 是否存在、类型符合官方约束 | 缺失/类型错误的具体字段路径 |
| `TURN_SCHEMA` | `turn_id`、`role`、`content` 的存在性、类型、角色枚举 | 对话 ID、消息数组索引、字段路径 |
| `POINT_SCHEMA` | 两个目标轮次 ID 及 `target` 结构是否存在、类型是否正确 | 预测点索引、字段路径 |
| `TARGET_SCHEMA` | `emotion_label`、`user_profile`、`response_text`、`memory_refs` 的字段及类型 | 缺失、`null`、类型异常分别统计 |
| `PROFILE_SCHEMA` | 三个画像维度是否为数组；数组元素是否合法 | 维度与非法值，不将 `[]` 判错 |
| `ENUM_CHECK` | 16 类情绪和三个画像维度是否符合官方标签枚举 | 非法值频次、样本定位 |
| `EMPTY_CONTENT` | 空消息、仅空白消息、空参考回复 | 按来源及角色计数、供复核 |
| `EMPTY_POINTS` | 对话存在但 `prediction_points=[]` | 数量与对话定位，**先标记不删除** |

枚举以项目可找到的官方 Schema 为首要依据；当前架构记录中的集合可作为对照：

- 情绪（16）：`joy`, `gratitude`, `relaxed`, `care`, `pride`, `neutral`, `surprise`, `mixed`, `sadness`, `loneliness`, `anxiety`, `anger`, `fear`, `disgust`, `shame`, `helplessness`。
- 性格（10）：`extroverted`, `introverted`, `open`, `conservative`, `high_conscientiousness`, `casual`, `agreeable`, `assertive`, `emotionally_stable`, `sensitive`。
- 兴趣（12）：`study_exam`, `programming_technology`, `reading_writing`, `film_animation`, `music`, `games`, `sports_fitness`, `travel_outdoor`, `pets`, `social`, `career_development`, `art_design`。
- 风格（11）：`brief`, `detailed`, `colloquial`, `formal`, `direct`, `indirect`, `humorous`, `rational`, `high_emotional_expression`, `low_emotional_expression`, `emoji_user`。

如果官方 Schema 与上述列表不同，**不要默默采用任一版本**；在报告中列明差异，并将“标签集合口径确认”列为 D0.2 前置问题。

**特殊情形**：`turn_id` 的类型及唯一性使用 Schema 确认。检测重复 ID 时保留原值与类型；不要将布尔、数字、字符串混同处理，不自动补齐缺号或改编号。

## 四、D0.1.2 对话时序与预测点关联审计

这是最高优先级的**正确性审计**，必须严格基于 `turns` 数组位置（`index`）建立 ID → 位置映射，不凭 `turn_id` 的大小计算先后。

对每个 Prediction Point，按以下顺序检查：

1. `target_user_turn_id` 在当前对话中是否**唯一**匹配一个 Turn。
2. 匹配的 Turn 是否具有 `role=user`。
3. `assistant_response_turn_id` 是否唯一匹配一个 Turn；该 Turn 是否为 `role=assistant`。
4. 参考回复所在数组位置是否严格晚于目标用户位置；早于或等于时记为 `RESPONSE_NOT_AFTER_TARGET`。
5. 目标回复是否恰好为目标用户消息之后的第一条 Assistant 消息；若不是，先记为 `RESPONSE_NOT_FIRST_ASSISTANT` **待复核**，不能直接认定标注错误。
6. `target.response_text` 是否与被指向的 Assistant Turn `content` 完全一致；如不一致，记录 `RESPONSE_TEXT_MISMATCH`，并分别统计“完全一致”和“仅换行/空白差异”的数量，不自动替换任一文本。
7. 同一对话内是否存在相同目标用户轮次的多个预测点；有则区分“重复相同监督”和“监督标签冲突”。
8. `turns` 的角色排列是否存在连续 User/Assistant、空轮次等现象；仅按数据约定将其列为警告或描述统计，**不能因为不交替就直接判错**。

**关键不变量**：对于一个关联合法的预测点，其未来训练输入只能由 `turns[:target_index+1]` 构造。D0.1 只审核这一规则是否能够执行并记录异常，不在此阶段生成训练样本。

**避免重复报错**：如果目标 ID 因结构问题无法定位，只记录根因与必要的派生说明，不继续针对同一预测点制造一串无意义的后续错误。

## 五、D0.1.3 重复、冲突、噪声与跨集合检查

采用低成本、确定性的第一轮筛查；不要对全部预测点进行无索引的两两相似度比较。

| 检查类别 | 规则 | 解释边界 |
|---|---|---|
| 重复对话 ID | 文件内、Train/Val 跨文件检查 `conversation_id` 是否重复 | ID 重复不直接等于内容重复 |
| 完全重复对话 | 对 `turns` 的规范化 JSON 表示求 SHA-256；区分内容相同与 ID 相同 | 相同对话需复核，不自动删除 |
| 完全重复预测点 | 同一规范化合法历史 + 监督目标内容求指纹 | 同一 Conversation 的不同目标通常应区别对待 |
| 相同输入、冲突监督 | 同一合法历史指纹对应不同 `emotion_label` 或画像标签 | 标记潜在监督冲突；不同合理回复不算必然冲突 |
| Train/Val 重合 | 跨集合比较对话文本指纹、规范化合法历史指纹 | 发现候选泄漏风险，不擅自删除官方 Val |
| 无效或异常字符 | 检测替换字符 U+FFFD、NUL、常见控制字符等 | Emoji、口语、重复标点不是自动清洗对象 |
| 极端文本长度 | 按 Unicode 字符数统计消息/回复长度分布，标记极端值 | 仅报告，不设武断的删除阈值 |

指纹计算必须**明确标准化层级**：

- 完全一致指纹：保留原始文本内容，只统一对象键排序/JSON 序列化实现细节，用于客观判断内容重复。
- 可选的“规范化比较”：仅用于识别疑似重复，例如统一换行、前后空白后再次哈希；必须与完全一致计数分开，不能用它改写原文。
- 无法可靠完成近似去重时，报告注明“仅执行精确匹配与轻度规范化候选检查”，不要假称已经完成全量语义去重。

对跨集合泄漏检查，还要区分常见模板化短句与长对话高度重合；输出统计与脱敏定位信息，不直接把短文本相同当作数据泄漏的证明。

## 六、D0.1.4 标签分布与基础长度统计

**这里仅做原始文本/标注统计，不使用 Qwen Tokenizer。** Token 预算与 1024/2048/4096 覆盖率属于 D0.4，避免 D0.1 同时承担模型相关预处理。

### 6.1 全量数量与分布

每个集合分别报告：

- JSONL 物理行数、可解析行数、对话数、`turns` 总数、预测点数；无预测点对话数；每段对话轮数及预测点数分布。
- 情绪 16 类频次、占比；Top 类与少数类；所有非法/缺失值数量。按**预测点**计数，不按对话计数。
- 三个画像维度：空数组率、各标签出现频次、每点标签数量、跨维度共现；区分三维全空、个别维度为空、字段缺失。
- `memory_refs`：空/非空比例、列表长度分布；**不将非空视为异常**。
- 用户当前消息、Assistant 参考回复的字符长度；每段合法历史的消息数及字符数（可定位时）；P50/P90/P95/P99/最大值。
- `response_text` 的重复频次与短回复、极长回复候选数量；短/长阈值来自配置，仅用于**提示人工复核**。

### 6.2 统计口径必须明确

- 所有百分比必须注明分母。例如“画像三维全空比例”以**结构有效且画像字段可读的预测点数**为分母；另报无法统计样本数。
- P90/P95 等分位数应选用固定、测试覆盖的算法，并在报告中注明口径。
- 遇到字段错误，记录“不可分析”数量，不能默默剔除后仍声称覆盖全部原始数据。
- 合法但稀有的情绪、空画像、非空记忆引用只做统计，不据此决定清洗或重采样。

## 七、异常分类、记录格式与审计伦理

### 7.1 异常等级

| 等级 | 含义 | D0.1 处理 |
|---|---|---|
| `ERROR` | 确定的结构或指向错误，可能无法安全提取监督样本 | 记录；提出 D0.2 待处置项 |
| `REVIEW` | 关联、语义或重复冲突可疑，需要人工确认 | 记录证据；**不自动下结论** |
| `INFO` | 合法但重要的分布现象，例如空画像、类别不均衡 | 汇总统计；必要时样本级定位 |

等级描述错误的**确定性**，不代表是否删除。例如“空预测点”属于合法结构事实，即使不能贡献监督样本，也不应强行判定为坏数据。

### 7.2 `issues.jsonl` 建议字段

```json
{
  "issue_id": "train:123:2:RESPONSE_NOT_AFTER_TARGET",
  "severity": "ERROR",
  "code": "RESPONSE_NOT_AFTER_TARGET",
  "split": "train",
  "source_line": 123,
  "conversation_id": "train_conv_example",
  "prediction_point_index": 2,
  "turn_index": null,
  "field_path": "prediction_points[2].assistant_response_turn_id",
  "observed": {"target_index": 8, "response_index": 5},
  "message": "Referenced assistant turn is not after target user turn",
  "proposed_action": "manual_review_in_D0_2"
}
```

实际字段以简洁、稳定、易于排序和追溯为原则。没有预测点的文件级错误允许 `conversation_id`、`prediction_point_index` 为 `null`；不要为兼容示例而编造定位信息。

**报告不默认复制整段私人对话文本。** 优先输出文件行号、对话 ID、消息索引、异常编码、长度及哈希；确实需要人工审查时由工具按定位读取原始数据。避免在终端日志、Git 文档中泄漏完整对话正文。

## 八、配置、实现要求与可复现性

### 8.1 `configs/data_audit.yaml` 最小字段

```yaml
inputs:
  train: data/train/train_public.jsonl
  val: data/val/val_public.jsonl

output:
  directory: outputs/data_audit/d0_1
  report: docs/data/D0.1_数据质量审计报告.md

checks:
  schema: true
  turn_references: true
  duplicates: true
  cross_split: true
  distributions: true

thresholds:
  short_response_chars: 5   # 仅作为异常候选提示，不决定删除
  long_response_chars: 2000 # 仅作为异常候选提示，不决定删除
```

阈值是示例初值。Codex 可根据数据分布建议调整，但不得把它们作为清洗规则；最终值必须在报告中列出。Schema 文件路径可由代码发现并写入 `manifest.json`，不得在缺少证据时声称完成 Schema 验证。

### 8.2 实现边界

- Python 3，优先使用标准库 `json`、`pathlib`、`hashlib`、`collections`、`statistics`、`argparse`、`csv` 等；不因审计而新增重型 NLP 依赖。
- 按行读取 JSONL；错误行也要记录，避免整个文件读取中断。数据规模允许适度构造索引，但不要实现不必要的分布式或数据库组件。
- 按固定顺序输出：**split → 文件行号 → 预测点索引 → 检查编码**；JSON 保证稳定的键排序/编码与换行规范，便于 Git diff 和运行复现。
- 与运行时间无关的 `summary.json`、`issues.jsonl` 应尽量字节稳定；时间戳、机器信息、Git Commit、Python 版本等放入 `manifest.json`，不要混入统计摘要造成无意义变更。
- `manifest.json` 至少包括：原始文件路径、大小、SHA-256、行数；可用 Schema 的 SHA-256；审计配置 SHA-256；代码 Git Commit/dirty 状态；Python 版本；执行检查清单与异常计数。
- 首次读取前记录原始文件 SHA-256，处理结束后再校验一次；若改变必须失败并停止验收。
- 不读取测试样例的标准答案（本阶段也不需要），不修改 `participant/`、模型缓存或训练配置。
- 如果发现当前项目已有同等用途模块，优先小范围扩展，不要为了符合文件名重复造轮子；保留同等 CLI、产物和验收语义即可。

## 九、测试任务与验收标准

### 9.1 必须编写的合成测试

使用小型合成 JSONL/临时目录验证以下场景，不能用实际原始数据来制造测试异常：

1. 正常多轮对话 + 多个 Prediction Point：计数正确；多个点的合法前缀彼此独立。
2. JSON 格式破损、顶层类型错误、缺字段、`null`、错误类型：均可定位，后续行不丢失。
3. 目标用户 ID 缺失/重复、目标角色非 User、回复 ID 缺失/重复、回复角色非 Assistant。
4. 回复 ID 指向目标用户消息之前；回复非第一条 Assistant；参考回复与 Turn 文本不一致：各自正确分级。
5. `prediction_points=[]`、画像三个空数组、非空 `memory_refs`：不得被误判为确定性错误。
6. 完全重复对话、跨集合重复、相同历史但情绪标签冲突、不同合法回复：计数及分类正确。
7. `turn_id` 不连续/非单调：通过**数组索引**判断先后，绝不通过数值大小；若本身违反 Schema 则独立标记 Schema 问题。
8. 含中文、Emoji、换行、重复标点：审计不更改文本内容。
9. 各统计分母、百分比、分位数；存在无效样本时不会将可分析数伪装成总数。
10. 相同输入和配置重复运行：摘要、Issue 序列保持一致；所有原始文件字节不变。

## 十、D0.1 报告必须回答的问题

`docs/data/D0.1_数据质量审计报告.md` 应是可直接复用到参赛技术报告中的**精炼审计结论**，避免原样堆叠所有 JSON/日志。按以下结构组织：

1. **审计范围与版本**：数据来源、文件指纹、规则版本、审计日期、项目 Commit、官方 Schema 使用情况。
2. **基本规模**：按 Train/Val 分别给出文件行数、有效对话数、预测点数、不可解析/不可统计记录数，并解释与历史预期的任何差异。
3. **结构与关联问题**：各 Issue 的数量、影响范围、可定位示例（默认仅 ID/行号，不贴隐私正文）；特别说明空预测点与异常回复轮次是否复现。
4. **标签分布**：完整情绪频次表，画像三维标签频次与空值率，记忆引用统计；突出长尾现象，但不据此下清洗结论。
5. **重复与跨集合**：对话/预测点重复、标签冲突、Train/Val 重合候选数量与判断限制。
6. **原始文本长度**：消息、参考回复、合法历史字符长度分布及明显长尾；注明**尚未做 Tokenizer 审计**。
7. **质量结论**：确定结构错误、待人工复核项、合法分布现象各有多少；每项影响多少条对话/预测点，而非只给 Issue 条数。
8. **D0.2 待决表**：问题编码、数量、例子定位、可选处置、潜在风险、建议优先级、需要谁确认；不直接把建议视为已批准的清洗规则。
9. **复现说明**：执行命令、测试结果、原始数据未修改的验证结果、输出文件位置。

报告中明确区分：**数据事实 / 自动规则判定 / 需人工解释或推测**。图表可留待技术报告阶段制作；D0.1 不要求另建绘图脚本，也不生成无谓的临时图片。

## 十一、Codex 执行顺序与交付格式

按以下顺序完成一个完整的 D0.1，而不是只创建空目录或只做部分计数：

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 检查 Git、目录、原始 Schema 和已有相关模块；记录输入哈希 | 明确审计依据和禁止改动范围 |
| 2 | 实现审计配置与结构/字段检查 | 可完整扫描并定位坏行 |
| 3 | 实现时序关联、重复/冲突、Train/Val 交叉检查 | 可复现 Issue 列表 |
| 4 | 实现标签、消息长度、历史长度等统计 | 机器可读完整 Summary |
| 5 | 加入合成测试、异常分类与输出稳定性测试 | `pytest` 通过 |
| 6 | 运行 train + val 全量只读审计 | 四份正式审计产物 |
| 7 | 对照报告、产物统计与原始 SHA；清理本任务临时文件 | D0.1 质量门禁通过 |
| 8 | 提交简要实施说明与 D0.2 待决事项 | 等待人工审查后再进入 D0.2 |

**Codex 最终回复只需交付以下内容**：

- 修改/新增文件清单及每个文件的职责。
- 审计后的 train/val 对话数、预测点数、ERROR/REVIEW/INFO 数量，以及最值得关注的异常类别。
- 测试及审计执行命令、实际结果、原始文件 SHA 一致性的确认。
- 审计报告路径与 D0.2 待人工决策事项。
- 如遇无法完成的检查，说明具体原因与未覆盖范围；**不得将部分审计宣称为完整 PASS**。

**停止边界**：D0.1 审计、报告和测试验收完成后停止。不得自动进入 D0.2 清洗、D0.3 规范化、D0.4 Tokenizer 审计或 E00/E01 训练。
