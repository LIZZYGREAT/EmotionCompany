## 二、术语、数据契约与不可变约束

### 1. 四个基础概念

- **Prompt**：P0 系统指令 + 当前预测点截止时的合法多轮对话 + Qwen Assistant 生成前缀。
- **Completion**：正确情绪、画像、回复与 `memory_refs:[]` 的紧凑 JSON，连同 Qwen 模板要求的结束标记；不包含官方提交 ID。
- **Labels**：与 `input_ids` 等长的目标数组；其中 `-100` 表示该位置不参与交叉熵损失。
- **Data Collator**：把若干条长度不同的样本组装为同一 Batch 的组件。此阶段只做**右侧动态 Padding**，不用 Packing（把多条样本串接在一条序列里）。

### 2. 单条有效 SFT 样本的不变量

由 `src/shared/prompting.py` 的同一组 API 构造：

```python
selection = select_recent_complete_suffix(history, p0_text, P, tokenizer)
messages = build_messages(selection["selected_history"], p0_text)
completion_json = serialize_completion(target, official_train_schema)
prompt_ids = selection["prompt_ids"]  # 同源 T1 已用真实 tokenizer 得到
full_ids = encode_full_training_sequence(tokenizer, messages, completion_json)

assert full_ids[:len(prompt_ids)] == prompt_ids
completion_ids = full_ids[len(prompt_ids):]
assert completion_ids  # JSON 正文 + 正确结束标记
assert len(prompt_ids) <= P
assert len(full_ids) <= S

input_ids = full_ids
labels = [-100] * len(prompt_ids) + completion_ids
attention_mask = [1] * len(input_ids)
```

正式实现可以封装为小函数，但不得复制 `apply_chat_template`、T1 或 Completion 序列化的另一套业务语义。

**需要同时验证：**

1. `len(input_ids) == len(labels) == len(attention_mask)`。
2. `input_ids == full_ids`，`input_ids[:prompt_len] == prompt_ids`。
3. `labels[:prompt_len]` 全是 `-100`；`labels[prompt_len:] == full_ids[prompt_len:]`。
4. Completion 的首个 Token 被监督，结束标记也被监督；不能存在有用样本全部 `labels==-100`。
5. 训练器内的 Causal LM 负责 next-token shifting，**构造 labels 时不要手动位移**。
6. 模板中出现 `</think>` 等字面文本时，必须沿用 `reasoning_content=""` 等共享协议逻辑，不允许重写用户或助手原文。
7. JSON `response_text` 经反序列化与原始 Target 逐字一致；画像数组排序和空 `memory_refs` 是**已冻结的 A0 Completion 规则**，不得反向写回 D0.3 Target。

注意：`labels` 不等于“只能把 Completion IDs 单独输入模型”。模型看到整个 `input_ids`，只是 Prompt 的预测损失被屏蔽。

### 3. S/P、G/K 的职责区分

- `S`（`max_train_seq_length`）：**本次训练序列最大长度**（Prompt + 完整 Completion）。
- `P`（`max_prompt_tokens`）：训练与推理共用的固定 Prompt Token 上限，T1 只看 Prompt 和 P。
- `G`（`max_new_tokens`）：推理时允许生成的最大 Token 数；不是训练的标准答案长度。
- `K`：实际推理服务可用上下文窗口；和 `S` 不自动相等，真实服务上的 `P+G<=K` 在部署验收阶段验证。

**在 D0.4.3 不根据 G/K 筛掉训练数据，也不修改 runner 的临时 P/G 默认值。**

## 五、B 阶段：建立 Completion-only 训练样本与排除账本

### 1. 样本处理顺序

以每个 D0.3 预测点为单位：

```text
读取 sample（source、sample_id、history、target）
    ↓
按固定 P 调用共享 T1：选择最新连续完整 History 后缀
    ↓
若仅保留当前 User + P0 仍超 P → 当前 S/P 标记不可用
    ↓
生成 P0/F2 Prompt Token IDs
    ↓
按 A0 JSON 规则序列化完整 Target（不回写原始数据）
    ↓
用同一 Qwen Chat Template 编码完整 Assistant 目标消息
    ↓
严格核验 Prompt/Full Token 前缀、Completion 和 EOS
    ↓
若完整序列超 S → 当前 S/P 标记不可用
    ↓
否则生成 input_ids、labels 和来源元数据
```

### 2. 单条 JSONL 训练产物格式

推荐格式（示例数字仅展示结构，不是真实 Token ID）：

```json
{"sample_id":"train_conv_000001:pp0","input_ids":[11,12,13,14,15],"labels":[-100,-100,-100,14,15],"prompt_length":3,"completion_length":2,"source_split":"train"}
```

- 允许记录 `source`/`conversation_id` 以便错误定位，但**不把它们传入 `model.forward()`**。
- `attention_mask` 对单条有效、未填充的序列等于全 1；可以在 Collator 中生成以免产物冗余。
- 不复制长篇 History、回复文本到 SFT 产物和日志；文本保留在来源 D0.3 文件，数字数据与来源 ID 足以回查。
- `sample_id` 不进入模型输入；`id` 只由比赛推理程序负责。
- 样本顺序沿 D0.3 已固定的原始输出顺序；不在这个阶段 shuffle，避免额外的不确定性。

### 3. 当前预算无法容纳时的处理政策

两种互斥的不可用原因：

- `prompt_floor_exceeds_cap`：仅 P0 + 当前完整用户消息也超过 P。
- `completion_overflows_train_budget`：T1 选择的 Prompt 合法，但加上完整标准 JSON 后总长度超过 S。

两者都不从 D0.3 原始文件删除、不更改标签、不把不可用样本“留在数据集中等待 Trainer 自动 truncate”。

`excluded_samples.jsonl` 每条至少记录：

```json
{"split":"train","sample_id":"...","S":2048,"P":1280,"reason":"completion_overflows_train_budget","prompt_tokens":1254,"full_tokens":2203,"source":{"split":"train","line":1,"prediction_point_index":0}}
```

数字为结构示意；实际来源字段遵循 D0.3 已有 `source` 契约。绝不记录未经必要的个人原始对话正文。

### 4. 必须符合 D0.4.2 的数量守恒

第一候选 `S2048/P1280` 的预期（如输入版本不变）：

| Split | 原样本 | `full_fit` | `trimmed_fit` | 不可用 | SFT 可用 |
|---|---:|---:|---:|---:|---:|
| Train | 16,312 | 11,381 | 4,811 | 120 | **16,192** |

## 六、C 阶段：动态 Padding 与 Batch 数据结构验收

### 1. Data Collator 应做什么

设一个 Batch 中样本的实际长度为 `n1,n2,...`，目标长度为 `L=max(ni)`。

只在每条序列右侧填充 `L-ni` 个位置，不提前把全部样本补齐到 S。

输出三个 PyTorch 张量，形状均为 `[batch_size, L]`：

```python
{
    "input_ids":      LongTensor[batch_size, L],
    "labels":         LongTensor[batch_size, L],
    "attention_mask": LongTensor[batch_size, L],
}
```

构造逻辑：

```text
有效前缀：
  input_ids = 已核验的 full_ids
  labels = [-100]*prompt_len + completion_ids
  attention_mask = 1

补齐位置：
  input_ids = 真实 tokenizer.pad_token_id（或经明确确认的兼容占位值）
  labels = -100
  attention_mask = 0
```

**注意 EOS/PAD 可能具有相同 Token ID**：绝不能通过扫描 `input_ids == pad_token_id` 来屏蔽 Labels！仅根据 Collator 真正增加的填充位置决定 `attention_mask=0` 与 `labels=-100`，否则可能遮蔽真实 EOS。

- 优先右填充，`pad_to_multiple_of=null`，Packing 关闭。
- 对 `batch_size=1,2,4` 覆盖等长、短长混合、Prompt/Completion 边界、超长样本过滤后的 Batch。
- 不使用会擅自将 `labels` 设回 `input_ids` 的通用 Language Modeling Collator，除非经真实接口检查证明它逐元素保留原始 Labels。可用一个**小型专用 Collator**，不要额外封装训练框架。
- 对于整个 Batch 内 `attention_mask==1` 的位置必须保留原始有效 Token；`attention_mask==0` 的位置 `labels` 必须为 -100。
- 不把 `sample_id`、统计信息、`source` 作为任意未知关键字传给 Qwen `forward`。

### 2. Batch 必须通过的不可变条件

```python
assert batch["input_ids"].shape == batch["labels"].shape
assert batch["input_ids"].shape == batch["attention_mask"].shape
assert (batch["attention_mask"] == 1).sum().item() == sum(len(s["input_ids"]) for s in samples)
assert not ((batch["attention_mask"] == 0) & (batch["labels"] != -100)).any()
```

并对每条样本反向切片：

- `batch_input_ids[i, :n] == prebuilt_input_ids[i]`。
- `batch_labels[i, :n] == prebuilt_labels[i]`。
- Prompt 部分全部 -100；Completion 第一个 Token、JSON 正文和最终 EOS 均被监督。
- Padding 段长度与位置精确符合右填充；不覆盖 EOS。
- 在 CausalLM 使用的 Labels 中不要提前手动左移一位；框架实际计算 next-token 交叉熵时会执行必要 shifting。

### 3. EOS 结束监督的具体测试

读取 Tokenizer 实际 `eos_token_id` 并核对配置签名：

- 完整 JSON 正文解码与原始监督一致。
- 编码序列末尾存在当前模板正确的 Assistant 回复结束 Token（本锁定 Qwen Tokenizer 报告 ID `151645`），且**最后一个真实 EOS 的 Label 不为 -100**。
- 即使 `pad_token_id == eos_token_id`，补齐区域仍必须 `labels==-100`，而真实 EOS 仍必须被监督。
- 包含转义引号、换行、Unicode/emoji、文字 `</think>` 的数据，在监督区域往返解码后语义和文本均符合原始 JSON。

**C 阶段门禁**：抽查真实 Train/Dev 样本 Batch 与合成极端情况全部通过；任何 Padding 都不会影响真实 EOS 和 Completion 监督。

## 七、D 阶段：Trainer 数据入口契约测试（不训练模型）

### 1. 首选方案与为什么需要测试

我们使用**预编码数据**：已经由共享 Qwen Template 构造好 `input_ids`、`labels`，不希望训练器再“帮忙”构造一套监督掩码。

当前项目锁定 `trl==1.14.2`、`transformers==5.20.2`。API 随版本变化；**不得仅根据 TRL 最新在线文档假设项目安装版本一定支持任意预编码 Labels 和自定义 Collator**。

执行时应通过查看实际签名/帮助和极小的本地试验确认：

```bash
python - <<'PY'
import inspect, transformers, trl, datasets
from trl import SFTTrainer, SFTConfig
print('transformers =', transformers.__version__)
print('trl =', trl.__version__)
print('datasets =', datasets.__version__)
print('SFTTrainer =', inspect.signature(SFTTrainer))
print('SFTConfig =', inspect.signature(SFTConfig))
PY
```

之后进行**数据接口级验收**：

1. 将已预编码的合成 Train/Dev 样本转换成实际准备交给 Trainer 的数据格式。
2. 经选定的 DataLoader/Collator 取到真实 Batch。
3. 比对 Batch 中完整 `input_ids`、`labels`、`attention_mask` 与 C 阶段预期。
4. 如 TRL 在 `SFTTrainer` 初始化时重新预处理、重排、截断或覆盖 Labels，明确显示差异与失败，不能悄悄容忍。
5. 可以采用合成、极小的本地模型/对象完成 Trainer **数据通路**验证，但不运行训练循环、不加载 1.7B 权重、不反向传播、不保存模型。

**禁止**为了“通过测试”把 `labels` 扔掉并改用通用的 `completion_only_loss=True` 后重新构造；那样会绕开本次要验收的关键契约。

如果锁定的 TRL 版本无法稳定接受预编码 Labels：**先停在 D 阶段，报告可复现的最小失败案例与替代方案**。改用原生 `transformers.Trainer`、升级 TRL 或改变训练数据表示都属于后续工程取舍，不能未经批准擅自修改 A0 主线。

### 2. 禁止的“假阳性”验收方式

- 仅检查 `SFTConfig(completion_only_loss=True)` 存在。
- 仅比较数据集加载前后的条数。
- 只跑普通 Tokenizer smoke test，未对 Trainer 实际收到的 `labels` 做逐元素比较。
- 用另外一个 Tokenizer、另外一种 Chat Template 或手写字符串来替代项目真实序列。

**D 阶段门禁**：至少通过一个实际候选 Trainer 数据路径的 Batch 全量字段断言；如受版本限制不能完成，要提供具体差异并明确阻断，不得报告“已完成 Trainer 集成”。

## 十一、简明验收标准

只有全部满足，才能宣布 D0.4.3 **数据构建与 Trainer 接口验收通过**：

1. **输入与协议**：D0.3、P0、Tokenizer/Template 均锁定，未改原文件；训练 Prompt 与正式 runner 的共享规则一致。
2. **监督正确**：Completion-only Labels 精确、真实 EOS 监督存在，无样本全 `-100`，不重复位移，不截断标准 JSON。
3. **预算正确**：固定 P 执行 T1，S 决定可用性；逐样本 outcome 与 D0.4.2 可核验，所有样本有去向。
4. **Batch 正确**：动态右侧 Padding，不把 EOS 当 PAD 掩盖；张量字段及标签经逐元素比对正确。
5. **Trainer 接口正确**：至少一种项目锁定版本下的实际训练器数据通路已经验证，不重编码、不重设掩码、不截断；若未通过，明确记录为阻断，不能宣称全通过。
6. **工程正确**：配置明确、测试全通过、可重复生成、报告与源码一致、输出文件清理规范、无提前扩展到正式训练。

**核心目标不是“生产了很多 Token 数组”，而是证明后续 E01 每一次前向计算读取的数据以及被优化的 Token 目标均可解释、可追溯、可复现。**
