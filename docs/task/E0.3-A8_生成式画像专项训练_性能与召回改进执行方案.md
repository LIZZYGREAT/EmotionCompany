# E03-A8：生成式画像专项训练性能与召回改进执行方案

> **执行对象**：`LIZZYGREAT/EmotionCompany` 的 `exp/e03-a8-generative-specialist` 分支。<br>
> **任务目标**：保留 A8 的 P（Profile-only）和 EP（Emotion+Profile）生成式 SFT 路线，解决训练过慢、Step 512 画像几乎全空的问题。<br>
> **本次交付范围**：训练性能诊断与优化、两份专项 Prompt 修改、首批训练数据重排、新 Run 的 P/EP Step 512 训练与画像评测。<br>
> **执行要求**：本方案自包含；保留当前 A8 历史 Run/Checkpoint/预测结果，不覆盖。新一轮使用独立 `A8-V2` 配置、数据产物和 Run ID。首次只训练至 **512 Optimizer Steps**，之后暂停并提交结果审核。

## 一、现有问题与本次修改目标

当前 A8 的 P 线 Step 512 已完成 **2,048 条样本曝光**，但得到：

| 固定评测集 | TP / FP / FN | 画像 Micro-F1 | 现象 |
|---|---:|---:|---|
| Pilot160 | 0 / 0 / 258 | 0 | 全空预测 |
| Dev224 | 1 / 0 / 372 | 0.0053 | 几乎全空 |

严格格式及 EOS 完成率均为 100%，说明模型已经较好地学会固定字段格式，**却没有表现出有效的非空标签判断能力**。

另外，现有 P Step 512 训练记录显示累计耗时约 `11,157s`，均值约 `21.8s/step`；实际观察中某些步骤超过 `40s`。需用相同样本和环境精确测量瓶颈，不得仅以不同任务或不同机器的单步耗时直接下结论。

本次修改围绕三个问题：

1. **减少无效计算**：完整 Causal LM 前向为所有 Prompt 位置生成大词表 logits，而监督只在 Completion；加之逐步大量 GPU→CPU 同步，可能造成显著开销。
2. **减少不合理的保守输出**：Prompt 的“依据不足即 `-`”容易使训练早期模型把 `-` 当成安全答案。改为鼓励从直接证据及合理间接线索输出标签。
3. **让模型在初期见到更充分的非空正例**：重新安排前 2,048 条训练样本，兼顾三维覆盖和必要的空画像负例。整个 Train 仍然保持 16,192 条、每条一轮只消费一次。

最终评价指标首先看 **画像 Micro-F1、Recall、TP 与 FP 的实际变化**；同时记录 Precision、Macro-F1、三维结果、格式率和每步耗时。不能用 Loss 下降或格式正确率代替画像质量评价。

## 二、明确保留的 A8 训练定义

本轮仍然只训练两套独立的 Qwen3-1.7B Base + QLoRA：

| 属性 | P：Profile-only | EP：Emotion+Profile |
|---|---|---|
| Prompt | `p_a8_v2_profile.txt` | `p_a8_v2_emotion_profile.txt` |
| Gold Completion | 3 行画像字段 | 1 行情绪 + 3 行画像字段 |
| 损失 | Completion-only Token CE | Completion-only Token CE |
| 生成 | `model.generate()` | `model.generate()` |
| 画像格式 | `Personality=...` / `Interests=...` / `Style=...` | 相同 |
| Emotion 格式 | 无 | `Emotion=...` |
| 多标签分隔符 | `\|` | `\|` |
| 空维度 | `-` | `-` |

保持 Base、Tokenizer、Chat Template、NF4/BF16、QLoRA（`r=8, alpha=16`）、学习率 `1e-4`、Microbatch=1、Gradient Accumulation=4、Seed=42、P=1280/S=2048 限制和固定评测集口径。只修改 **生成式训练计算路径、Prompt 和首段样本顺序**。两条线使用相同的样本 ID、相同训练顺序及相同历史截断结果。

禁止引入额外分类头、BCE、Response 字段或 Response Loss；也不修改正式赛事推理接口。

## 三、修改一：优化 A8 训练速度

### 1. 先定位真实耗时

重点审查 `src/training/e03_a8_staged.py::_execute_segment()`：

- `model(**batch)` 对整段 Prompt+Completion 执行 Causal LM 前向；仅 Completion Tokens 参与 CE。
- `_gradient_facts()` 在**每个优化步**遍历所有 LoRA 梯度，逐张量执行 `isfinite().all().item()` 与 `count_nonzero().item()`，产生大量潜在 GPU 同步点。
- 每条 Microbatch 都使用 `loss.item()`，可能同步 GPU。
- 每步调用 `inference.cuda_memory_facts()` 与 `_append_ledger()`；后者每步执行 `fsync()`。

先增加一个**不修改模型参数与正式 Run 状态的性能诊断入口**，从真实 Train 中固定选取短、中、长序列的代表性样本：

1. 在相同设备上统计 `data_fetch/collate`、模型 Forward、Backward、Optimizer、梯度统计、日志落盘各部分耗时。
2. CUDA 计时在诊断边界同步，正式训练不要每个 Microbatch 都同步；同时记录 CUDA 峰值和输入 Token 数。
3. 报告整体每优化步均值/P50/P90、不同序列长度的耗时，解释超长步与短步差异。
4. 先完成性能定位，才能决定最终保留哪些优化。

旧训练日志可按相邻 `elapsed_segment_seconds` 差值还原逐步用时。该字段为**累计段时间**，不能把每一行数值直接当成当步耗时。

### 2. 核心优化：仅为受监督 Completion 计算词表 logits

在 `src/training/e03_a8_staged.py` 中增加独立的 `completion_only_forward_loss(...)` 计算路径，具体可放在 `src/training/e03_a8_completion_loss.py`。

一条预编码训练样本满足：

- `input_ids` 长度为 `n`；
- `prompt_length = p`；
- 目标 Token 为 `input_ids[p:n]`（含 EOS）；
- Causal LM 第 `t` 个隐藏状态负责预测第 `t+1` 个 Token。

实现：

```python
# 伪代码：单样本，右侧无 Padding；用同一套 Qwen Backbone / LM Head
outputs = backbone(
    input_ids=input_ids,
    attention_mask=attention_mask,
    use_cache=False,
    return_dict=True,
)
hidden = outputs.last_hidden_state       # [1, n, d]
pred_hidden = hidden[:, p-1:n-1, :]    # 只保留能预测 Completion 的位置
logits = lm_head(pred_hidden)           # [1, n-p, vocab_size]
target = input_ids[:, p:n]              # [1, n-p]
loss = cross_entropy(
    logits.float().reshape(-1, logits.shape[-1]),
    target.reshape(-1),
    reduction="mean",
)
```

**实现关键：**

- 复用真实模型的 `get_output_embeddings()` / LM Head，不能新建一个随机初始化的输出头。
- Backbone 必须就是带训练中 LoRA 的那条实际计算路径；检查 Qwen 最终 Norm、模型包装层和梯度能正常传入 LoRA。
- 第一个 Completion Token 要用 `p-1` 处隐藏状态预测；必须监督最终 EOS；不偏移、不遗漏、不重复。
- 维持与当前 `model(**batch).loss` 相同的 CE reduction、logit dtype 转换、Prompt Mask 意义、训练/推理模式。
- 优化仅减少**未受监督位置的词表投影**；完整 Prompt 仍必须参与注意力计算。

**等价性门禁（必须在正式训练前通过）：** 对同一真实 Base+LoRA、同一批短/长、空/非空 Gold 样本，不进行 `optimizer.step()`，分别运行旧路径与新路径，逐条比较 Loss 和**全部可训练 LoRA 梯度**。给出绝对/相对误差与容差依据；如果发现不一致，先定位偏移或精度问题，不得直接训练。

### 3. 减少常规训练中的同步与 I/O 开销

在保留故障可发现性、Checkpoint 完整性和精确恢复能力的前提下：

- 将 `_gradient_facts()` 的逐张量完整检查改到 Dry-run、前几个 Step、周期性诊断（建议每 32 Step）和保存 Checkpoint 前。常规每步使用更轻量的总梯度范数/非有限检查，保持异常即中止。
- 不再为每个 Microbatch 立即执行 `loss.item()`；用 `detach()` 累积数值，按诊断间隔批量回收标量。仍保留每步 Loss 记录，需准确还原其来源。
- CUDA 内存完整事实、日志细节也按间隔采样；常规日志减少重复的设备同步。
- 采用缓冲批量写 `step_ledger.jsonl`，在间隔边界和保存 Checkpoint 前显式 Flush + `fsync`。异常中断时只允许从**最后一个已验证的完整 Checkpoint**恢复，不能把内存中未持久化的 Step 计为完成。
- 优先排查实际 GPU 计算耗时与 Host 同步次数，再决定是否调整 Gradient Checkpointing；不得为追求速度直接关闭导致 8GB OOM。

建议使用相同 16–32 个代表性优化步做旧/新基准测试，并分别提供 P、EP 的实际均值/P50/P90、训练有效 Token 数、峰值显存、GPU 利用率（如果可用）。目标是**相同样本与硬件下显著加速，优先达到至少 2 倍**；如果达不到，必须给出测量证据和剩余瓶颈，暂停正式 512 步重训，由用户决定是否接受速度。

## 五、修改三：重排首批 512 步训练样本

### 1. 新首段配比

A8 原来对 16,192 条 Train 随机打乱后训练。新版只改变**样本进入训练的顺序**，不增加、不删除、不复制训练样本。

首批 **2,048 条**建议固定为：

| Gold 画像类型 | 数量 | 首段占比 |
|---|---:|---:|
| 至少一个画像标签非空 | **1,536** | **75%** |
| 三维画像全部为空 | **512** | **25%** |
| 合计 | **2,048** | 100% |

这是提高训练早期正例曝光的实验性设定，不代表最佳配比已得到验证。剩余 14,144 条放入后续同一轮的随机顺序，全部恰好使用一次。

### 2. 正例内部不能简单随机抽取

在 `scripts/e03_a8_prepare.py` 的 Schedule 构建中增加独立、可复现的 `A8-V2` 首段分层选择函数（建议写入 `src/data/e03_a8_sft.py` 或新 `src/data/e03_a8_schedule.py`）：

1. 从冻结的 16,192 条有效 Train 中读取对应的官方 Gold 画像，按 `sample_id` 精确对齐，不改训练答案。
2. 拆分为 `nonempty` 和 `all_empty` 两个集合，只在 Train 内采样。
3. 在 1,536 条非空样本中，尽可能覆盖 Personality、Interests、Style 三维的正例；同时兼顾历史长度（短/中/长）与不同标签的出现频率。
4. 避免选出的样本过度集中在少量 `conversation_id`；优先增加独立会话覆盖，必要时允许同一会话多个不同预测点，但必须记录数量。
5. 对极稀有标签记录在首段中是否出现、出现次数；不强制为了覆盖少数极稀有标签而复制样本。
6. 从空画像集合选择 512 条，仍覆盖不同历史长度和会话，保留模型学习真正空画像的能力。
7. 两组 Arm 使用**完全同一条** 16,192 样本顺序，四条样本组成一个 Optimizer Step。
8. 使用固定 Seed，保存完整 `sample_order.jsonl`、算法版本、抽样明细摘要及 SHA-256。

首段建好之后，输出审计报告：实际全空/非空占比、三维各自至少一个正例的样本数、33 标签频次、会话数与重复度、历史长度分布、Prompt 和 Completion Token 长度 P50/P90、首段与剩余样本是否集合互补。

**历史截断一致性：** 新 Prompt 比旧 Prompt 更长，必须重新运行 `P0/T1 → P/EP 共同历史截断 → 编码`，保证每个样本两线看到相同历史，Prompt 不超过 1,280 Token，总序列不超过 2,048 Token。若出现当前用户消息本身超出预算或样本不可编码，报告并中止重建；不得静默丢样本导致两线 ID 不一致。

P 的训练 Gold 仍然是：


EP 的训练 Gold 仍然是：


Prompt Token 的 `labels=-100`，仅 Completion 正文和终止 EOS 参与 Token CE。空维度按官方 Gold 序列化为 `-`。**不能因为 Prompt 改得积极，就将 Gold 中原本为空的维度修改成非空。** 本轮不增加 Token 加权、新的 Loss 类型或人工伪标签，以便把首段正例比例与 Prompt 改进的效果解释清楚。

## 七、Codex 执行顺序与验收门槛

### 阶段 A：只读诊断

检查旧 P512 的 `step_ledger.jsonl`、已消费 2,048 IDs、数据分布与已有预测。报告：

- 旧首段 Gold 的空/非空率、标签分布、三维覆盖；
- 按 Step 还原的时间 P50/P90，长短序列是否显著影响耗时；
- 每步的 Forward、Backward、梯度统计、CUDA 同步与 I/O 占比（新增诊断跑）；
- 可定位的性能主因和优化前基准。

只读，不重新跑旧的 512 步，也不修改旧 Checkpoint。

### 阶段 B：代码与数据改造（CPU + 有限 GPU 验证）

按第三至六节修改；CPU 先检查语法、严格协议、样本集合、Token Mask、EOS、P/EP 共用历史、数据 SHA，再执行少量 GPU 对照：

- **Loss 一致性**：旧 `model(**batch).loss` 和新 Selective Logits Loss 数值接近；LoRA 梯度方向、范数和逐参数误差符合冻结容差。
- **计算正确性**：正例样本的非空标签 Token 确实参与 Loss，不存在只监督固定字段或 `-` 的情况。
- **速度对照**：相同真实样本、相同环境、实际前向+反向+更新，对比均值/P50/P90、显存。性能未获明显改善时先汇报，不直接发起长训练。
- **可恢复性**：小规模独立 Run 验证暂停→保存模型、Optimizer、Scheduler、RNG、样本游标→重载→继续，确保没有掉步/重步。

### 阶段 C：全新 P / EP Step 512

在门禁通过后，从原始 Qwen3-1.7B Base 分别新建 P 和 EP Adapter，不继承旧 A8 P512 权重。两线使用一致的初始 LoRA 权重、数据顺序、优化器参数。各训练到累计 **512 步**，保存完整 Checkpoint，确认可独立重载。

每次训练必须记录：已消费的 2,048 个样本 ID、全局步数、实际 Token 量、每步/每 32 步训练耗时、全段 Loss 均值、最近一个 Step Loss、非空 Gold 分组 Loss（可通过独立只读诊断求得）、峰值显存、Adapter/Checkpoint SHA。

### 阶段 D：固定 Dev 生成评测，提交人工审核

P 和 EP 分别从新 Checkpoint 加载、使用各自新 Prompt、Greedy 生成规定的 3/4 行；严格 `=`、`|`、`-`、固定字段顺序与 EOS，不增加 Response。

用已冻结的 Pilot160 和 Dev224，生成并冻结预测文件后再读取 Gold 评分。至少提交：

| 评测内容 | 必须报告 |
|---|---|
| 工程 | 预测覆盖、严格解析率、EOS 率、非法标签/截断原因 |
| 画像总体 | TP/FP/FN、Micro-P/R/F1、Macro-F1 |
| 画像分维度 | Personality/Interests/Style 各自 TP/FP/FN 与 F1 |
| 输出行为 | 非空画像预测数、全空率、每样本平均标签数、空 Gold 的 FP |
| 情绪 | EP 的 Emotion Accuracy；P 标注 N/A |
| 对照 | A8 原 P512 同 ID 结果，以及 P-V2 与 EP-V2 结果 |
| 资源 | 每步训练 P50/P90/均值、GPU 峰值显存、累计训练时间 |

另外，使用已消费过的 Train 正例进行**只读生成诊断**（例如固定 64 条正例），区分模型是否连训练见过的非空标签也无法输出。Train 诊断不代替 Dev 指标，也不用于事后改 Gold。

最后只交付 Step 512 结论和下一阶段建议，状态标记为 `awaiting_manual_review`。**未经用户审阅，不继续到 Step 1,024。**
