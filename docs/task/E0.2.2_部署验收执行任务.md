### 2. 唯一异常：`test_001058_t0`

已有证据：`status=invalid_label`、`generated_tokens=1200`、`stop_reason=server_finish_reason:length`、延迟 23294.338 ms；从 `extract_object(raw_text)` 提取的对象中 `response_text` 的读取长度为 0、`emotion_label` 无效、`user_profile` 不为对象。

## 二、任务执行原则

1. **先 CPU / 静态、后 GPU**。GPU 实跑一次一份 Run ID，运行失败保留原目录、日志和报错；不得覆盖旧结果。
2. **基线不可漂移**。冻结 Base 权重 SHA、Full B Adapter 权重和配置 SHA、Tokenizer 修订、P0 SHA、P/F/T、Greedy、LoRA 路由、vLLM 0.11.1。Smoke 使用 P=1280、G=1200、K=2560、BF16、rank8、`gpu_memory_utilization=0.80`；不同实验使用独立配置快照。

## 四、E02.2-A：P0/F2/T1 的真实服务端 Token ID 等价性（第二优先级）

### 1. 已发现的技术途径

vLLM **0.11.1 版本化文档**在 `ChatCompletionRequest` 中声明 `return_token_ids`，响应可包含 `prompt_token_ids`。相关依据：

- https://docs.vllm.ai/en/v0.11.1/api/vllm/entrypoints/openai/protocol/
- https://docs.vllm.ai/en/v0.11.1/api/vllm/entrypoints/openai/serving_chat/

当前 Runner 只核对 `usage.prompt_tokens` 与本地数量；缺少完整 token 序列核验。先在 **隔离诊断请求**中显式传 `return_token_ids: true`，验证 pinned vLLM 0.11.1 返回值的真实字段位置、类型与长度。不借用最新 vLLM 文档推断旧版本行为。API 若不接受或不返回字段，如实记录 `unsupported/not_observable` 和 HTTP/字段证据，不能伪造 PASS，也不直接改 vLLM 内核。

### 2. 必须比较的两条真实数据路径

**本地预期链**：

`target-free id+history` → 仓库 `select_recent_complete_suffix` (T1，最多 P=1280) → `build_messages` (P0+原生多轮) → 固定 `Qwen3-1.7B` Tokenizer 的 `apply_chat_template(tokenize=True, add_generation_prompt=True, enable_thinking=False)` → `expected_prompt_ids`。

**vLLM 观察链**：

同一份选择完成的 `messages` → `/v1/chat/completions`，`model=e01-full`，`chat_template_kwargs.enable_thinking=false`，`return_token_ids=true` → 读取响应 `prompt_token_ids` → `actual_prompt_ids`。

比较时必须有 `expected_prompt_ids == actual_prompt_ids`（逐位置的整数序列），而非仅 `len()` 相同。记录 ID 总数、首个不一致位置、两侧该位置的整数和局部窗口、两侧 Token ID 序列的 SHA；默认报告**不输出原始消息文本和全部 Token IDs**。若发现差异，可在忽略的本地目录保存供调试的受限证据。首轮可复用本次 10 条 Smoke 的无标签 `test_input.jsonl`，覆盖短、中、长 History；再补 1～2 个包含 `</think>` 字面内容的**合成测试**，检验仓库对 assistant 消息的特殊处理。不要直接往官方 Runner 中加入有副作用的诊断开关。

### 3. 实现建议和验证门禁

优先新增小型 `scripts/e02_token_equivalence.py`（或在现有 E02 probe 中增加清晰子命令），复用 `participant.run_inference` 与 `src.shared.prompting` 的同一份加载/模板代码，不重写第二套 P0/F2/T1。若必须启动服务，可以让现有 `start.sh` 提供**显式 opt-in 的本地诊断钩子**或采用独立生命周期脚本，但不可改变官方只接受 `TEST_FILE RESULT_DIR` 的入口契约。

诊断请求可将 `max_tokens` 设为 1 以减少 GPU 计算，因为本阶段只检查输入 Token IDs；记录该独立诊断请求不同于正式推理配置，不能拿它计算性能。始终保持 `model=e01-full`、相同 Messages 和 Chat Template 参数。

CPU 测试覆盖：精确相等、同长度但不同内容、不同长度、服务不支持 `return_token_ids`、响应缺字段、错误的 `model`、缺失 `enable_thinking=false`、T1 保留历史变化、重复样本 ID、输出路径覆盖拒绝。仅本阶段得到真实 0.11.1 服务响应后才能写 `passed_exact_server_prompt_ids`；不能通过 Mock 充当 GPU 验收。
