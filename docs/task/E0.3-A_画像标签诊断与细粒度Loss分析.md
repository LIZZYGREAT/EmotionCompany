# EmotionCompany E03-A0.1：画像标签可学习性与细粒度监督诊断（Codex 执行方案）

> **目标仓库**：`LIZZYGREAT/EmotionCompany`。<br>
> **本轮定位**：E03-A0.1 画像标签证据与细粒度监督诊断，现已完成；为后续 E03-A1 Loss 对照提供依据。<br>
> **任务边界**：A0.1 阶段只做诊断，不调整 Loss、不训练或续训、不修改模型权重、不改变比赛推理协议，也不启动官方提交和 Docker。用户已单独批准 E03-A1 Loss 对照，执行范围见独立任务书。<br>
> **环境**：WSL2 中项目 `.venv`；标签分布、证据审计和 Token 细分以 CPU 为主；有限 Teacher-forced CE 需要时使用现有 Transformers + NF4/BF16 + Full B Adapter，**不需要 vLLM**。

## 一、已有事实和本轮研究问题

E03-A0 已完成 16,192 条有效 SFT Train 的 Token 全量诊断，以及 128 条分层 Train 样本的冻结 Full B Teacher-forced CE 测量。当前报告：

- 全量 2,851,614 个有效监督 Token 中，`response_text` 占 **79.2621%**，`user_profile` 占 **8.8924%**，`emotion_label` 占 **1.0569%**；其余为公共结构、EOS 和跨边界 Token。
- 128 条 Teacher-forced CE 样本中，`response_text` 占 CE 总和 **98.3665%**，`user_profile` 占 **1.2795%**，`emotion_label` 占 **0.2565%**；这是 **Train 子集上的算术 CE 贡献**，不能等同于训练梯度或推理准确率。
- `user_profile` 的平均每 Token CE 约为 **0.2307**，但现有画像统计区域仍包含部分相对容易预测的固定结构；据此尚不能判断 **实际画像标签值** 的预测难度。
- E01-B Full 的 Dev 画像 33 标签 Micro-F1 **0.4223**、Macro-F1 **0.2700**，三维 Exact **32.08%**。例如 `conservative`、`high_emotional_expression`、`indirect`、`emotionally_stable` 在 Train 中均有一定正例，Dev 中却很少被预测。这些差异需要研究证据来源、标签定义与模型监督方式。

本轮着重回答两个问题：

1. **标签可学习性**：现有 Train 的 Gold 标签在对应对话中有什么依据？模型当时实际看到的 **T1 保留历史** 是否包含这些依据？哪些标签表现出明确证据、间接证据、证据不足或语义不确定的情况？
2. **细粒度监督**：`user_profile` 的 Loss 中，具体标签值、空数组决策、键名/JSON 结构、跨边界 Token 各占多少？在 Gold 非空时，现有字段平均 CE 是否被容易预测的结构 Token 稀释？

这两个问题相互补充：标签诊断解释数据与证据，细粒度 CE 描述冻结模型对 **Gold Completion** 的条件预测难度。都不是 A1 性能收益试验。

## 三、工作一：画像标签的 Train 证据与可学习性分析

### 1. 全量分布统计（CPU）

以 **16,192 条实际参与 Full B 训练的 SFT Train** 为主母体，使用 D0.3 同源 `target` 与 `history`，输出每个标签的正例数、Gold 非空率、各维度标签共现、单样本标签数分布，以及按 `full_fit/trimmed_fit`、对话长度、Gold 三维全空/非空的条件统计。

对于有 Dev 诊断记录的标签，可以在报告中**引用已冻结的 E01-B Full 聚合指标**作为选择研究对象的背景，但不能用 Dev 的逐条答案选择、修改 Train 标签，也不重新针对 Dev 调参。

建议优先审查这些存在不同表现的标签：

| 研究对象 | 已有 Train Support | 研究意义 |
|---|---:|---|
| `conservative` | 1,205 | 支持量不低，Dev 几乎不预测 |
| `high_emotional_expression` | 831 | 支持量不低，Dev 几乎不预测 |
| `indirect` | 459 | 支持量有限但不极端，Dev 未预测 |
| `emotionally_stable` | 296 | 更依赖综合证据，Dev 未预测 |
| `games` | 605 | 表现较好的对照标签，通常较易找到明确兴趣证据 |
| `sensitive` / `rational` | 4,471 / 3,733 | 高频对照，用于观察易过度泛化的性格、风格标签 |

这里的 Support 来自既有仓库诊断报告。实际执行应使用当前数据重新核验，不应把表中数字当作新 Run 的实测结论。

### 2. 可复核的 Train 证据判断样本

从 Train 中以固定 Seed 和明确采样策略抽取 **少量**审查对象，兼顾：目标标签的 Gold 正例、Gold 负例、证据可能分布在长历史中的样本、短历史样本，以及对照标签。可选择每个重点标签约 8–12 条正例，并加入适量负例；由于样本多标签共现，应记录唯一 `sample_id` 数与各组分母，不机械相加。具体审查规模可按工作量调整，但不得为“找到支持假设的例子”反复挑样本。

应同时提供两种历史视图：

- **原始合法 history**：仅包含该预测时刻之前的输入；不得查看未来轮次。
- **实际进入模型的 T1 history**：由既有 P0/F2/T1 构造得出，记录裁剪情况。不要调用成员 B 的尚未确定的 T2。

每条判断记录至少包含：Gold 标签、支持消息索引、该证据是否保留在 T1、证据类型、可能的冲突或歧义，以及审阅 Agent 的简短依据。

使用以下可复核的证据分类口径（属于**Agent 证据判断**，不直接改 Gold）：

- `explicit`：用户明确说出兴趣、偏好或相关事实；
- `inferred`：多轮表现形成间接但可解释的依据；
- `insufficient`：当前可见历史无法提供足够依据；
- `conflicting`：存在互相矛盾或随时间变化的证据；
- `uncertain`：证据边界或标签定义难以稳定判断。

同时独立标记 `retained_by_T1`、`removed_by_T1`、`not_identified`，避免将“证据不足”与“被裁剪丢失”混为一谈。Agent 如果只检查了部分历史，记录 `not_fully_reviewed`，不能强行归类为证据不足。

脚本负责抽样、显示本地材料和核对消息索引，不自行给出语义结论。本轮由三个 Agent 协作完成：Agent 1 初审，Agent 2 复核，Agent 3 先保存独立判断，再结合前两份意见逐条裁决。Agent 1 的记录说明其定稿时已经参考 Agent 2，因此这些结果不是三张独立选票，也不按多数票决定。最终分类必须明确标为 **Agent 判断**，不能称为人工核验、Gold 真值或标注错误率。`uncertain` 和 `insufficient` 是已定稿的判断类别，不是等待人类处理的队列；未被 Agent 识别为支持证据时仍须保留相应边界说明。

### 3. 输出结论的范围

可以根据实际审查数据讨论：

- 是否存在“Gold 有明显证据，但 Full B 仍难以预测”的训练研究动机；
- 哪些标签的证据相对直接，哪些主要依赖跨轮推断；
- 哪些样本的证据实际被 T1 裁剪，适合移交给成员 B 的上下文研究；
- 是否值得开展更大规模的标签审计。

不得仅凭少量审查样本宣布标注错误率、修改官方标签定义或给出“标签不可学习”的整体结论。由于本轮不要求重跑 Train 的自由生成，**Gold 证据审计不能直接推出逐标签生成错误的成因**；已有 Dev 逐标签错误只能作为背景。

## 四、工作二：画像标签值与 JSON 结构的细粒度监督统计

### 1. 在 A0 精确 Token 对齐基础上增设第二层归属

当前 A0 将 `user_profile` 作为较大的字段值区域，三个维度下也可能包含键名与符号。需要进一步在完整序列上区分：

| 二级类别 | 含义 |
|---|---|
| `profile_label_value` | Gold 中实际出现的 33 个合法标签字符串的 Token |
| `profile_empty_decision` | 对应画像维度为 Gold 空数组时，能够**明确**归属于空数组值的 Token |
| `profile_structure` | 固定维度键名、引号、逗号、括号及其他 JSON 结构 |
| `profile_boundary_mixed` | 同一个 Token 同时跨越两种细分区域，无法唯一归属 |

同时保留 `personality_traits`、`interests`、`style` 的维度归属，以及每个出现标签的统计。单个 Token 的文本可能同时包含引号/括号或跨字段边界，**不得为增加“标签值覆盖率”而任意分配**。若无法准确标记独立的空数组 Token，应该显示 `not_separately_attributable`，而不能将空数组监督记成不存在。

可以使用已有 `parse_completion_regions`、`assign_token_regions` 的完整文本 Offset 思路，在 **实际保存的原始 `input_ids`** 上扩展局部跨度；必须继续逐 ID 验证与旧版本相同，并让每个有效监督 Token 在新归属体系中恰好落入一个桶。原 A0 顶层统计口径与历史 JSON 不得被重写。

这部分特别需要防止如下边界：

- 中文、转义字符、`</think>`、重复字符串；
- 标签之间的逗号、引号和空数组；
- Token 横跨标签值与标点、跨维度的边界；
- EOS、首个 Completion Token、右 Padding 的 Mask；
- 同一标签在其他 JSON 字段文本中出现，不能错误匹配；
- 实际标签数为 0 时，相关字段值的统计仍应真实体现决策信息与不可分离边界。

### 2. CPU 统计：尽量复用已验证数据

提供全量 SFT Train 中以下**聚合**结果：

- `profile_label_value / profile_empty_decision / profile_structure / profile_boundary_mixed` 的 Token 计数、占比、样本均值及实际覆盖率；
- 画像三个维度的分布、Gold 空与非空样本的相应分布；
- 对 33 个标签，分别统计出现样本数、能够**明确归属**的标签值 Token 数和边界混合 Token 数；
- 明确归属口径的总 Token 数与 A0 顶层 `user_profile` Token 数如何对应；若新分类包括跨顶层边界的 Token，必须注明覆盖方式和守恒范围。

如果需要重新扫描 16,192 条数据，也应使用独立 Run 目录、只读模式和已有哈希验证。不要为了重新生成相同的 A0 汇总结果而覆盖其历史文件。

### 3. 可选的冻结模型 CE 补充

如果细分映射通过 CPU 验证、现有本地模型和 8GB GPU 环境可用，可沿用先前 A0 的 **128 条固定选择**复算细分 CE；这样比较同一批样本的顶部字段 Loss 与细分 Loss 更方便。若这 128 条对某些标签没有足够覆盖，则报告 `insufficient_support`，不要将零样本的标签 CE 写成 0；也不必立即扩大 GPU 样本量。

如确实需要补充重点标签的 Train 正例 CE，可另建一个 **独立、有界、明确记录选择策略** 的诊断 Run，并与原 128 条基准分开报告，不得直接合并为一个代表性总体估计。

CE 计算仍使用冻结 Full B、`model.eval()`、`torch.inference_mode()`、既有 NF4/BF16、本地 Transformer 模型加载，按 Causal LM shift 对齐。要验证新细分类别的 Token 和 CE 总和守恒，并与 A0 既有字段汇总一致；若有新定义的重叠或跨边界类别，应明确其不同口径，不伪称数值完全相同。

**特别注意：Gold 标签值的 Teacher-forced CE 低，不等于该标签具有较好的自由生成召回。** 自回归模型对未输出的负标签没有逐标签独立 BCE；本轮只提供后续研究依据。
