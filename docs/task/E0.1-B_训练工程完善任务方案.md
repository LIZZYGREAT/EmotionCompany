# E01-B：全量 QLoRA SFT 训练工程完善任务方案

> 仓库：`LIZZYGREAT/EmotionCompany`<br>
> 审查基线：`feat/e01-qlora-training-isolation`，`71b057ec457fffacbb529cf29151128d7f1fb5fb`<br>
> 前置依赖：《E01-A 训练诊断收尾任务方案》完成或明确登记其缺失项。<br>
> 本任务交付 **E01-B 可执行训练系统 + CPU/小规模 GPU 验收**；**不允许自动启动 16,192 条全量训练**。

## 一、现状与任务目标

E01-A 已验证 8 条 Train、120 Optimizer Steps 的真实 NF4 QLoRA 更新、Adapter 保存与重载，并在 20 条 Dev Smoke 上完成质量诊断。E01-B 的 `configs/training/e01_b.yaml` 仍为 `draft_manual_gate`，学习率、训练总步数、Epoch 等为 `null`，`src/training/training_sft.py::validate_training_mode()` 明确禁止 B 执行训练。

当前入口主要为 Micro-overfit 设计：`_select_real_samples()` 从 Train 挑选 8 条；`_build_sft_trainer()` 设置 `train_sampling_strategy=sequential`、`save_strategy=no`、`eval_strategy=no`；逐步更新回调会将全部 LoRA 可训练参数拷贝到 CPU 比较；`execute_training()` 仅支持 A 的 Step Proof 和独立 Run。**不能简单把 `sample_selection.count` 改成 16,192 就视为 E01-B 已完成。**

目标是在保留 E01-A 和 E00 行为的前提下，建立一条适用于全量 16,192 样本、可随机打乱、可恢复训练、可追溯评价且不会破坏 Base 的独立训练链路。

## 二、不可变的基线约束

- Base：`Qwen/Qwen3-1.7B`，权重聚合 SHA-256 `005d20550c04f4e246e5b434448786b44a0196b47d758d0acc77aba279e5bbc5`；本机 `participant/model` 是**只读输入**。
- 训练方式：NF4、BF16、Double Quant，冻结基础权重；只优化新的 LoRA A/B；不得加载 E01-A 的 Adapter 作为 B 初始权重。
- P0/F2/T1、Tokenizer、Chat Template、Non-thinking、Completion-only Labels、`S=2048/P=1280` 候选均保持现有协议；Prompt 和 Padding 的 Labels 为 `-100`，Completion 及 EOS 监督保留，不重复 Tokenize、不二次 Shift。
- 数据：`data/processed/sft/v1/train.jsonl` 有效 Train 16,192；SFT Dev 1,821 用于 Loss，独立生成评测 Dev 1,833。官方 Val 及 Dev 的 Gold 均不得作为训练输入。
- 模型身份、数据哈希、配置快照、Run ID 与日志写入忽略目录；禁止覆盖其他 Run 和 `participant/model`。
- 首轮正式 E01-B 延续标准 Completion-only Loss；暂不加类别权重、字段权重、特殊 Prompt、另外的分类头或不同模型。那些留待公平对照实验。

## 三、分阶段实现（按依赖顺序执行）

### B1. 建立独立训练配置与执行门禁

修改 `configs/training/e01_b.yaml`，并新增 `configs/training/e01_b_pilot.yaml`：

| 配置 | 数据范围 | 状态/权限 | 说明 |
|---|---|---|---|
| `e01_a.yaml` | 8 条固定 Train | 原实现不变 | 保留历史复现实验 |
| `e01_b_pilot.yaml` | 从有效 Train 固定选择约 512 条 | 可在完成预检后手动启动 | 真实长度和标签分布的试运行 |
| `e01_b.yaml` | 全量有效 Train 16,192 条 | 保持 `draft_manual_gate` | 仅经用户后续明确许可才能解除 |

Pilot 与 Full B 都要独立从同一 Base 新建 LoRA，并分别保存 Adapter。两者不相互续训。Pilot 必须在 Run Manifest 中标记 `training_scope=pilot`，不得将其成绩当作全量 E01-B 成绩；正式 B 标记 `training_scope=full_train`。

Pilot 的选择必须固定 Seed、保存样本 ID 与选择算法版本，覆盖实际训练数据的序列长度分位区间及情绪、画像非空情况；**不应照搬 E01-A“优先最短”策略**。512 是诊断规模候选，不是强制调整 D0.4.3 的原始数据量。

配置集中在 YAML：Seed、LoRA 配置、Batch、累计步数、学习率、Epoch/Steps、Warmup、Scheduler、日志和 Checkpoint 周期、验证周期、样本选择、显存约束。禁止散落在脚本中的不可追踪默认训练参数。

### B2. 重构训练执行路径：复用共性，但保留 A/B 语义

在 `src/training/training_sft.py` 中以最小侵入方式抽取公共机制：

```text
预检 Model/Data/Tokenizer/P0 与 Manifest
  → 根据实验配置选择训练样本（A固定8条；Pilot抽样；B全量）
  → 新建 Base + LoRA（初始 Adapter 独立）
  → D0.4.3 预编码 Dataset → 已有 SFTDataCollator
  → SFTTrainer 训练/验证 DataLoader
  → Train Forward / Backward / Optimizer Update
  → 定期日志、Dev Loss、可恢复 Checkpoint
  → Save Adapter + Manifest
  → Release → Reload 验证
```

特别要求：

1. B/Pilot 的 DataLoader 使用适当的 **确定性随机打乱**，并记录 Seed、Epoch、全量样本数与步骤数。A 的固定顺序不变。
2. 保留已有 TRL `skip_prepare_dataset=True`、`max_length=None`、`packing=False`、`padding_free=False`、`remove_unused_columns=False` 和自定义 Collator；训练初始化时用若干**可追溯的随机 Batch**校验 Labels 与预编码原数据，不能照抄“第一个 Batch 对应 JSONL 第一行”的顺序假设。
3. 防止因 `SFTTrainer` 的内部数据准备而覆盖已有 `labels`；Prompt 与 Padding 继续不参与 Loss。
4. 梯度累计步数在配置中明示；日志中的 `global_step` 一律指 **Optimizer Step**。增加实际训练 Token 数、有效样本/批次、Learning Rate、训练 Loss、吞吐和显存峰值记录。
5. 对梯度/参数更新的高开销全量 CPU 对比，只在首 Step、固定稀疏周期或异常时执行；常规训练只保留轻量标量指标。**不得为了监控导致每一步复制所有 LoRA 参数到 CPU**。
6. E01-A 已有训练/推理/API/评分行为与参数不得因重构出现变化。

### B3. 实现完整 Checkpoint 与续训能力

当前 A 的 `adapter_snapshots/` 与 `progress.json` **不足以恢复优化器、LR Scheduler、RNG 或采样位置**。B/Pilot 必须使用真正的 Trainer Checkpoint：

- 保存模型 Adapter、Optimizer、Scheduler、Trainer State、RNG State 以及能够支持同一 Run 恢复的数据顺序信息。
- 断点恢复仅允许同一 Run 的有效 Checkpoint；核验 Run ID、Base/Tokenizer/P0/Data Manifest/配置 Hash、训练范围、Checkpoint Step 与续训状态，不接受不同 Run 的 Adapter 或 Checkpoint 误用。
- 恢复前检查文件完整性；不允许在新 B 实验中加载 E01-A Adapter，更不得把恢复操作伪装成“独立实验”。
- 不覆盖原 Checkpoint 或已完成 Run；设置合理保留策略，例如保留最近 2 个有效中间 Checkpoint 及最终 Adapter，但不能删除恢复所需的唯一有效状态。
- 必须用**同一 Pilot Run 的暂停→恢复**测试核对步数和 LR 连续性，必要时比较连续训练与恢复训练的参数/指标一致性。若底层框架/算子导致逐位确定性不可实现，需明确差异边界而非宣称 bitwise 一致。
- 调整 `save_strategy` 和 `eval_strategy`；避免在每个训练 Step 或每次日志记录时进行全量生成推理。

### B4. 训练期间的评估口径

- 定期记录 **SFT Dev Loss**（1,821 条或固定、可复现的 Dev 子集，配置明确），仅用于训练进度观察和后续 Checkpoint 选择；这不是官方质量分数。
- 独立生成评测使用 D0.3 Dev 的无标签 `id+history` 输入，Gold 只由 Scorer 读取。Pilot 可先选定固定 160～256 条 Dev 作为工程诊断；选法、ID、Hash 保存，检查覆盖多个情绪和长短序列。
- 情绪 Accuracy/Macro-F1、画像 33 标签 Micro-F1/每维 Recall、Raw 严格 JSON 与 Raw Schema 分开报告。不得只看标准 Loss、归一化 Submission Schema 或三维画像 Exact Match。
- Pilot 的质量数字仅作为工程风险信号；**不根据其低分就自动切换模型或 Prompt**。

### B5. 训练预算与硬件管理

首轮候选保持 `r=8`、`alpha=16`、`dropout=0`、七类 LoRA Target、Micro Batch=1、Gradient Accumulation=4、AdamW、学习率 `1e-4`、BF16、梯度 Checkpointing。

- Pilot 建议最多 128 Optimizer Steps，足以在 Micro Batch 1、累计 4 的典型设置下遍历 512 个样本一次；它是资源上限候选，应由 GPU 预检和实际训练日志确定。
- Full B **先只记录候选**：1 Epoch、16,192 条有效 Train、Batch=1、Accumulation=4，对应理论约 `ceil(16192/4)=4048` 个 Optimizer Steps。实际 Steps 必须以框架的 DataLoader / Drop Last / Epoch 配置复核，不能把该算术估计冒充实际运行值。
- E01-A 的 475.5 秒对应短序列 8 条反复训练，不能直接线性外推到完整数据。Pilot 用真实长度分布测量显存峰值、Token 吞吐、每步耗时及可完成预算。
- 若显存不足，先排查激活、梯度 Checkpointing、显存驻留与长样本 Batch；不得静默降低 S、裁剪 Gold Completion 或改变 P0/F2/T1。任何变更要产生新实验版本。
