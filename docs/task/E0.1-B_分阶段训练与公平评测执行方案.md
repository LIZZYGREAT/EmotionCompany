# E01-B：分阶段正式训练与公平对照评测执行方案

> 仓库：`LIZZYGREAT/EmotionCompany`<br>
> 审查基线：`feat/e01-qlora-training-isolation`，`71b057ec457fffacbb529cf29151128d7f1fb5fb`<br>
> 前置依赖：《E01-A 训练诊断收尾任务方案》与《E01-B 训练工程完善任务方案》。<br>
> 执行门禁：**本文件是下一阶段方案，不授权 Codex 当前自动启动 Full B 或全量 Dev Base 推理。**

## 一、阶段目标

在 E01-A 验证真实 QLoRA 可训练之后，E01-B 需要正式回答：同一个 `Qwen3-1.7B` 在 **16,192 条有效 Train** 上进行 Completion-only QLoRA SFT 后，对未参与训练的 Dev 是否出现可靠改善？

当前仅有 E00.2 Base 与 E01-A Adapter 的 20 条固定 Smoke 对照：

| 指标 | E00.2 Base Greedy | E01-A 微过拟合 Adapter |
|---|---:|---:|
| Emotion Accuracy | 1/20 | 2/20 |
| Emotion Macro-F1 | 0.0179 | 0.0625 |
| Raw A0 Schema 合法率 | 0/20 | 7/20 |
| Profile 33 标签 Micro-F1 | 0.0400 | 0 |
| 画像三维 Exact Match | 5/20 | 8/20 |
| 字符级 BLEU-4 | 2.2406 | 1.3041 |
| 字符级 ROUGE-L | 0.1290 | 0.1531 |

这些结果是小样本局部诊断，**E01-A 的 8 条 Train 拟合不等于正式 SFT**。本方案先完成工程 Pilot，再执行独立 Full B，最后在同一批 Dev 上对 Base 和 B 进行配对比较。

## 二、实验组定义与独立性

| 组别 | 初始化 | 使用的数据 | 作用 |
|---|---|---|---|
| E00 Base | 固定原始 Qwen3-1.7B，无 Adapter | 无赛题 SFT | 零微调对照 |
| E01-A | 同一 Base + 新 LoRA A | 固定 8 条 Train | 训练链路、Micro-overfit 验证 |
| E01-B-PILOT | 同一 Base + 全新 LoRA Pilot | 约 512 条 Train | 显存、时长、Checkpoint 与训练路径预验收 |
| E01-B-FULL | 同一 Base + 全新 LoRA B | 16,192 条 Train | 正式训练和泛化评估 |

严禁将 E01-A 或 Pilot 的 Adapter 作为 Full B 的初始权重；Checkpoint Resume 只属于**同一** B Run 的继续训练。所有 Run 的配置、数据身份、初始化 Seed、Adapter SHA、Checkpoint 来源和评价输入 Hash 单独保存。

## 三、正式执行次序

### 阶段 0：根据 Pilot 确定预算（必须人工审核）

读取 `docs/experiments/E01-B_训练工程与Pilot验收报告.md`，并至少审阅：

1. 是否已验证 8GB RTX 4060 Laptop 的真实长序列 Batch（非 E01-A 的 425～461 Token 短序列）。
2. 训练期间 LoRA 参数梯度/Loss 是否正常；是否 OOM、NaN、Offload。
3. 按 Pilot 的实际序列长度与 Token 吞吐估算 Full B 的资源成本，明确估算的不确定性。
4. Checkpoint 及恢复是否成功、磁盘空间是否满足容量计划。
5. `configs/training/e01_b.yaml` 中的 `learning_rate`、Epoch/Steps、保存/验证间隔是否已经由人工确认并冻结。

只有明确批准 **E01-B-FULL 正式训练**，才可将配置由 `draft_manual_gate` 改成 `approved_for_full_training`，记录批准日期、任务范围与配置哈希。禁止通过程序检测 Pilot `passed` 就自行解锁。

首轮可考虑单一标准配置，不进行网格搜索：`r=8`、`alpha=16`、Micro Batch 1、累计 4、学习率 `1e-4`、约 1 Epoch。上述只是候选；实际预算需在批准前基于 Pilot 验证。下一轮才分别测试 Rank、学习率、Loss 权重等。

### 阶段 1：正式独立 Full B 训练

训练只读取 D0.4.3 有效 Train 16,192 条。固定数据顺序 Seed、P0/F2/T1、Tokenizer、S=2048/P=1280、原始监督 Labels、LoRA Target 与 Base SHA。

运行后检查：

- `manifest.json` 标记 `training_scope=full_train`、`init_adapter=null`、没有来自 A/Pilot 的任何 Adapter 源。
- Step、Epoch、已见样本/Token、梯度、Loss、Learning Rate、显存等日志持续写入忽略目录。
- 每次 Checkpoint 含足够完整的恢复状态；出错时可以在**原 Run**续训，不能创建新 Run 冒充独立训练。
- 定期记录 SFT Dev Loss；训练中不得将 Dev 混入优化器的 DataLoader。
- 保存最终 `adapter/` 与身份指纹，冻结选择用于正式评测的 Checkpoint。
- 独立重载后，Greedy Token IDs 在定义好的相同硬件/软件环境下按现有验收口径核对；不将训练过程中一次诊断视为正式最终结果。

建议在实现后提供显式 Full B CLI，例如：

```bash
# 注意：以下新 Full B 命令必须等人工解除门禁，且由操作人显式调用。
python -m src.training.training_sft \
  --config configs/training/e01_b.yaml \
  --mode train --run-id "E01-B-FULL-$(date +%Y%m%d-%H%M%S)" \
  --allow-full-training
```

`--allow-full-training` 是**待实现接口要求**，与配置中的 `approved_for_full_training` 双重检查。不得把它视作当前仓库已存在的命令。

### 阶段 2：补齐可比的全 Dev Base 对照

E00.2 只跑了固定 20 条，E00.3 完整 Dev Base 评测 `not_run`。在 Full B 完成后，必须针对相同的完整 Dev 建立 Base Greedy 的实际对照，不能把 20 条 Base Smoke 拿来与 1,833 条 B 比较。

使用 E00.1 已生成的、无标签的完整 `inference_input.jsonl`，共 **1,833 条**；References 与推理过程物理隔离。固定：

- **Base 模型与 Tokenizer**：两组使用同一 Qwen3-1.7B 文件指纹与 Tokenizer/Template。
- **Prompt**：P0/F2/T1，非 Thinking；P=1280，G=1200（如果修改任意一项，必须为两组创建相同新快照）。
- **Decode**：Greedy，`do_sample=false`；实际 NF4/BF16/CUDA 情况可验证。
- **评分器**：同一个 E00 Scorer 版本，同一指标、相同完整 ID 集、相同 Reference Hash；两组只区别 Adapter enabled 与否。
- **身份**：Base 组 `adapter.enabled=false`；B 组记录 Base SHA + B Adapter SHA + Adapter Config SHA。

建议增加通用的 `scripts/e01_b_evaluate.py` 或小规模扩展 `scripts/e01_evaluate.py`，但**不得直接沿用当前脚本的 `E01-A` 硬编码**：现有 `_load_run()` 仅接受 `experiment_id=E01-A`，`_prepare_snapshots()` 也把实验写死为 `E01-A`。新评测脚本需要支持 Full B 的已完成 Run，保持 E00/E01-A 原有协议和数据评分行为不变。

完整 Dev Base 与 B 的 GPU 生成应单独设人工资源许可，**不跟随训练成功自动启动**；推理可能较耗时，需保留进度与失败恢复机制，不能半途丢掉已经完成的推理记录，也不能把部分 ID 的结果冒充全 Dev。

### 阶段 3：生成评价与失败归因

对两组分别统计：

| 评估板块 | 必须输出的结果 |
|---|---|
| Emotion | Accuracy、16 类 Macro-F1、每类 Support/Precision/Recall/F1、混淆矩阵、预测分布 |
| Profile | 33 标签 Micro/Macro-F1、三个维度的独立指标、Gold/预测非空占比、非空样本 Recall、三维 Exact Match |
| Raw 格式 | 严格 JSON 可解析率、Raw A0 Schema 完整合法率、错误类型分布、字段遗漏、EOS/生成长度 |
| Submission | 最终官方 Schema 合法率，需明确归一化/置空可能掩盖 Raw 错误 |
| Reply | 字符级 BLEU-4、ROUGE-L；BERTScore 若环境/模型不可复现则明确 `not_run` |
| 性能 | Token 生成数、延迟分布、显存、硬件与计时作用域；20 条或不完整 100 轮不冒充正式性能 |
| 统计对照 | 相同 ID 上的 Base/B 配对正确/错误迁移与差值；必要时报告配对置信区间，避免仅报漂亮百分比 |

对分类错误至少拆分：生成格式失败、合法标签但分类错误、画像非法标签、错误空集/漏报、标签类别混淆，防止把 Parser 兜底后提交合法率解释为模型理解能力。

全部逐条 Raw 和对话保留在忽略目录；跟踪的 Markdown 只呈现聚合指标、匿名差异案例和实验结论。

### 阶段 4：根据实际结果选择下一种实验

不得预先设定“训练必然有效”。根据 Full Dev 证据分类讨论：

| 观察到的现象 | 优先后续实验方向 | 不应立即作出的推断 |
|---|---|---|
| Raw Schema 大幅提升，但情绪混淆多 | 对照 Prompt 增加经 Train 标注核对的类别边界定义；混淆矩阵引导少量示例 | 不代表必须升级 4B |
| 非空画像 Recall 低、倾向输出 `[]` | 先分析 Train/Dev 标签支持、不平衡、缺失值与现有归一化；再做字段级损失权重/采样对照 | 三维 Exact Match 提高不等于画像更准确 |
| Dev Loss 改善但回复指标不升 | 分析训练目标中回复 Token 占比、输出内容长度与实际回复质量；考虑多目标权重试验 | BLEU 单项下降不等于回复一定变差 |
| Train 拟合正常、Dev 全面停滞 | 核查数据分布、标签噪声、历史裁剪、容量限制；再设计较大模型对照 | 单次 E01-A 不能证明 1.7B 不适合 |
| 性能预算紧张 | 对比量化/生成长度、部署后端及更紧凑模型 | 不能只按离线 Quality 选择最终方案 |

如比较 1.7B/4B 或 P0/P1，分别创建新实验 ID、配置与干净初始化的 Adapter；用**相同 Dev ID 和评分口径**，尽量一次只改变一个主要变量。

## 四、必须保留的隔离原则

```text
participant/model/  # 原始 Base 不可改写
       ├── E00 Base → 全 Dev 预测/评分
       ├── E01-A Adapter（8 样本，历史工程验证，不作为 B 初始化）
       ├── E01-B-PILOT Adapter（512 样本，独立）
       └── E01-B-FULL Adapter（16,192 样本，独立）→ 全 Dev 预测/评分
```

每个 Run 都保存独立配置快照、数据 Manifest Hash、Base 权重 SHA、Adapter SHA、训练/生成参数、状态、时间和可恢复 Checkpoint。若路径冲突、模型身份不匹配或 References 混入推理输入，则立刻拒绝执行。

## 五、交付文件与运行命令

**建议交付：**

- `docs/experiments/E01-B_正式SFT与Dev对照验收报告.md`：Run ID、训练实际预算、最终结果与局限。
- `configs/evaluation/e01_b_full.yaml` 或在 `outputs/` 内保存独立评分快照：沿用已有 E00 Scorer 语义。
- 新增/扩展 `scripts/e01_b_evaluate.py` 或 `scripts/e01_evaluate.py`：Full Dev Base/Adapter 配对入口、Run/Adapter 身份核查、完成/失败状态持久化。
- 针对性的 `tests/test_e01_b_evaluate.py`：错 ID、错 Adapter、数据泄漏、评分口径偏移、部分完成不能冒充全量、重试隔离。
- `docs/workflow.md`：列出实际已验收命令与产物位置。

以下为**执行合同示例，评测接口需先实现并测试**：

```bash
# 审核后手动运行 Base Full Dev（不能在训练成功时自动触发）
python scripts/e01_b_evaluate.py \
  --scope full-dev --model base \
  --run-id E00.3-BASE-<人工指定唯一RunID>

# 审核后手动运行同一套 Full Dev 的 B Adapter
python scripts/e01_b_evaluate.py \
  --scope full-dev --model adapter \
  --training-run-root outputs/training/<真实E01-B-FULL-RunID> \
  --run-id E01-B-EVAL-<人工指定唯一RunID>

# 输入验证、离线配对汇总，不得重新训练
python scripts/e01_b_evaluate.py \
  --scope compare \
  --base-run-root outputs/evaluation/<真实Base评测目录> \
  --adapter-run-root outputs/evaluation/<真实B评测目录> \
  --output-dir outputs/evaluation/e01_b/comparison/<唯一对照ID>
```

命令中的占位符必须由执行人依据实际 Manifest 填写；新脚本创建后更新 `docs/workflow.md` 为真实可运行指令。

## 六、验收标准和停止条件

- [ ] 工程 Pilot 已完成，资源预算和 Checkpoint/Resume 经人工审核；完整训练得到单独批准才启动。
- [ ] Full B 使用 16,192 条有效 Train，**从 Base + 新 LoRA 开始**，不继承 A/Pilot 权重。
- [ ] 保存真实训练步骤、有效 Token/样本、Loss、学习率、显存、Checkpoint、Adapter 和身份信息。
- [ ] 全量 Dev Base 与 B 均为 **相同 1,833 个 ID**，Gold 不进入推理；不存在半数样本“补零凑数”的比较。
- [ ] Raw/Submission、各类情绪与画像、多目标回复指标分别报告，并解释 `[]` 空画像导致的 Exact Match 假提升。
- [ ] 评分与对照从现有 E00 Scorer 复用，E00/E01-A 回归通过；BERTScore、官方性能口径未验证时写 `not_run`。
- [ ] 输出目录、模型、Checkpoint 与 Raw 均保持 Git 忽略，正式文档只记录统计、结论及复现入口。
- [ ] 若出现 OOM、不可恢复 Checkpoint、NaN/Inf、协议/身份不一致，立即暂停并保留失败证据，不自动更换模型、Prompt、S/P/G 或继续训练。

**此任务真正完成的判据是：一组可重复、严格配对的完整 Dev Base vs E01-B 结果，而非 E01-B Loss 下降本身。**
