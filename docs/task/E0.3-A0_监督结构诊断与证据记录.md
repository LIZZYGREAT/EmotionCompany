# EmotionCompany E03-A0：监督结构诊断与证据记录（Codex 执行任务）

> **任务性质**：独立诊断工具、有限的冻结模型前向评估、可复核的结果记录。<br>
> **仓库**：`LIZZYGREAT/EmotionCompany`；工作基准分支：`feat/e01-qlora-training-isolation`。<br>
> **研究目标**：为 E03-A1 字段级 Loss 设计提供证据，**本任务不修改 Loss，不训练、不续训、不保存新 Adapter**。<br>
> **运行环境**：WSL2 Ubuntu、项目 `.venv`；仅模型前向诊断需要 RTX 4060 Laptop 8GB。无需 vLLM、Docker 或官方提交。

## 一、背景与需要回答的问题

E01-B Full 已在 `Qwen3-1.7B + NF4 QLoRA` 上完成正式训练（16,192 条 SFT Train，4,048 步），其 Dev 画像 33-label Micro-F1 为 `0.4223`，Macro-F1 为 `0.2700`，其中人格与交流风格维度较弱。这些结果表明存在研究空间，但**不能由此认定是回复 Token 过多或字段 Loss 竞争导致**。

当前 `src/data/sft_dataset.py` 将完整 JSON Completion 编码成 `input_ids`，Prompt 区域对应的 `labels=-100`，Completion Token（包含字段名、标签、回复正文及结束标记）参与普通 Causal LM 交叉熵；`src/data/sft_collator.py` 保留这些标签；`src/training/training_sft.py` 使用 TRL `SFTTrainer` 训练。

A0 要回答的是：

1. **监督量**：每条样本中情绪、画像、回复、固定结构分别占多少有效 Token？它们在整个 Train 中的分布如何？
2. **实际损失**：冻结 Full B Adapter 在同一训练样本上的 *teacher-forced* 字段级 Cross-Entropy 有多大？各部分对总体 CE 的算术贡献是多少？
3. **画像差异**：Gold 三维全空与非空样本，以及 `personality_traits` / `interests` / `style` 各维，监督 Token 与 Loss 有何差别？
4. **证据边界**：哪些结果能够支持后续字段加权假设，哪些仅是相关性，哪些尚无法判断？

A0 不负责验证标签是否合理、不设计新的采样策略、不研究 T2、不搜索 Loss 超参数；这些属于后续任务。

## 四、CPU 诊断：监督 Token 归属与数量分布

### 1. 输入与标注对象

对 `data/processed/sft/v1/train.jsonl` 的每条有效样本，用 `sample_id` 与 D0.3 `train.jsonl` 关联，读取其真实 `target`。通过仓库现有 `serialize_completion` 与已锁定 Tokenizer / Chat Template 得到**原来完整的 JSON 文本**及其在预编码序列中的位置。

必须逐样本验证：

- `input_ids` / `labels` / `prompt_length` 与现有 D0.4.3 记录一致，Prompt 全为 `-100`，Completion 含真实 EOS。
- 训练 Completion 与使用现有工具重新编码得到的实际 Token 序列完全一致；**不能重新编码一套不同的训练序列并将其当作 Full B 数据**。
- `sample_id` 唯一且一一对应；数据来源、协议签名和输入 Hash 与历史 Manifest 一致；无法验证则明确报告。

### 2. 字段边界与 Token 归属的正确性

这是本任务最关键、也最容易出现静默错误的环节。

建议建立两层归属：

- **字段区域**：`emotion_label`、`user_profile`、`response_text`、`memory_refs`、公共 JSON 结构和 EOS。用于回答各区域在完整监督中的实际份额。
- **画像细分**：`personality_traits`、`interests`、`style`，并区分 Gold 全空 / 非空样本。若能可靠细分，可再记录具体标签字符串、空数组相关 Token 与固定键/括号，但不是 A0 的必要前置。

优先使用**同一条完整 Chat Template 序列**及其精确 Token IDs，结合可验证的字符 Offset/序列边界映射；任何通过 Tokenizer offset 或渲染文本实现的映射，都必须再次核实所得 Token IDs 与原 `input_ids` 逐元素相同。JSON 值需要正确处理中文、多字节字符、引号转义、反斜杠以及字段文本重复等情况。

**禁止**直接分别 Tokenize `emotion_label`、`user_profile`、`response_text` 再把长度相加冒充它们在完整 Completion 中的真实 Token 长度。BPE/Tokenizer 可能跨越字段字符边界。

若单个 Token 同时覆盖两个区域，归入 `boundary_mixed` 并统计数量及比例；不能任意指派到其中一个字段。若 Offset/字符跨度无法严格验证，则报告 `alignment_blocked`，停止字段定量结论，不生成看似准确的结果。每个有效监督 Token 最终必须恰好归入某个字段或明确的结构、EOS、边界混合桶，核对分类总数与有效 Token 总数守恒。

### 3. 统计口径

至少输出：

- 有效 Train 行数、已核验行数、无法对齐行数；训练 Token 总数、有效监督 Token 总数。
- 字段区域的 Token `sum / mean / median / P90 / share`；公共结构、EOS 与 `boundary_mixed` 同样计数。
- Gold 三维全空 vs 至少一维非空两个群体的规模与字段 Token 分布。
- Gold 各画像维度非空与否的条件统计；如果进一步计算逐标签分组，必须注明多标签样本允许重叠，不把各标签组人数相加当作总体。
- 可选：按 `full_fit / trimmed_fit`、Completion 长度分层观察分布；与 T2 相关的结论仅记录观察，不在 A0 提出新的历史裁剪规则。

全量 CPU 扫描针对 16,192 条有效 SFT Train，避免加载完整 1.7B 模型。只读、流式处理优先，避免重复持久化大型数据。

## 五、GPU 诊断：冻结 Full B 的 Teacher-forced CE

### 1. 范围与资源

**只有 CPU Token 对齐通过后**，才尝试加载现有 Full B Adapter 进行有限的 GPU 前向测量。使用 WSL 项目 `.venv` 的 `Transformers + NF4/BF16 + PEFT`，不使用 vLLM。采用 `model.eval()`、`torch.no_grad()` 或 `torch.inference_mode()`；不构造优化器、不调用 `backward()`、不写模型文件，也不进行生成。加载模型时核验 Base / Adapter 身份；若 GPU 不可用、依赖不兼容或显存不足，保留 CPU 结果并标明 `gpu_blocked`，不要自动更改量化方式或迁移到其他后端。

建议默认选择 **128 条 Train 有效样本**做前向诊断，固定 Seed 42 和选择算法，并允许通过配置调整样本上限。抽样不以 Dev Gold 或某次预测好坏决定；应尽量覆盖画像 Gold 全空/非空、三维是否非空、短/长 Completion 和 `full_fit / trimmed_fit`。每种分层实际选中了多少条需要记录，不应声称 128 条代表完整 16,192 条的统计分布。可先以少量样本做 GPU smoke，确认无 OOM 后再运行有界前向；**不自动扩大到完整 Train / Dev**。

### 2. Cross-Entropy 的正确计算

模型的 Logits 维度为 `[B,T,V]`，位置 `t` 预测位置 `t+1` 的 Token。计算 unreduced CE 时要显式对齐：

```python
shift_logits = logits[:, :-1, :]
shift_labels = labels[:, 1:]
shift_fields = field_ids[:, 1:]

per_token_ce = torch.nn.functional.cross_entropy(
    shift_logits.float().reshape(-1, shift_logits.shape[-1]),
    shift_labels.reshape(-1),
    ignore_index=-100,
    reduction="none",
).reshape_as(shift_labels)
```

这是用于理解对齐的核心示意，并非要求复制到训练器。`field_ids` 由第四节的原始 Token 归属生成，与 `labels` 索引一致；Padding、Prompt 等无效位置必须被排除。**第一个 Completion Token 的 CE 是由前一个 Prompt Token 的 Logits 预测得来，不能遗漏。** EOS 单列；如果一个区域没有有效 Token，按 `not_applicable` 处理，不以 0 Loss 冒充观测值。

设各 Token CE 为 `ℓ_t`，各区域有效 Token 集合为 `S_f`，计算：

\[
L_f=\frac{\sum_{t\in S_f}\ell_t}{|S_f|}, \qquad
C_f=\frac{\sum_{t\in S_f}\ell_t}{\sum_{t\in S_{\mathrm{all}}}\ell_t}.
\]

- `L_f` 是该区域在固定样本上的**平均每 Token CE**；`C_f` 是它对本次标准 CE 总和的**算术贡献比例**，并不等于真实梯度贡献。
- 同时报告**全样本 Token 汇总（pooled / micro）**与**逐样本字段平均后再对样本求平均（macro by sample）**，两种口径不能混用。
- 若存在 `boundary_mixed`，其 Token 和 Loss 单独列出。不能让混合 Token 的损失消失在分母之外；字段 CE 应报告明确归属的覆盖率。
- Gold 全空 / 非空画像、三个画像维度及必要的分层分别统计；明确它们是条件子群，不能直接推断因果。

至少设置三个数值一致性检查：

1. 全部有效 Token 的 unreduced CE 按同一归一化口径汇总，应与模型原生 `output.loss` 在允许的数值误差范围内一致（同时记录 dtype 与误差容差）。若不一致，报告差异并检查 shift / Mask / reduction。
2. 所有区域连同 `boundary_mixed` 的 Token 数与 CE 总和必须与总体完全守恒（容许浮点舍入）。
3. 同一输入重复前向，在确定性设置下统计值应处于定义好的容差范围，不能把 `train()` 状态下含 Dropout 的随机结果误作固定模型测量。

8GB 显存下不建议一次汇集大 Batch Logits 或长期缓存完整 `[T,V]` 张量；可逐条前向、按需分块计算 CE，并及时释放引用。任何 CUDA OOM 都记录实际运行条件、失败规模，不重试成大规模循环。

> 此阶段测得的是**冻结 Full B 在 Train 上看到 Gold Completion 时的条件预测难度**。它不是自由生成准确率，不证明某一标签在实际预测时一定出现，也不是 Full B 训练 4,048 步过程中每一步的梯度历史。**A0 默认不计算梯度范数、不执行 backward。**

1. **环境与身份**：分支/Commit、dirty 状态、Python/torch/transformers/PEFT 版本、设备、Base/Adapter 与数据/Tokenizer 指纹；完整文件缺失时明确 `blocked`。

5. **讨论与限制**：哪些现象支持后续 A1 研究，哪些仍需数据质量审计、推理对照或梯度分析；**禁止将 Token/CE 占比表述成已证实的梯度冲突或比赛得分提升**。
6. **后续候选**：本任务形成时只提出 2–3 个待验证的 A1 Loss 设计方向，不批准或实现任何一个。后续状态已变更：用户于 2026-11-03 单独批准 E03-A1 Loss 对照，范围和门槛见[独立任务书](E0.3-A1_Loss对照实验任务书.md)。

聚合统计的比率必须附分子、分母；空值、缺失与未运行不能写成 0。Train 的 Teacher-forced CE 不与历史 SFT Dev Loss 或自由生成质量分数直接作同分母比较。
