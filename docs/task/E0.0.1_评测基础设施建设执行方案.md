## 二、E00.1 目标架构及数据流

```text
D0.3: data/processed/v1/dev.jsonl + outputs/data_pipeline/v1/manifest.json
    │
    │ 校验 D0.3 输入 hash、来源、样本数、唯一 sample_id
    ▼
src/evaluation/prepare_dev.py
    ├── inference_input.jsonl   [id, history]                  → 模型允许读取
    ├── references.jsonl        [eval_id, sample_id, target]  → 只给评测器
    ├── id_map.jsonl            [eval_id, sample_id, source]  → 对齐/追踪
    ├── smoke_*                 固定种子的代表性子集
    └── manifest.json           文件/配置/来源 hash 与行数
                │
                ▼
participant/run_inference.py (唯一现有生成实现；增加可选诊断输出)
    ├── submission.jsonl         官方格式；标准化预测
    ├── performance_report.json  官方约定的性能报告
    └── raw_predictions.jsonl    仅在显式开启 E00 诊断时写入；原始文本与状态
                │
                ▼
src/evaluation/score.py + metrics.py
    ├── 校验三份记录的 ID 集合/唯一性/输入指纹一致；拒绝目标泄漏
    ├── 比对 submission 与 references：情绪/画像/回复本地指标
    ├── 比对 raw_predictions：原始 JSON、字段、标签、结束原因等诊断
    └── metrics.json + report.md + case_errors.jsonl
```

**关键设计原则**：`participant` 是唯一生成与比赛提交实现；`src/evaluation` 是只读评测层。不要在 `src/evaluation` 复制 `generate_transformers_sample`、API 请求处理、`parse_prediction`、P0/F2/T1 或整个官方 runner。

## 四、模块任务与实现要求

### A. Dev 输入适配与数据泄漏防护（`prepare_dev.py`）

#### A1. 输入与合法性

从 `data/processed/v1/dev.jsonl` **只读**读取 D0.3 规范化记录，并核对 `outputs/data_pipeline/v1/manifest.json` 记载的输入文件指纹、数量及来源。正式数据准备必须满足：

- Dev 正好 `1,833` 条，所有 `sample_id` 唯一；`history` 非空，最后一条为当前 `user` 消息，消息角色与内容符合当前 D0.3 契约。
- 每条 `target` 满足训练 Schema；`source.split` 仍可能是 `train`（Dev 来自原始 Train），**不能把它误判成训练集泄漏**。应结合规范化文件划分和 D0.3 Manifest 判定分区。
- 不从 `data/processed/sft/v1/dev.jsonl` 读取：它只包含 1,821 条 SFT 可用监督记录。
- 使用原始 D0.3 行顺序建立**确定性**本地评测 ID：第 `i` 条（从 1 起）映射为 `test_{i:06d}_t0`。这是**本地构造的符合官方 Schema 的评测 ID**，不是官方秘密测试 ID；`id_map.jsonl` 明确保存原始 `sample_id`。同一输入多次执行 ID 与输出字节一致；源记录有变更时 Manifest 必须改变。
- 推理输入每行仅保留 `{ "id": ..., "history": [...] }`；不携带 `target`、标签、source、任何答案字段。Reference/Map 路径严格独立；在评测器开始前进行结构和禁止字段断言。
- 三份输出不得覆盖 D0.3 文件。使用同目录临时文件与原子替换避免部分写入被误用；Manifest 最后写入，包含原始输入 SHA-256、配置、输出各文件 hash/行数、Git commit（能读取时）。

建议格式（仅示意，内容不是比赛样本）：

```json
{"id":"test_000001_t0","history":[{"role":"user","content":"最近压力有点大。"}]}
```

```json
{"eval_id":"test_000001_t0","sample_id":"train:conv_example:pp0","target":{"emotion_label":"anxiety","user_profile":{"personality_traits":[],"interests":[],"style":[]},"response_text":"听起来你最近承受不少压力。","memory_refs":[]}}
```

注意：D0.3 的原始 target 可能有**非空 `memory_refs`**，Reference 必须如实保留；A0 推理固定输出 `[]`，目前不将 `memory_refs` 作为自行定义的模型能力指标，不能为了让评测一致而覆写真值。

#### A2. 小样本集与可追踪选择

从完整 Dev 确定性派生 E00.2 将使用的 `smoke_input.jsonl`、`smoke_references.jsonl`、`smoke_id_map.jsonl` 及选样说明。推荐 12–24 条，覆盖尽可能多的情绪类别、空与非空画像、长与短历史、Unicode/特殊文本；如果目标数据没有某些特殊标记，应如实记录“未覆盖”，不要合成伪装为真实 Dev 的样本。

抽样过程允许使用 `target` 决定代表性，但是派生的 `smoke_input.jsonl` 仍不得包含真值；同一 `seed` 和同一 Dev Manifest 必须获得一致结果。不得把这个小样本的任何结果称为正式模型质量基线，也不强制覆盖全部 16 类（极稀有类别可能样本不足）。

提供独立 CLI：

```bash
python -m src.evaluation.prepare_dev --config configs/evaluation/e00.yaml
```

实际 CLI 参数可按仓库已有配置风格设计，但必须有 `--config`、非零退出码、输出文件位置和清晰错误原因；**缺少真实 Dev 时只报缺失，不暗中生成替代数据**。

### B. 推理入口最小扩展与真实模型加载配置

#### B1. 增加 opt-in 原始结果追踪

对 `participant/run_inference.py` 做局部扩展，让开发评测可指定独立原始记录路径，例如 `EVALUATION_RAW_OUTPUT_PATH`（环境变量名称可以小幅调整，但必须明确、测试并文档化）。默认**关闭**，这样官方 `start.sh`、原有两个提交文件和既有调用方完全不变。

在一次模型生成中保留以下**同一条**结果，不允许为了获取原始 JSON 再推理一次：

| 字段 | 记录内容 |
|---|---|
| `id` | 本次推理样本 ID |
| `raw_text` | 未执行 `extract_object`、`recover_response_text`、`normalize_prediction` 前的原始解码字符串；若根本未生成，使用 `null` |
| `status` | 现有 `success`、`parse_failure`、`invalid_label`、`prompt_floor_exceeds_cap` 等，沿用现有含义 |
| `prompt_tokens`、`generated_tokens` | 客户端真实 Prompt 长度与生成 Token 数；API 返回数量缺失时不能填猜测值 |
| `stop_reason` | EOS / `max_new_tokens` / 服务端 finish reason / 未生成等，无法区分时明确记录未知 |
| `latency_ms`、`removed_history_messages` | 同轮耗时与裁剪数量 |
| `backend` | Transformers / OpenAI-compatible；模型与量化事实由运行配置和性能报告追踪 |

原始诊断中可以加入少量直接可测的标记，但**严格 JSON 合法性**必须由评测器统一计算，不要在 runner 中另写一套不同定义的 Schema 判定。

- 原始输出可能包含完整用户对话内容，所有诊断文件留在 `outputs/`，不得 Git 提交或写入跟踪文档。
- 原始日志和提交文件须有完全相同、唯一的 ID 集合；未生成的记录也要记状态，不能悄悄消失。
- 正式比赛不依赖或引用这个可选文件；未设置选项时，保留现有输出行为。
- 避免可选日志路径与提交两个文件冲突；不覆盖已有不属于本轮的文件。

#### B2. 正确计时

现有 Transformers 路径在 `elapsed_ms` **之后**才同步 CUDA，可能遗漏异步 GPU 操作。修改为：

```text
先同步 GPU（排除上一条尚未完成工作）
started = perf_counter()
    Tokenization / Generate / Decode / Parse / Schema（按现有实际代码范围）
同步 GPU（等待本条 GPU 工作真正完成）
elapsed_ms = (perf_counter() - started) * 1000
```

异常时也不能误记已完成的 GPU 时间。对 Mock 与 CPU 运行验证同步调用次序。明确 `backend_report.timing_scope` 中模型加载、模型初始化、首次预热是否排除；不能把 E00.1 的 Mock 耗时报告成 GPU 速度，也不能把 Transformers 和 vLLM 两种计时范围不一致的数值直接比较。

现有比赛报告仅统计前 `performance_rounds=100` 条；小样本 `rounds<100` 时 `complete=false` 是预期，不是本阶段失败。额外的全样本延迟诊断可在 E00 报告中汇总，但不得改动官方固定字段语义。

#### B3. NF4/ BF16 加载配置的最低支持

采用**显式可选**的 NF4 配置，且未开启时兼容当前模型加载行为。Transformers 侧优先使用官方 `BitsAndBytesConfig`，最小参数包含：

```text
load_in_4bit = True
bnb_4bit_quant_type = "nf4"
bnb_4bit_compute_dtype = torch.bfloat16
bnb_4bit_use_double_quant = <实验配置固定的布尔值>
```

- 不为了 E00 修改基础 Qwen 权重文件；不把 LoRA 合并逻辑、训练器或 vLLM 复杂配置加入此阶段。
- 当前 `participant/configs/inference_config.json` 默认 `backend=transformers`、`model_path=./model`、`P=1280`、`G=1200`、`K=null`。保留候选性质，不把 `K` 写成已验证；不要在未实测的条件下宣称 BF16/NF4 已成功加载。
- 记录基础模型标识、**实际权重来源/修订版本或本地权重文件指纹**、Tokenizer revision/指纹、NF4 与 double-quant 配置、Compute dtype。不要将 Tokenizer 的 revision 自动当作本地**模型权重**的 revision。
- 使用可替换的构造函数 / Mock 验证量化配置参数和默认分支；不以本阶段加载真实 Qwen 作为通过条件。
- E01 正式比较时应复用这个推理配置机制，只新增 Adapter。NF4 不是强制的最终 vLLM 部署格式。

### C. 评测器：输入、指标及严格定义（`metrics.py`、`score.py`）

#### C1. 评测输入一致性

`score` 读取由同一 Manifest 生成的 `references.jsonl`、`submission.jsonl`，可选读取 `raw_predictions.jsonl`，依次断言：

- 对比的 ID 唯一；Submission 与 Reference 的**完整集合**一致（不能因为部分失败而改变分母）。行顺序可以不同，但必须按 ID 对齐；缺失、重复、多出均报错，不能静默 inner join。
- Reference 中的 `sample_id` 与 `id_map` 对应；关联 Manifest 的文件指纹。若预测文件来自不同模型/参数/数据输入，不允许仅凭行数相同就当成同一实验。
- 提交 Schema 的每个输出均可校验；若不合格，指出 ID 并**拒绝把它当有效的正式提交预测**，同时可在异常报告保留诊断，不要无提示剔除。
- `target` 仅在 score 端读取；推理输入和 raw 诊断文件不包含真值。`sample_id` 和真值不得通过 HTTP/API 或模型 Prompt 泄漏。
- 分层指标使用 D0.3 的真实正确标签进行分组，不能用模型预测标签来定义真值类别。

#### C2. 情绪识别（16 类）

计算：

- 主指标 `accuracy = 正确数 / 1833`（或本次合成 / smoke 的实际评测集合大小）。提交里的空情绪 `""`、非法/解析失败导致的空值都算错误，不得删除或把空值作为第 17 个正常情绪。
- `macro_f1`（固定对官方 16 类取平均）、16 类各自的 support / precision / recall / F1、16×16 混淆矩阵。**若需要展示预测失败**，另单独汇总 `invalid/empty_prediction` 列，不要把这个新列当正常类别参与 Macro-F1；支持 16×17 的诊断矩阵或独立失败计数。
- `zero_division=0`，明确记录；样本量很少的类别提示解释限制。
- 单独的**简单规则参考基线**：仅从 D0.3 Train 统计多数情绪，并在 Dev 上测准确率；不可看 Dev 真值决定多数类。此基线与 E00 模型结果分开记录，不为其捏造回复质量和延迟。

#### C3. 用户画像（3 维、33 标签）

固定合法标签定义来自现有官方 Schema / P0，禁止另造一份可能漂移的常量枚举。

对 `personality_traits`、`interests`、`style` 分别计算：

- **Exact Match**：集合完全相等的样本占比，双方都空视为完全匹配；再给一个三个维度同时 Exact Match 的整体比率。
- Micro Precision/Recall/F1：以该维度所有样本×标签二值判断的 TP/FP/FN 累计计算；Macro-F1：固定枚举中的每个标签计算 F1 后取平均；整体 33 标签可另给 Micro/Macro-F1。
- `gold_empty_rate`、`pred_empty_rate`、平均标签数、标签级 support / TP / FP / FN。避免因很多空集合而将单独一个 F1 当作画像完整质量。
- 标准化输出已剔除非法标签的情况，以 Raw 诊断和字段失败率报告，绝不能把“被修复为空”的结果当作模型原始正确预测。

官方画像具体计分口径尚未核实。所有字段命名为 `local_*` 或报告注明 `local_proxy`，不自动生成赛事 15 分的估算。

#### C4. 情感回复（中文文本）

E00.1 必须有稳定且可单测的本地指标**定义与计算入口**：

1. `BLEU-4`：用经过固定版本的标准实现计算**Corpus BLEU-4**（中文采用明确且固定的字符级分词约定，比如 SacreBLEU `tokenize="char"`），保留原参考文本和预测文本；不要平均句子级 BLEU 后声称是 Corpus BLEU。零长度输出作为零质量参与整体评测，不筛掉。
2. `ROUGE-L`：固定字符级（Unicode 文本、明确空白字符处理）最长公共子序列 LCS 实现，输出逐样本 F1 的宏平均，明确不声称与未知官方分词方式相同。可使用成熟依赖，也可实现小而明确的 LCS 计算；避免另建复杂 NLP 管线。
3. `BERTScore`：设计**可选且显式**的离线评分入口，指定本地评分模型路径/具体 revision、评分实现版本和语言等元数据；只有模型确实可用时执行，未缓存则返回 `status: not_run` 和明确原因，指标值为 `null`。E00.1 不下载大型模型、不因无法实际计算 BERTScore 而捏造分数。使用确定性 stub / mock 测试接口及元数据保留。
4. `response_text` 保持原始参考文字，不用额外清洗训练集；必要的文本评分分词/空白处理单独写明。原始模型生成、标准化提交的文本不可混淆。空回复比例、参考/预测长度分布是必要诊断。

如需新增依赖，放 `requirements-eval.txt` 并锁定兼容版本；不要直接重写项目已有 `requirements.txt` 的整份锁定依赖，也不要要求官方镜像安装离线评分模型依赖。运行前检查当前 venv 包与 Python 版本兼容性。

#### C5. 原始输出合规与失败诊断

务必**分开**计算下列事实：

| 诊断指标 | 严格定义 |
|---|---|
| `raw_json_parse_rate` | 将 `raw_text` 整体 `json.loads`（允许 JSON 前后空白）得到**唯一对象**的比例；嵌在代码围栏或夹杂额外解释文本的不算原始合格 |
| `raw_schema_valid_rate` | 上述严格 JSON 对象满足 A0 Completion 约定字段和字段类型、官方合法枚举、`memory_refs=[]` 的比例；不得沿用提交 Schema 的 `id` 要求 |
| `valid_emotion_rate` | 原始生成中情绪字段值属于 16 类的比例 |
| `valid_profile_rate` | 原始画像三维字段齐全、集合标签合法且无重复的比例 |
| `nonempty_response_rate` | 原始回复字段是非空白字符串的比例 |
| `submission_schema_valid_rate` | 最终 `submission.jsonl` 所有行符合官方提交 Schema 的比例（允许 `""` 失败哨兵） |
| `generation_stop_counts` | EOS、生成上限、API finish_reason、未生成、未知原因等归类；不能凭生成数不足 G 就猜 EOS |
| `error_case_counts` | 严格 JSON 失败、缺字段、非法枚举、空回复、历史超 P、生成达到 G 上限、协议等价失败等，可多标签计数，且定义清楚 |

`participant.parse_prediction` 当前可从非严格原文抽取 JSON/救回回复；**这是提交容错行为，不是原始格式正确的证明**。如果原始文本是 `{...}` 外加多余说明，`raw_json_parse_rate` 必须算失败，即使最终提交 Schema 合格。JSON 语法合法与任务回复非空也是两层不同结果。

`metrics.json` 中必须有 `sample_count`、分项分母、实验 ID、输入/预测哈希、`metrics_scope=local_proxy`；默认不计算“官方总分”。原始文本保存到 JSONL；错误报告只保留必要定位 ID/失败原因，避免同一份长对话在多个产物反复复制。
