## 二、P0：把“快评对照工具”真正变成“候选快速筛选工具”

### 已核实的缺口

`scripts/e03_profile_fast_eval.py` 当前只有 `parse-raw`、`audit-source`、`gpu-compare` 三种模式。`gpu-compare` 在每个样本上**同时执行完整生成和早停生成**；因此 82.19% 是“早停那一次生成相对于完整生成”的效率增益，并非现有 CLI 完成整个候选评测所节省的比例。

此外，`src/evaluation/profile_fast_eval.py::select_unique_conversation_samples` 对样本数设有 `count<=32` 的验收上限。这是合理的 Smoke 限制，但目前不能直接拿来评估 224 点短程候选。A3 的 `scripts/e03_a3_short_evaluate.py` 则仍使用完整生成，未复用快速路径。

### 修改要求

1. **保留已有 `gpu-compare` 行为与身份记录**；增加独立、显式的 `gpu-fast-only`（名称可按仓库风格确定）研究模式。该模式每条样本只生成到 `user_profile` 完整闭合，不再次运行完整生成，不生成 `response_text`，更不能写为正式 Submission。
2. 分开配置“16–32 点机制验收模式”与“固定开发集候选筛选模式”。后者允许预先冻结的 224 点或其他明确 ID 列表，但在启动前先检查整段会话边界、ID SHA、target-free 输入、P0/F2/T1、Tokenizer、Base+Adapter 身份和预算；不允许因为调参结果而变动成员。
3. 在早停独立模式中复用既有 `ProfilePrefixStopper` 和 `profile_metrics`。所有 `invalid` / `incomplete` / `unsupported_order` / `budget_exhausted` 案例都必须进入**固定分母及失败统计**；禁止只对成功解析的少数样本报告一个看起来较高的 F1。可同时报告 `valid_only` 诊断，但不能用它代替候选筛选的主指标。
4. 对比不同 Adapter 时，冻结完整样本集合、Greedy、P0/F2/T1、模型配置、最大生成预算和评分口径。结果 Manifest 必须区分 Base、Adapter、实验版本、代码与数据哈希。旧 E01-B Adapter 不许被覆盖。
5. CPU 测试首先覆盖解析器失败路径、指标固定分母、历史映射错误、候选身份不一致和预算终止。**不自动运行 GPU**；正式启用前另行获批少量新候选配对检查。已有 16/16 GPU 验收保留，不必再次从头验证同一模型。

### 验收条件

- `gpu-fast-only` 路径无完整 `model.generate` 调用；对于每个样本仅执行一次候选生成。
- CPU 测试证明：非法/提前 EOS/预算中止不会被静默算作正确标签，也不会从总分母凭空消失。
- 使用明确的 Run ID 与不可变快照；中断能输出 `incomplete` / `budget_exhausted`，不能冒充 `passed`。
- 仅在有单独 GPU 授权时，将已有完整推理基线与新早停路径进行固定小样本一致性检查。最终模型选择仍须跑完整 JSON 和多指标评测。

## 三、P1：修正状态判定与未来实验配置的限制

### 1. CLI 返回值避免被误认成功

`e03_profile_fast_eval.py::main` 目前把 `not_adopted`、`budget_exhausted`、`blocked_environment` 也作为退出码 0。对于报告型命令这可能是有意设计，但自动调度时容易被误解为测试通过。

- 让调用方能够显式使用严格模式（例如 `--require-passed`）使以上状态返回非零，默认诊断兼容行为可保留。
- 对全部状态、退出码和输出 JSON 增加合成回归；文档说明“命令顺利生成诊断报告”和“性能门槛通过”不是一回事。

### 2. 未来训练规格区分两种初始化路线

`src/training/experiment_spec.py` 当前只允许 `initialization.source=base` 且禁止 `adapter_path`；这适合**改变 LoRA rank 后从 Base 创建独立 Adapter**，但不能直接描述“保留相同 rank、从 E01-B Full Adapter 做短程续训”的 Replay/BCE 研究。A3 已另外实现过 Full B 初始化，因此继续新增实验时容易产生配置语义不一致。

- 仅在 CPU 规格层设计两个明确互斥的初始化方式：`new_adapter_from_base`（适用 Rank 对照）与 `new_run_from_existing_adapter`（适用同 rank 续训、独立 optimizer、新 Run）。后一种必须核对 Base/Adapter SHA、rank、target modules、量化和参数 dtype，禁止跨实验恢复旧优化器/Checkpoint。
- **本轮不增加 GPU Trainer**，更不授权 BCE 辅助头或高 rank 实训。仅写规格与合成测试，防止后续开发误解。
