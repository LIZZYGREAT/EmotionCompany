# EmotionCompany｜E00.2-D 单字段情绪识别诊断：Codex 执行方案

> **任务性质**：E00.2 之后的独立、一次性诊断实验；不是 E00.3 全量 Dev 评测，也不是 E01 SFT。
>
> **目标仓库/分支**：`LIZZYGREAT/EmotionCompany` / `e00-1-evaluation-infrastructure`。方案编写时 HEAD 为 `d29765b176af5ec55e0c256d791a6cf05fee1b02`；实施时先核对本地 HEAD 与工作区状态。
>
> **核心问题**：在真实 Qwen3-1.7B、相同 20 条 D0.3 Dev Smoke 和相同对话历史条件下，去掉 A0 的画像与回复联合生成要求，仅预测一个情绪标签，模型能否产生更多有效且正确的分类结果？
>
> **总原则**：复用原有权重和输入机制；新实验独立标识、独立 Prompt、独立输出；**不修改 A0，不污染旧分数，不把诊断分数当赛事正式基线**。

- 已有只读证据：`docs/experiments/E00.2_错误归因与后续决策.md`、`outputs/evaluation/e00_2/E00.2-20261026-220635/` 和 `outputs/evaluation/e00_2/diagnostics/E00.2-20261026-220635/`。

### 2. 本轮只做什么

1. 新增一个**单字段、无 JSON 包装**的情绪识别诊断 Prompt（`Pdiag-E1`）。
2. 复用 E00.2 的 20 条 Smoke、同一模型、Greedy 和 **同一被选中的对话历史**，跑 **一组**真实推理。
3. 以原始生成文本直接判定是否恰好为 16 个官方枚举之一，计算合法率、Accuracy、16 类 Macro-F1、混淆与失败分组。
4. 与归档的 A0 Greedy 按同一 ID 做**描述性配对**；给出下一步选择，不直接展开更多实验。

**不做**：新训练、LoRA、100/1,833 条推理、Sampling 调参、P0 改写、D0.3 重新划分、Val 测分、vLLM、Docker、BERTScore、强制 JSON/枚举解码、任意自动标签映射、人工改写模型输出。

## 二、一个重要实验设计：必须保持历史内容可比

仅固定 `P=1280` 并不足以保证两次模型真正看到相同的对话历史。系统 Prompt 从 P0 变成更短的 `Pdiag-E1` 后，如果直接重新执行 T1，可能多保留一些旧消息；届时改善无法分辨来自任务简化还是历史增加。

**本轮要求采用“固定 A0 历史子集”策略：**

1. 对 20 条 `smoke_input.jsonl`，先用**原版 P0 + 冻结 Tokenizer + T1**重新计算 E00.2 Greedy 的 `selected_history`。
2. 逐 ID 对照归档 `performance_report.json` 的 `original_history_messages`、`retained_history_messages`、`removed_history_messages` 和 `client_prompt_tokens`；与已保存的 D0.4.2 预算记录一致。任一不一致则停止，不能使用一个重新抽取的近似历史。
3. **只把已确认的这段 `selected_history`**交给 `build_messages(selected_history, Pdiag-E1)` 和 `encode_inference_prompt(tokenizer, messages)`；此处**不允许**再次根据更短 Prompt 扩充旧历史。
4. 校验新诊断 Prompt 的 Token 数 `<=1280`。理论上新系统说明更短，但仍须逐条实测；超限则报告并停下，不要隐式改变保留的历史。
5. 记录每条原 A0 Prompt Token 数、新 Prompt Token 数和保留历史消息数。**两种 Prompt 不可能具有相同的 Token IDs；固定的是模型权重、输入样本、历史消息、Chat Template、推理设备和 Greedy 解码。**

此设计让对照更可解释，但仍不是严格的“只改变一个参数”：任务说明和输出形式都发生了变化，因此不能把分类提升直接归因于某一个单独因素。

### A. 单字段 Prompt `Pdiag-E1`

参考文本如下；实际落盘后冻结其 SHA-256，并与模型运行报告绑定：

```text
你负责识别最后一条用户消息表达的主要情绪。结合已有对话历史，在以下情绪标签中恰好选择一个：
joy, gratitude, relaxed, care, pride, neutral, surprise, mixed, sadness, loneliness, anxiety, anger, fear, disgust, shame, helplessness

只输出一个英文标签本身，不要 JSON、引号、代码围栏、解释或任何其他内容。
```

- 标签枚举和顺序**从官方提交 Schema 校验**；Prompt 作为独立版本，不覆盖 `configs/prompts/p0.txt`。
- 不附带参考答案、不添加示例 Gold，不插入样本 `id`。
- 严格使用 F2 原生 `system/user/assistant` 消息和 `enable_thinking=False`；依旧保护历史 assistant 文本中的字面 `</think>`。
- **不调用** A0 四字段 `load_runtime_protocol()`/`parse_prediction()` 来解释单标签输出，因为它们为 P0/A0 JSON 契约服务；单标签解析作为诊断代码的简单专用函数即可。

### B. 诊断运行配置

新 YAML 仅保存本轮必要差异与引用，避免复制两份完整的 P0/Tokenizer 设置：

```yaml
experiment_id: E00.2-D
prompt_version: Pdiag-E1
model_reference: Qwen/Qwen3-1.7B
model_path: participant/model
baseline_run_id: E00.2-20261026-220635
input_path: outputs/evaluation/e00_1/dev_adapter_v2/smoke_input.jsonl
references_path: outputs/evaluation/e00_1/dev_adapter_v2/smoke_references.jsonl
history_policy: exact_E00.2_A0_greedy_selected_history
prompt_budget: 1280
generation:
  do_sample: false
  max_new_tokens: 64
  # 不要为 Greedy 强行传入无意义的 temperature/top_p
```

`G_diag=64` 是诊断用生成上限，**不是对正式 A0 G=1200 的修改**；记录 EOS / 达上限 / 生成失败。如果多条样本触及 64 Token 上限，本轮不能贸然将失败归因为分类能力，应先报告这个混杂因素，追加试验需另行决策。也不比较本轮和 A0 的延迟优劣（G、Prompt、输出任务不同）。

## 四、实施步骤

### D1：仓库及归档预检（不写旧产物）

- `git status --short`、`git log -1 --oneline`；先检查是否存在未提交的他人改动。
- 读取 `AGENTS.md`、`docs/competition/赛事文件边界与运行契约.md`；保护官方 Schema、数据、`participant/start.sh` 及 P0/F2/T1。
- 确认 20 条 Smoke ID、文件 SHA、E00.2 Greedy 的 Raw/Performance/权重 SHA 和诊断报告一致。只从 Manifest 定位归档，不猜测路径。
- 检查 `participant/model` 指向冻结 snapshot；优先复用已经归档并核对过的权重身份。不下载、不覆盖、不重建模型目录。
- 在**本机 WSL**验证 `torch.cuda.is_available()`。Codex 隔离环境 GPU 不可用时，只交付代码、Mock 测试和本地运行命令，标记 `BLOCKED_IN_CODEX_ENV`，不得编造真实分数。

### D2：复用现有推理基础设施，添加单字段入口

目标：实现一个**单一职责、小体量脚本**，避免再次出现千行级诊断器。

- 优先复用 `participant.run_inference` 的 `model_path`、`load_runtime_tokenizer`、`build_quantization_config`、`require_cuda_for_quantization`、`inspect_quantization_runtime`、`_weight_identity`、`generate_transformers_sample`、`synchronize` 等已验证函数。
- 模型加载只需针对本轮 `Qwen3-1.7B` 调用 Transformers `AutoModelForCausalLM.from_pretrained(..., local_files_only=True, trust_remote_code=False, device_map='auto', quantization_config=...)`；不要重建第二套通用推理框架。加载后执行真实 NF4/BF16/CUDA/无 offload 检查，实际权重指纹须与归档一致。
- 复用 `src.shared.prompting` 的 `build_messages`、`select_recent_complete_suffix`、`encode_inference_prompt`，按第二节固定历史。
- 使用 Greedy `do_sample=False`，生成的 Completion 仅解码新 Token；与 A0 一致使用同一 Tokenizer 的 `skip_special_tokens=True`；记录 `stop_reason` / token 数 / CUDA 异常。
- **推理入口只能读不含标签的 Smoke input 和已有 A0 性能元数据**；跑模型时不得读取 References/Gold。评分阶段才读取 References。
- 每条样本保留原始生成字符串到仅本地的 `raw_emotion_predictions.jsonl`，不将其拼进官方 `submission.jsonl`，也不能改写旧 Raw 文件。
- 对中断或单条错误：保留 ID 和失败标记，不用 Gold 补值；确保最终 N=20，否则整个验收不得 PASS。
- 尽量实现为一个 CLI，提供 `run`、`score` 两个明确子命令（便于确保生成阶段不接触 Gold）；若拆分入口更简洁，也可拆分，但避免过度封装。

### D3：单字段的严格评分（不得依赖 A0 JSON 修复器）

对每个 Completion：

1. `raw_text` 必须是字符串；仅允许去掉首尾空白后恰好与官方 16 个标签之一一致，才算**严格合法单字段标签**。
2. `raw_text` 包含解释、其他标点、引号、多个标签、JSON、代码围栏或非法同义词，均记**原始格式无效**，不得偷偷提取内部标签、翻译中文标签或做后验映射。
3. 所有无效输出均算 Emotion 错误，保留在总分母中；不能只对有效输出算 Accuracy。
4. 计算：`strict_label_valid_count / 20`、`correct_count / 20`、`correct_count / valid_count`（仅诊断，分母为 0 时输出 `null`）、固定 16 类 Macro-F1、逐类 TP/FP/FN/Support、16 类混淆矩阵加无效输出诊断列、预测标签直方图。
5. 与归档 A0 Greedy 按 ID 对齐，记录旧/新标签是否存在、旧/新是否正确以及从「缺失/错误」到「合法/正确」的转移；**不能把 A0 Sampling 与本轮 Greedy 当作单变量对照**。
6. 使用 Train 侧预先确定的多数类 `anxiety` 作为解释性参照：现有 E00.1 记录它在同一 20 条 Smoke 上为 `2/20=10%`；评测器也应从来源数据/归档核验，而不是从 Dev Gold 中挑选最优多数类。
7. 额外按**原 A0 历史是否裁剪**分组，记录 4 条/16 条上的合法率、正确数；分组沿用既有 A0 历史选择，避免以 Pdiag 不同 Prompt 长度重新定义裁剪类别。
8. 输出 `per_case.jsonl` 仅包含 ID、Gold 标签、预测标签或无效状态、错误类型、截断标记、正确与否，**不要把原始对话或回复正文写入版本化报告**。

关于 Macro-F1：继续使用**固定官方 16 类**，缺少支持的类别按现有 E00 口径处理，不因样本少而换成只计有支持类别的指标。20 条为分层 Smoke，不是总体分布样本；报告须同时列出正确条数和各类 support，避免过度解释微小差异。

### D4：结果解释与是否继续的决策

生成一个简明报告，不提前写结论，至少包含：

| 要回答的问题 | 必需证据 |
|---|---|
| 单标签是否能稳定输出？ | 严格合法标签数、格式错误类型、EOS/上限停止分布 |
| 合法以后是否真的会分类？ | 全样本 Accuracy、合法子集准确率、16 类 Macro-F1、预测分布 |
| 相比历史 A0 发生了什么？ | 同 20 ID 的配对转移、相同历史确认、模型权重指纹一致 |
| P=1280 是否解释差异？ | 旧 A0 历史裁剪 4/20 的独立统计及子组正确数 |
| 是否可以声称某方案优于另一方案？ | 明确说明小样本、不确定性、Prompt/输出契约已改变，不作因果或正式模型排名结论 |

**分支判断（仅产出建议，不自动启动下一阶段）：**

- **单标签合法率与正确率都明显提高**：提示联合任务/格式约束可能影响有效输出，但无法区分“少了画像/回复”“不再要求 JSON”“Prompt 文案改变”三个因素；如有必要，再单独设计只含 `emotion_label` 的**最小 JSON** 诊断，不得把其结果混进本次 A0 成绩。
- **合法率提高，但分类仍很差**：说明格式问题被减轻，而主要分类困难仍在；后续优先考虑标签语义、标签支持与 E01 的 SFT，而不是继续修改现有 Parser。
- **合法率仍然很低**：检查真实 Raw、EOS/预算、Chat Template 和指令遵循；只有发现可复现的实现错误才修改代码。
- **结果差异仅一两条**：结论标记 `inconclusive_small_n`；不要声称解码、Prompt 或训练路线已经验证优越。
