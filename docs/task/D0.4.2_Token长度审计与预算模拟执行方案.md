## 一、目标与边界

### 1. 任务目标

将 D0.3 的规范化数据转换成**可用 Qwen3 Tokenizer 精确测量的输入输出序列**，并在不改变原始数据、不训练模型的前提下，对候选 Token 预算模拟历史保留情况，形成后续选择训练长度与推理长度所需要的证据。

本阶段须回答：

1. P0 系统指令、多轮历史、完整 JSON 答案各占多少 Token，整体长度分布如何？
2. 1024、2048、4096 Token 训练长度下，不截断、按 T1 截断、仍无法容纳的样本分别有多少？
3. 在不同固定 Prompt 上限下，裁掉了多少历史消息及原始文本，哪些标签/画像样本受影响？
4. 哪些超长样本无法同时保留当前用户消息和完整答案？其原因是什么？
5. 后续 D0.4.3 及 E00/E01 应采用哪些**待实测验证**的长度候选，而非现在冻结单一数值？

### 2. 明确不做

- 不训练 Qwen、不加载完整 1.7B 模型、不执行反向传播或显存基准测试。
- 不生成最终 `labels`/Loss Mask、Padding 张量或最终 SFT 数据缓存；这些属于 D0.4.3。
- 不修改 D0.3 `train.jsonl`、`dev.jsonl`、`val.jsonl`，不改清洗/去重/数据划分，不删除超长样本。
- 不决定最终 `max_train_seq_length`、`max_prompt_tokens`、`max_new_tokens`；只评估候选。
- 不实现 P1 详细 Prompt，不执行模型效果对照，不在此阶段改写官方 `participant/` 提交接口。
- 不进行自动内容改写、历史摘要、语义压缩、对长回答进行静默裁剪。

## 三、D0.4.1 已确认协议的最小落地（D0.4.2 前置工作）

**原因：** D0.4.2 必须测量最终真正会使用的 Prompt；当前仓库还没有统一 P0 / F2 构造模块。因此先建立唯一的协议来源，避免在长度统计脚本里硬编码一个临时 Prompt。

### 1. 新增协议文件与模块

建议新增：

```text
configs/prompts/p0.txt           # 唯一权威 P0 提示词文本
src/shared/__init__.py
src/shared/prompting.py         # 消息构造、目标 JSON 序列化与 Chat Template 编码
```

P0 采用下述内容为初始冻结文本（必要的换行与标签展开可做规范化，但不得自行增加 P1 式长篇规则；如作文字调整，记录版本与 SHA-256）：

```text
你是一名中文情感陪伴对话助手。请根据提供的历史对话，完成以下任务：
1. 判断最后一条用户消息表达的主要情绪。
2. 根据截至当前的对话证据，推断用户的性格特征、兴趣和交流风格。
3. 为最后一条用户消息生成自然、贴合上下文的中文回复。

合法情绪标签（恰好选择一个）：
joy, gratitude, relaxed, care, pride, neutral, surprise, mixed, sadness, loneliness, anxiety, anger, fear, disgust, shame, helplessness

合法画像标签（各维度可选择零个或多个）：
personality_traits: extroverted, introverted, open, conservative, high_conscientiousness, casual, agreeable, assertive, emotionally_stable, sensitive
interests: study_exam, programming_technology, reading_writing, film_animation, music, games, sports_fitness, travel_outdoor, pets, social, career_development, art_design
style: brief, detailed, colloquial, formal, direct, indirect, humorous, rational, high_emotional_expression, low_emotional_expression, emoji_user

输出要求：
- 情绪和画像只能使用上述标签。
- 画像只输出有对话证据支持的标签；某维度证据不足时使用空数组。
- 回复应理解当前用户的情绪和诉求，保持自然、恰当，不输出无关说明。
- memory_refs 固定输出空数组 []。
- 只输出一个合法 JSON 对象，字段依次为 emotion_label、user_profile、response_text、memory_refs，不输出 Markdown 或额外文字。
```

说明：必须对照官方 Schema 校验标签枚举集合。**官方 Schema 是合法性唯一依据**；若其与示例存在差异，停止并报告，不静默变更候选集合。

### 2. 构造接口与序列化规则

`prompting.py` 负责且只负责：

```python
build_messages(history, prompt_text) -> list[dict]
serialize_completion(target, official_schema) -> str
encode_inference_prompt(tokenizer, messages) -> list[int]
encode_full_training_sequence(tokenizer, messages, completion_json) -> list[int]
```

行为要求：

- `build_messages` 产生 `[system(P0), *history]`，**不把历史拼成一个 user 字符串**。
- `history` 末轮应为 User，角色只能为 `user` / `assistant`，文本必须完整原样；遇到违反已知 D0.3 契约的数据报错并定位。
- `serialize_completion` 输出紧凑 JSON，`ensure_ascii=False`，不加入 `id`，键顺序固定为 `emotion_label`、`user_profile`、`response_text`、`memory_refs`；三个画像子键顺序固定。
- 画像数组按官方 Schema 中各维度枚举的顺序排序，拒绝重复或非法标签；原始 `target` 不允许被就地修改。
- `memory_refs` 始终输出 `[]`；但原始 D0.3 值保持在输入中供追溯。
- 所有 JSON 以标准序列化处理换行、双引号、反斜线，不做文本替换/截断。
- Prompt 与 Completion 不允许靠 `"Prompt + 字符串 + EOS"` 这样的手工模板猜测实现；应通过**实际同一份 Qwen Chat Template**构造完整 Assistant 消息。
- 统一使用 `tokenizer.apply_chat_template(..., tokenize=True, enable_thinking=False, ...)`。推理入口 `add_generation_prompt=True`；训练完整消息采用对应的 Assistant Completion 和该模板的正确终止标记；**以真实 Token ID 校验一致性**。
- 不硬编码 `<|im_start|>`、`<|im_end|>`、`<|im_sep|>`、`<|eot_id|>` 等任何特殊 Token 字面量或 ID；以当前固定 Tokenizer 及模板实际行为为准。

#### 训练/推理前缀不变量（强制门禁）

同一 `messages`，得到：

```python
prompt_ids = encode_inference_prompt(tokenizer, messages)
full_ids = encode_full_training_sequence(tokenizer, messages, completion_json)
assert full_ids[:len(prompt_ids)] == prompt_ids
completion_ids = full_ids[len(prompt_ids):]
assert completion_ids
```

如果当前 Transformers / Qwen 模板下不成立，**必须先调整构造方式或明确定位模板差异，不能用“两个长度相减”冒充 Completion 长度**。

这里的 `completion_ids` 是标准 JSON 正文加上模板要求的结束标记；应通过解码或 Token 边界检查验证，不允许将目标答案遗漏或重复加入。

**特别注意：** Non-thinking 必须作为 Chat Template 参数真正传入，而不是只在系统提示词中写“不要思考”。

### 3. Tokenizer 版本与加载

- 只加载 `Qwen/Qwen3-1.7B` 对应的 Tokenizer，不加载模型权重；优先使用本地已经缓存的官方 Tokenizer。
- 明确记录：模型标识、Tokenizer 实际路径 / revision、Tokenizer 相关文件指纹或 Hub Commit、`transformers` 版本、`chat_template` 的 SHA-256、特殊 Token ID 映射、P0 文件 SHA-256。
- 离线模式下应提供 `--local-files-only` 或同等配置；若需要联网下载 Tokenizer，遵从当前开发环境配置，不引入隐藏下载行为。
- 不能让不同的缓存或不同的 Chat Template 在同一个统计结果中混用。

## 四、D0.4.2 第一轮：未经截断的全量长度审计

### 1. 统计对象

遍历 Train / Dev / Val 全部规范化样本，不改动输入，分别计算：

| 名称 | 精确定义 | 目的 |
|---|---|---|
| `prompt_tokens_full` | `len(prompt_ids)`：P0 + 完整 History + Assistant 生成前缀 | 实际推理输入长度 |
| `completion_tokens_full` | 前缀不变量通过后，`len(full_ids)-len(prompt_ids)` | 完整 JSON + 结束标记的真实监督长度 |
| `train_sequence_tokens_full` | `len(full_ids)` | 训练样本真实总长度 |
| `current_user_only_prompt_tokens` | P0 + 仅当前 User 消息 + 生成前缀的精确长度 | 最小历史可行性边界 |
| `current_user_text_tokens` | 当前用户正文单独编码的长度，仅作诊断 | 区分当前消息过长问题 |
| `history_message_count` | 原始合法历史消息总数 | 判断对话轮次 |
| `history_text_characters` | 原始 History 的角色内容字符数合计 | 计算截断后原文保留比例的基数 |
| `response_text_characters` | 原始参考回复字符数 | 长回复分析（不能代替 Token 数） |

可另记录 P0 原文独立编码所需 Token；其只是静态参考，**不与其他独立编码长度直接求和作为完整训练长度**。

分位数（P50、P90、P95、P99）采用明确、统一的方法（建议 nearest-rank：排序后取 `ceil(p*n)-1`），同时记录均值、最大值、样本数。报告注明单位及算法。

### 2. 统计分组

必须分别提供：

1. Train / Dev / Val 单独统计及三者总体（总体仅供概览，不能用于调参拟合 Val）。
2. 每种情绪标签的样本数与相关长度分位数；极少类应注明样本太少，统计不稳定。
3. `user_profile` 三维全空 vs 非全空样本；可选各维度是否非空的分组。
4. 参考回复长度分组（短/中/长分桶的阈值取自 Train 分位数并在报告公开），观察长 Completion 的比例。

本阶段**不得据 Val 的长度或标签特征定制训练时的独立截断规则**；可报告 Val 兼容性与潜在评测风险。

## 五、D0.4.2 第二轮：固定 Prompt 上限与 T1 历史截断模拟

### 1. 区分四种长度变量

| 变量 | 含义 |
|---|---|
| `S` = `max_train_seq_length` | 训练时 Prompt + 完整 Completion 的总 Token 上限 |
| `P` = `max_prompt_tokens` | 训练与推理共用的固定 Prompt 上限 |
| `G` = `max_new_tokens` | 后续推理允许新生成的最大 Token 数；本阶段只做兼容性检查 |
| `K` = `serving_context_limit` | 推理服务可用的上下文总窗口；不假定它等于 S |

约束：训练可用需 `L_prompt <= P` 且 `L_full <= S`；用于推理的候选配置还应满足 `P + G <= K`，其中 G 为预留的生成上限，不是已知的标准答案长度。

**当前不确定 S、P、G、K 的最终数值。** D0.4.2 只模拟并报告，不替用户做训练长度决定。

### 2. 候选配置矩阵（用于审计，不代表推荐定值）

先支持 YAML 自定义，默认提供以下审计组合：

| S（训练总预算） | P（固定 Prompt 上限候选） |
|---:|---|
| 1024 | 512、768 |
| 2048 | 1024、1280、1536 |
| 4096 | 2048、3072、3584 |

以上数值只是探索性网格。其余组合可配置，不要写死在 Python 逻辑中。不得因某种组合最终不可用就从报告中删掉。

`G` 与 `K` 不需要在当前阶段强行绑定到上述训练档位；可在报告的“推理部署预算检查”中作为单独候选进行 `P+G<=K` 约束检查。不要把 `S` 和 `K` 混为一谈。

### 3. T1 最近完整消息优先算法

对于给定的固定 Prompt 上限 `P`：

```text
输入：history = [m0, m1, ..., mn]，其中 mn 是当前 User 消息；P、P0、Tokenizer

selected = [mn]
如果 encode(P0 + selected) 的 Prompt Token 数 > P：
    记录 CURRENT_MESSAGE_WITH_SYSTEM_EXCEEDS_PROMPT_CAP
    本组合不可构造；不得截断 mn 或 P0
否则：
    从 mn-1 起向前尝试：
        candidate = [更早的一条消息] + selected
        使用真实 Qwen Chat Template 重新编码 candidate
        如果 candidate Prompt 长度 <= P：
            selected = candidate
        否则：
            立即停止，不能跳过这条消息再去找更早的短消息
输出 selected（时间顺序不变）、实际 Prompt 长度、删除消息数量
```

说明：不对单条消息做字符/Token 中间裁切；即使保留下来的消息以 Assistant 开头，也不自动插入伪造的 User 或摘要；系统提示词保持不变。

### 4. 在选定历史后检查完整监督是否仍可容纳

对每组 `(S, P)`：

1. 使用 T1 **只依据 Prompt 与固定 P** 选出消息后缀；不能查看标准答案长度来调整历史。
2. 重新按完整 Assistant Completion 消息渲染并编码，核实 Token 前缀不变量，取得 `L_prompt`、`L_completion`、`L_full`。
3. 如果 `L_prompt <= P` 且 `L_full <= S`：标记 `usable`；按是否删除历史区分 `full_fit` / `trimmed_fit`。
4. 如果最小 `[P0, mn]` 也超过 P：标记 `prompt_floor_exceeds_cap`。
5. 如果 Prompt 合法但 `L_full > S`：标记 `completion_overflows_train_budget`。进一步指出是 `completion_tokens_full > S - min_prompt_tokens`（即使仅保留当前 User 也无法在 S 内容纳），还是“固定 P 下选中的 Prompt 太长导致超额”；**仅用于诊断，不改变本轮既定 T1 结果**。
6. 完整监督不可用也必须记录；绝不裁剪 JSON、修改参考回复、减少用户当前消息、自动丢样本或更改 D0.3 数据。

这一步与“按标准答案长度动态倒推历史预算”的方案不同。我们选择固定 Prompt 策略，是为了维持训练和推理可复用的历史规则。

### 5. 每组预算必须统计的结果

- `n_total`、`n_full_fit`、`n_trimmed_fit`、`n_prompt_floor_exceeds_cap`、`n_completion_overflows_train_budget`；互斥且总和守恒。
- `raw_full_fit_rate`、`usable_rate`、`truncation_rate`、`unusable_rate`；分母统一且公开。
- 已选中样本删除的历史消息数分布及均值；保留原始 History 的消息数比例与正文字符数比例（清晰标注为代理指标，不冒充 Token 保留比例）。
- 原始完整 Prompt 长度与选择后的实际 Prompt 长度；`full_sequence` 的处理后长度分布，仅在成功生成完整序列时统计。
- 失败样本按情绪标签、空画像/非空画像分组的数量和比例；小样本分组标注统计局限。
- 比较 2048 与 4096 时，特别输出**额外保留历史数量与受影响画像样本比例**，但不得据此推断已经提升分类准确率。

### 6. 性能与确定性

20,499 条样本、多套预算、最长 50 条消息，避免对每个候选都从零重复进行所有 Tokenization。

允许使用：相同 `sample_id` 的完整 Prompt 编码缓存、不同历史连续后缀的长度缓存、按候选 P 共享已计算结果。**任何优化后的长度必须与直接调用真实 Tokenizer 的结果一致**，并由测试覆盖。

不要使用文本字符数估算 Token 来代替真实统计；不要依赖未证实的“每条消息编码 Token 数可以简单求和”。输出可选用流式 JSONL，控制内存开销。

## 八、审计产物与可复现性

### 1. `token_stats.json`

包含：

- 输入数据的数量及哈希；P0、Tokenizer、Chat Template 指纹；分位数定义；实际配置。
- 按 Train/Dev/Val 的 Prompt、Completion、全序列 Token 长度分布。
- 按情绪、画像有无、回复长短的分层统计。
- 每组 `(S, P)` 的互斥分类数量、可用率、裁剪率、平均删减历史条数、消息和正文保留比例、异常数量。
- 清晰区别**事实统计**、**预算模拟**、**资源可行性尚未验证**。

### 2. `budget_simulations.jsonl` 与 `length_exceptions.jsonl`

记录每条样本每组候选的：`sample_id`、Split、S、P、原始/裁剪后 Prompt 长度、完整 Completion 长度、总长度、原始/保留消息条数、删减条数、最终分类、必要的原始 source 定位。

`length_exceptions.jsonl` 仅记录无法容纳的组合及原因。两份文件只存定位和统计数据，不复制私有对话正文和真实回复。

### 3. `manifest.json`

必须记录：

- Git Commit、工作区状态、配置 SHA-256、P0 SHA-256。
- Tokenizer 的**实际可复现版本**（Hub revision / 本地相关文件指纹）及 Chat Template SHA-256。
- Python / Transformers / Tokenizers 版本；数据输入文件 SHA-256 与 D0.3 Manifest 的对比。
- 结果文件 SHA-256、统计样本数、候选网格。
- 测试实际执行命令和结果摘要。

不要声称所有产物逐字节恒定：若 Manifest 内含运行时间、机器路径，元数据可能变化。应明确区分**确定性统计产物**与**含环境信息的运行记录**。

### 4. Git 中的 `D0.4.2_Token长度审计报告.md`

建议章节：

1. 输入数据版本与本次 Tokenizer / P0 / 模板定义。
2. Train/Dev/Val 实际长度分布表（P50/P90/P95/P99/Max）。
3. 每组 S/P 的完整容纳率、裁剪率、处理后可用率、不可用原因。
4. 长历史、长回答与画像样本的关系；说明统计限制。
5. 两到三张必要图表：完整训练长度分布、Completion 长度分布、候选预算下的历史保留率（可在 `outputs/` 生成，报告可以引用简要数据表；不要生成大量临时图）。
6. 候选长度选择建议：列出优势/代价/未验证风险，不直接宣布最终值。
7. 复现命令、测试结果、已知限制、D0.4.3 交接条件。

报告可以提出“优先尝试 2048 的 QLoRA 显存测试”之类**有数据依据的建议**，但不得把硬件可行性或模型效果推断为已验证事实。
