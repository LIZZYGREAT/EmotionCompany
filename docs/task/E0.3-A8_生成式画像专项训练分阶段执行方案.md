## 一、任务目标与冻结的实验设定

### 1. 需要完成的两条路线

**P：Profile-only**。模型输入专用画像任务 Prompt 与用户历史，输出且仅输出三行：

```text
Personality=sensitive
Interests=games|pets
Style=direct|rational
```

**EP：Emotion+Profile**。输入另一份独立 Prompt 与**完全相同的用户历史**，输出且仅输出四行：

```text
Emotion=joy
Personality=sensitive
Interests=games|pets
Style=direct|rational
```

- 字段名固定大小写：`Emotion` / `Personality` / `Interests` / `Style`；赋值符号固定 ASCII `=`。
- 同一维度的多个标签以 ASCII `|` 分隔；标签必须去重，并按照官方 Schema 中该维度的枚举顺序排列。无标签写 `-`，禁止空字符串、`null`、`[]` 或自编标签。
- Emotion 必须从官方 16 类情绪枚举中选择**恰好一个**；P 模型不输出 Emotion 字段。
- 最后一行后直接结束 Assistant 消息，由 Qwen Chat Template 写入 EOS；不额外生成 `Response=`、`response_text`、`memory_refs`、解释、Markdown 代码围栏或完整 JSON。
- **两个模型都使用正常的自回归 `model.generate()` 生成文本**；本次不引入独立 Sigmoid/Softmax 分类头，也不使用 BCE 辅助损失。训练均采用 Completion-only SFT。

本轮两组模型均由相同的 Qwen3-1.7B Base 初始化全新 LoRA，且从同一冻结初始 LoRA 张量值起步。两组训练使用同一训练样本 ID 顺序、批次边界、优化器方案和累计步数。训练完成后对生成的文本解析为结构化标签并计分。

### 2. 为什么采用生成式专项训练

原数据中的一条 Gold 有 `emotion_label`、`user_profile`、`response_text`、`memory_refs`。现在只把目标任务对应字段转为 Completion，保证每一次梯度更新只对当前任务的输出 Token 计算 Loss。

记用户历史和任务指令构成的输入为 `x`，某条生成式分类答案经 Tokenizer 编码为 `y=(y_1,…,y_T)`。训练目标：

$$
L_{\mathrm{completion}}(\theta)=-\frac1T\sum_{t=1}^{T}\log P_{\theta}(y_t\mid x,y_{<t}).
$$

训练阶段将真实 Completion 作为 Teacher Forcing 上下文，使用 `labels=[-100]*prompt_length + completion_token_ids`，由模型内部进行下一个 Token 的位置移位，**首个答案 Token 和最后的 EOS 均须受到监督**。Prompt 中可以存在标签定义、用户历史，但 Prompt Token Loss 被 Mask。推理阶段不给任何 Gold Completion，由模型逐 Token 生成三行或四行，最终以真实生成预测计分。

两个实验应分别报告自己每个优化步的 Completion Token 数与 Loss；**由于 P/EP 的目标长度不同，二者训练 Loss 不能直接当作分类效果排名**。画像 F1、Precision、Recall、FP 才是主比较指标。

### 3. 冻结模型与训练超参数

| 内容 | 规定 |
|---|---|
| Base | `Qwen/Qwen3-1.7B`，revision `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e`；本地 `participant/model` |

## 三、专项 Completion 协议、序列化与解析

### 1. 建议模块与数据形态

新建 `src/shared/e03_a8_protocol.py`，提供下列接口（命名可按仓库风格微调，但职责必须保留）：

```python
PROFILE_DIMS = ("personality_traits", "interests", "style")
FIELD_ORDER = {
    "P":  ("Personality", "Interests", "Style"),
    "EP": ("Emotion", "Personality", "Interests", "Style"),
}

def validate_a8_prompt_enum_order(prompt_text, official_schema, arm): ...
def serialize_specialist_completion(target, official_schema, arm): ...
def parse_specialist_output(raw_text, official_schema, arm): ...
def validate_training_target_round_trip(target, arm): ...
```

序列化规则：

1. 先用官方目标 Schema 验证 Gold，不能修补、猜测或遗漏原始 Gold 标签；确保来源有效。
2. 对三个维度分别按官方枚举排序，`"|".join(labels)`，空数组写 `-`。
3. `EP` 首行加 `Emotion=<Gold emotion_label>`，`P` 不含 Emotion。
4. 三行/四行按 `\n` 连接；**末尾不额外添加解释性换行**；模板提供的 EOS 是独立的结束监督 Token。
5. `P` 训练 Completion 不包含 `emotion_label` 的任何 Token；`P` 与 `EP` 均不包含 Gold 的 `response_text`、`memory_refs`。
6. 解析器严格校验字段名、行数、顺序、分隔符、官方枚举、去重、规范顺序、额外文本和 EOS 后解码残留；输出结构化 `user_profile`，`EP` 额外输出 `emotion_label`。
7. 对不完整、非法、越界、额外字段等保存稳定失败状态；**不得用从自由文本提取标签、自动补列、默认标签、可疑替换等行为掩盖模型的真实生成错误**。只有明确约定的 EOS/终止空白可以在解析前处理，处理规则须冻结并有单测。

**注意**：既有 `src/shared/f4_protocol.py` 已有 `Emotion/Personality/Interests/Style`、`|`、`-`、官方枚举排序和严格解析逻辑，可借鉴不变的通用函数，但其协议要求第五行 `Response=`。本实验的解析器必须严格支持完整三行或四行且直接 EOS；不要通过伪造 `Response=` 来满足旧解析器。

### 2. 测试用例（必须全覆盖）

- 空画像三维：`Personality=-\nInterests=-\nStyle=-`。
- 多标签按官方枚举排序；同一维度 0、1、多标签边界。
- 错字段大小写、使用 `:`、`,`、缺失 `=`、重排行、重复字段、额外字段、额外叙述。
- 标签重复、枚举外标签、跨维错标签、标签次序不合法；文本中存在回车/多余空行。
- `EP` 缺 Emotion、Emotion 多值、Emotion 不在 16 类内；P 错误包含 Emotion。
- 训练 Gold 序列化后解析，要求在对应的目标字段上**逐值完全一致**；不能将 Response 文本拼入训练 Completion。
- EOS 结束与 `max_new_tokens` 截断分别正确记录；发生截断时不得把已有三行片段伪装成完整有效预测。

## 四、Train 数据构建：同历史、同样本、只改变训练答案

### 1. 数据来源与范围

- 原始规范化 Train：`data/processed/v1/train.jsonl`，历史记录 **16,312** 行。
- 冻结有效 SFT Train ID 集：`data/processed/sft/v1/train.jsonl`，**16,192** 行；由 D0.4.3 排除的历史 **120** 条暂不在本次训练中加入。此次两个实验完全使用同一批 16,192 ID。
- D0.3/D0.4 Manifest、官方 Train Schema、P0、Tokenizer、原始 E01-B、F4 数据和其他实验缓存均只读。
- 从规范化 Train 依据 `sample_id` 唯一 Join 回 Gold `target` 与完整 `history`；对照原 16,192 SFT ID 及 `conversation_id`。不能用现有 SFT JSON Token 直接删去 Response Token，因为 Prompt/Completion 语义及 EOS 都变了，必须重新调用 Chat Template 编码。
- 不从 Dev、Val、官方测试集抽取训练数据；训练构建不能从 Dev 错例动态派生标签规则或 Prompt。

### 2. 统一的历史视图：避免 P/EP 输入不同

P/EP Prompt 长度不同，如果两条路线分别独立执行 T1，可能保留不同的历史消息，造成不必要的混杂变量。因此本轮建立 **Common History Selection（固定共同历史）**：

1. 先取 D0.4.2/F2 已审计的该样本 P0/T1 选中历史后缀，校验与原 SFT Prompt Token ID 前缀一致。
2. 在相同历史后缀上，分别使用 P Prompt 和 EP Prompt 调用 `encode_inference_prompt()` 实际 Tokenize，均必须满足 `P=1280`。
3. 若任一 Prompt 超过 1280，则从**该历史后缀最早的一条消息开始**继续裁剪，两个分支**同时采用同一个裁剪后缀**；保持连续、末尾包含当前 user 消息，禁止任一分支独自多保留历史。
4. 不允许添加在旧 P0/T1 视图之外的更早消息，避免与既有 E01-B 输入形成额外的历史信息优势。
5. 如果只保留当前用户消息仍无法让两个 Prompt 均满足上限，标记 `prompt_floor_exceeds_cap`，**阻断全量数据构建**并报告对应样本/Prompt 长度；不得静默删除导致两组样本数不同。必要时单独版本化缩短两份 Prompt，再从头重建完整数据与 Hash。
6. 将每条 `selected_start_index`、共同历史 SHA、两种 Prompt Token 长度、额外历史裁剪数量保存到忽略目录；实施前确认全量 `16,192 / 16,192` 都可编码且两个分支使用的历史 SHA 完全一致。

同一个共同历史规则还必须用于 P/EP 的**每一条 Dev Fast-only 样本**。对 E01-B 既有 Baseline 做比较时说明它使用原 P0/T1 视图，因此与新模型是**实际候选模型间的质量对照**，不能单独归因于删掉 Response Loss；P 与 EP 之间则保持共同历史完全一致。

### 3. 每条训练样本的真正构建过程

建议实现 `src/data/e03_a8_sft.py` 与 `scripts/e03_a8_prepare.py`。对于某个 `sample_id`：

```python
# 伪代码：所有字段来自同一条冻结 normalized Train Gold
sample = normalized_train_by_id[sample_id]
common_history = select_common_history(sample.history, p_prompt, ep_prompt, tokenizer)
for arm in ("P", "EP"):
    prompt = PROMPT[arm]
    messages = build_messages(common_history, prompt)
    prompt_ids = encode_inference_prompt(tokenizer, messages)
    completion = serialize_specialist_completion(sample.target, official_schema, arm)
    full_ids = encode_full_training_sequence(tokenizer, messages, completion)
    completion_ids = validate_completion_suffix(tokenizer, completion, prompt_ids, full_ids,
                                                sample_id=sample_id)
    assert full_ids[:len(prompt_ids)] == prompt_ids
    assert len(prompt_ids) <= 1280 and len(full_ids) <= 2048
    labels = [-100] * len(prompt_ids) + completion_ids
    assert labels[len(prompt_ids):] == full_ids[len(prompt_ids):]
    assert tokenizer.eos_token_id in completion_ids
    write_preencoded_row(arm, sample_id, full_ids, labels, common_history_fingerprint)
```

每条新数据需要保留 `sample_id`、`conversation_id`、`source_split=train`、`input_ids`、`labels`、`prompt_length`、`completion_length`，可继续使用 `src/data/sft_collator.py::SFTDataCollator`。两份数据的 ID 顺序、样本数、共同历史 hash 必须完全对齐。

### 4. 冻结一次训练 Schedule

用同一 seed `42` 对 **16,192** 个 Sample ID 作一次随机打乱并冻结为唯一 `sample_order.jsonl`。这个顺序在 P/EP 间共享，不由 Trainer 自行二次 Shuffle。

- Step 512：恰好消费前 `2,048` 个不同样本。
- Step 1024：累计 `4,096` 个不同样本。
- Step 2048：累计 `8,192` 个不同样本。
- Step 4048：累计 `16,192` 个不同样本，一轮完整 Train。

所有计数均为**累计优化步和累计唯一样本**；不允许将不同节点重新抽样凑齐固定步数，也不允许 P/EP 使用独立随机数据排序。

推荐的真实执行逻辑：

```python
# 伪代码：一组 arm 一次训练段，两个 arm 顺序占用 GPU
assert cpu_preflight_passed(arm) and gpu_dry_step_passed(arm)
assert valid_stage_authorization(arm, from_step, to_step)

if from_step == 0:
    model = attach_new_lora(model, seed=42)
    assert sha_initial_lora(model) == frozen_shared_initial_lora_sha

else:

    assert cursor == from_step * 4
for step in range(from_step + 1, to_step + 1):
    optimizer.zero_grad(set_to_none=True)
    for sample_id in frozen_schedule[step]:  # 4 个 Microbatch
        batch = collate(arm_preencoded_row[sample_id])
        loss = model(batch.input_ids, labels=batch.labels).loss
        assert finite(loss)
        (loss / 4).backward()
    assert finite_nonzero_lora_gradients(model)
    clip_grad_norm_if_configured()
    optimizer.step()
    scheduler.step()
    append_immutable_step_ledger(arm, step, sample_ids, loss, lr, gpu_peak)

verify_standalone_adapter_reload_and_base_unchanged()

```

若底层用 TRL `SFTTrainer`，必须确认它只使用传入的预编码 `input_ids/labels`、不二次 tokenize、不生成新 completion、不改变预先冻结的数据顺序，并按 Qwen 自回归标签移位计算 Completion-only Loss。必须用 CPU 合成测试验证 Batch/Mask/EOS 与样本消费；不能仅靠配置中的 `packing: false` 作保证。

**训练中不加载 Gold 完整 JSON 作为 Completion**；训练器对现有 JSON 字段应毫无依赖，只接收新的 P/EP 预编码数据。Base 冻结，只优化各自 LoRA；两组必须使用独立的 Optimizer/Run 路径。

### 2. Checkpoint 必需内容

每个正式节点在对应 Run 下保存完整可恢复状态：

```text

  config_snapshot.yaml
  sample_order.jsonl
  step_ledger.jsonl

  trainer/checkpoint-2048/

```

每个已完成的 Checkpoint 至少包括：

- LoRA Adapter 权重/配置，训练时 dtype、保存 dtype、独立重载的张量核对摘要；
- AdamW `optimizer.pt`（动量、参数映射和 step）、`scheduler.pt`；
- Python、PyTorch CPU/CUDA、NumPy、Sampler 的 RNG 与数据游标；
- Trainer State、`global_step`、已消费样本 ID 的累计 Hash、对应 Step Ledger；
- Base/Tokenizer/Chat Template、P/EP Prompt SHA、官方 Schema、预编码数据/共同历史、Schedule、源 commit/代码哈希；
- 显存峰值、训练耗时、设备身份、梯度与有限性检查；
- 每个节点完整 Checkpoint Manifest SHA，写完之后只读保留，不得被自动轮转删除。

若使用 PEFT 加载/保存，注意 LoRA Tensor dtype 是否在加载时发生自动转换（`autocast_adapter_dtype`）；必须沿用与该训练路径实际一致的 dtype 语义，逐值核验独立重载，不得将重载偏差视为训练改进。以冻结的 QLoRA 工程约束决定实际保存精度并写入 manifest，不能未经验证套用其他实验的 `float32`/`bfloat16` 结论。

### 3. 分阶段授权与恢复

节点授权状态分别记录两组实验，建议独立 CLI：`scripts/e03_a8_staged_authorize.py`。记录必须绑定：

`experiment_id + arm + run_id + from_step + to_step + checkpoint_manifest_sha256 + last_eval_summary_sha256 + reviewer_decision + config/data/code_sha256`

- `0→512`：本任务允许在全部 CPU 和 GPU Dry-run 门禁通过、用户本轮允许首节点训练的前提下各运行一次；必须显式 `--allow-first-stage-training`，不能由仅运行 preflight 的命令暗中启动训练。
- `512→1024`、`1024→2048`：用户已于 2026-11-07 对 P/EP 给出有条件的持续训练授权。每组必须先完成对应节点的完整评测；质量门槛通过时写入绑定 Run/Checkpoint/Eval Hash 的条件授权回执，再从同一完整 Checkpoint 恢复。
- `2048→4048`：必须收到用户新的明确批准；本轮授权绝不涵盖此段。
- 节点状态根据质量门槛记录为 `conditionally_authorized` 或 `awaiting_manual_review`。模型分数本身不能越过下面冻结的止损规则，也不能授权超过 2048。
- 被审核否决、缺少评测、SHA 不一致、某一组训练中断且没有合法 Checkpoint，均阻止下一节点。
- 审核可明确允许两组继续、只允许其中一组继续，或者全部停止。如果只推进一组，后续报告必须标识节点不同，禁止错配步数来排名。
- 恢复必须从**同一个 Run** 的完整 Checkpoint 恢复 Optimizer/Scheduler/RNG/顺序，不得仅加载 Adapter 并新建优化器却标为累计续训。

参考 `scripts/e03_a6_f4_staged_train.py`、`scripts/e03_a6_f4_staged_authorize.py` 与 `src/training/e03_a6_f4_staged_full.py` 的命令和身份结构，但 A8 使用独立 Run namespace 和独立协议。旧 A6 Run 保持只读。

## 六、评测：只生成分类字段，逐节点评价画像

### 1. 冻结评测样本

优先复用已经存在且具有身份哈希的两套 Dev 无标签输入：

| Cohort | 大小 | 样本 ID SHA-256 | 主要用途 |
|---|---:|---|---|
| `pilot160` | 160 | `98f24f1c1b41e1676618f4e557daa402b3cbb80686916ca818e1bdc1b89ae49c` | 观察早期训练趋势，保留 F4 可比较的样本集 |
| `dev224` | 224（101 段会话） | `d3c84beb6227e87c0fd09e425619635cd9fc6bac5b087e3f1010fb089f4ff8d2` | P/EP 同 ID 主评价；与 E01-B Fast-only 224 基线对比 |

这两个集合有 **20 个重叠 ID**：每组模型每节点只生成去重并集 `160 + 224 - 20 = 364` 条预测，并分别以 160、224 固定分母计分。先核对实际 ID、输入和 Gold 的一致性以及 SHA，再采用上述预期计数。

相关源路径、SHA 和映射见 `configs/evaluation/e03_a6_f4_staged_fast.yaml`：

- Pilot：`outputs/evaluation/e01_b/pilot_dev_v1/smoke_{input,id_map,references}.jsonl`。
- Dev 224：`outputs/diagnostics/e03_a3/E03-A3-DIAG-20261104-05/frozen_eval_{input,id_map,references}.jsonl`。

**推理与评分必须分离**：先只读取 `input/history`、ID、必要的会话映射，分别生成 P/EP 预测并将预测 JSONL 原子冻结 SHA；然后才读取 References/Gold 调用 `src/evaluation/metrics.py::profile_metrics()` 等已有评分器。Gold 不参与 Prompt/生成，也不能用于解码中途决定标签。

### 2. 每条预测的真实运行过程

```python
for eval_sample in frozen_deduplicated_union:
    common_history = select_common_history(eval_sample.history, P_prompt, EP_prompt, tokenizer)
    for arm in ("P", "EP"):
        prompt_ids = encode_inference_prompt(tokenizer, build_messages(common_history, PROMPT[arm]))
        raw_text, generation_facts = model_for_arm.generate_greedy(prompt_ids, max_new_tokens=256)
        prediction = parse_specialist_output(raw_text, schema, arm)
        write_prediction_minimal(arm, id, prediction, parse_status, generation_facts)

```

真实 GPU 推断可以按两组逐个加载并在同一 364 ID 顺序执行，不要求在 8GB 显卡上同时常驻两套模型。一次 `model.generate()` 仅负责一个样本的一条专项答案，输出没有 Response，所以也没有依赖 `Response=` 的提前截断逻辑；是否完成以**完整字段 + EOS 合法**为准。

必须记录每个 ID 的实际生成次数、EOS、生成 Token 数、超时、非法字段、字段缺失、生成超预算、未知标签以及非空情况；中断时已完成的最小预测允许落盘，但**不得把部分 Run 当完整质量报告**。推荐单模型每节点的 364 点总预算在 GPU preflight 后冻结，首选 ≤2400 秒，超限停止不自动重试。

### 3. 评价口径：防止空画像与误报造成误判

P 和 EP 的画像都使用**同一官方 33 标签顺序、同一 Gold、同一固定分母评分器**。建议核心指标：

| 类别 | 必须统计 |
|---|---|
| 总体画像 | `TP / FP / FN`，Micro Precision、Recall、F1，Macro-F1，样本级 Exact |
| 三个维度 | `personality_traits / interests / style` 各自 TP/FP/FN、Micro-F1、非空率 |
| 稀疏与误报 | Gold 非空但预测全空的数量、Gold 全空上的 FP、每样本标签数分布、长尾标签的 TP/FP/FN |
| 格式 | 3/4 行严格解析率、EOS 完成率、非法标签率、截断率、逐 ID 失败状态及固定分母兜底 |
| 情绪 | **仅 EP**：16 类 Accuracy / Macro-F1 / 主要混淆；P 情绪记 `N/A`，不得按 0 评分 |
| 配对 | 同 Step 的 `EP - P`，同一分支跨 Step、对 E01-B Dev 224 基线的差值；按 conversation cluster 做配对 Bootstrap |
| 资源 | 加载时间、生成时间、每点总 Token、P50/P90/P99 延迟、显存分配和实际完成率 |

严格解析失败的样本必须保留在固定分母：画像按空预测计入 Gold 对应 FN；同时列出独立的模型格式失败数，防止用“全空”掩盖解析错误。EP 情绪解析失败按错误/无效记录入固定分母，不能把无效样本从 Accuracy 分母中删除。若已存在可核验的 E01-B Fast-only 224 基线，画像 Micro-F1 约 `0.425787`（TP/FP/FN=`142/152/231`）可作为候选质量参照；必须绑定该基线对应的预测文件和身份，不应直接用历史完整 JSON `0.422323` 与专项前缀混算。

**主决策重点是画像**：不能因为 EP 情绪略优就宣布 EP 优于 P；更不能因为模型学会输出很多标签而只看 Recall。Precision 与 FP 必须同表展示。

### 4. 节点结果与人工审阅规则

每个节点交付一份报告，至少包含：

1. 两条路线累计步骤、已消费的唯一 Train 样本数、完整 Checkpoint/Optimizer/RNG/Schedule 哈希，以及是否可以从当前节点恢复。
2. 同 Step 的 P/EP 在 Pilot 160 与 Dev 224 上的全指标对照；两组使用相同共同历史且真实输入 ID 一致。
3. 画像非空数、TP/FP/FN、Precision/Recall/F1，三维拆解、逐标签主要漏报/误报、格式错误和异常样本分布。
4. 与上一节点的差异：哪些标签从 FN→TP，哪些新输出是 FP；必要时按会话做 1000 次 Bootstrap（只用于探索性置信区间）。
5. 与 E01-B Fast-only 主基线的关系；对于 P 和 EP 单独给出“当前质量是否足以继续研究”的明确依据。
6. `next_stage_recommendation=continue/stop/inconclusive` 与 `authorization` 状态；2048 之前按用户授权的宽松止损规则处理，2048 之后以用户明确批准为唯一放行条件。

建议决策思路：

- **Step 512**：先检查格式、学习是否正常、是否开始预测非空画像、Recall 与 FP 的比例；作为冷启动阶段，即使尚低于 E01-B，也不要机械宣布研究失败。
- **Step 1024**：检查画像是否产生连续真实 TP 增长，是否在少数高频标签上塌缩，以及 EP 是否出现相对 P 的系统性 Precision/Recall 改变。
- **Step 2048**：核心审查。如果仍大面积全空、TP/Recall 很低，或新标签主要是 FP，则明确建议停止；若 F1 与有效非空覆盖率连续改善且 FP 可控，报告继续的理由。
- **Step 2048**：本轮已授权上限。完成评测、保留完整 Checkpoint 与报告后停止；若质量表现正常，不表示自动获准继续到 4048。

#### 本轮宽松止损门槛（首次训练前冻结）

- 两个 Arm 独立判断。早期节点不要求 Micro-F1 达到或追平 E01-B 的 `0.425787`，也不因单个节点低分、Precision 偏低或 FP 偏高单独停止；这些指标仍需完整报告。
- 某 Arm 的评测输出需完整覆盖 Pilot 160 与 Dev 224，并且严格解析率至少 `98%`、身份与 Checkpoint Hash 全部一致。缺失覆盖、身份不匹配、解析率不达标或训练完整性错误时立即停止该 Arm，状态为 `awaiting_manual_review`，不得把工程失败计作模型质量结论。
- 只有当同一 Arm **连续两个已完成节点**在 Pilot 160 和 Dev 224 上均 `TP=0` 时，才判为 `quality_failed` 并停止该 Arm，留待用户 review。单节点 TP=0 仍可继续到下一节点。其余有效结果均视为本轮宽松门槛通过，允许在授权范围内继续；无需自动满足 E01-B 基线门槛。
- P 与 EP 分开授权。某一组停止时，另一组仍可按自身有效节点继续。达到 Step 2048 后一律停止并等待用户明确批准是否进入 4048。所有阶段仍报告 F1、Precision、Recall、TP/FP/FN、非空覆盖率、格式与 EOS 统计；`next_stage_recommendation` 解释上述条件判定。

## 八、必须具备的回归与完整验收

### 1. 协议与数据测试

- 两个 Prompt 均拥有完整 33 画像枚举，EP 另有完整 16 情绪枚举，名称与官方 Schema 完全匹配。
- 严格 `=`/`|`/`-`、三/四行、规范排序、重复与非法字段、空画像；Gold 序列化与解析双向一致。
- 全 16,192 样本的 `sample_id/conversation_id/source/history` 一一对应，P/EP 顺序完全相同、共同历史 SHA 相同、没有 Dev/Val 加入训练。
- 完整训练序列必须以推理 Prompt IDs 作为真实前缀；Prompt Mask 和 Completion 标签逐 Token 对齐，EOS 被监督，`P<=1280`、`S<=2048`；不出现 Response 正文 Token 作为训练目标。
- 由 `sample_order` 推导 512/1024/2048/4048 节点的样本累计数精确为 2048/4096/8192/16192，所有 ID 唯一，恢复后无重复/跳过。

### 2. 训练、恢复和授权测试

- 相同 Seed 的初始 LoRA Tensor 摘要相同；两个不同 Run 的后续参数、Optimizer State 不共享；Base 始终冻结。
- GPU dry-step 不更新权重，真实更新后可确认 LoRA 参数变化；非有限 Loss/梯度、OOM、CPU offload、身份错误必须立即失败。
- Checkpoint 保存/独立加载、Optimizer/Scheduler/RNG、Sampler 游标与 Step Ledger 一致；从节点恢复后的连续数据消费与未中断参考路径一致（数值误差如有须有范围记录）。
- 缺少有效评测、条件授权回执或必要用户批准不能进入下一节点；错误 Run ID、步骤、Checkpoint SHA、数据 SHA、超预算、重试覆盖均拒绝。连续两节点双 Cohort TP=0 时拒绝自动继续。
- 旧 E01-B、A6、P0、D0.3/D0.4、官方 Train/Val 文件前后 SHA 未被改变；Git 提交不包含模型权重、Gold 明细和预测正文。

### 3. 评测与质量测试

- 两 Cohort 的 160/224 固定 ID 及其 20 重叠正确处理；每个 Arm、每个 Step 生成并计分完整去重并集 364 个样本。
- 推理进程严格 target-free；Gold 仅在预测文件 SHA 冻结后读取。不同 Arm 的共同历史选择及 ID 完全一致。
- 固定分母计算 TP/FP/FN 与 33 标签 Micro/Macro-F1，异常输出不得被遗漏、不得自行补标签。
- P 的情绪是 `N/A`；EP 的无效 Emotion 纳入固定分母；汇总能对齐 E01-B 224 Fast-only 基线与 P/EP 逐节点结果。
- 每个节点都有 `stage_manifest.json`、`evaluation.json`、已完成/失败明细、逐样本预测 SHA、质量结论及明确的下一阶段建议。没有 Step 4048 产物时不能写成 Full 完成。
