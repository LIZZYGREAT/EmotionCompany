## 二、统一定义完成、异常与质量状态（先改 CPU 逻辑）

当前两个错误耦合点必须一起修：

1. `participant/final_dual_inference.py` 中 `cap_gate = all(count == 0 for count in cap_hits.values())`，从而一条 `length` 导致整个 `start.sh` 退出 1。
2. `scripts/final_dual_docker_package.py::compare_reference_outputs()` 与 `verify_output()` 把宿主与容器的 `generation_cap_hits` 相等、以及绝对零 cap，作为 Docker 部署身份/运行通过门槛。这与实际观测到的跨启动生成差异冲突。

把事件与状态明确拆开：

| 状态 | 触发 | 推理行为 | 是否硬失败 |
|---|---|---|---|
| `completed_stop` | `finish_reason=stop` 或明确的正常终止标志 | 按原结果解析并提交 | 否 |
| `length_limited` | `finish_reason=length`，达到 1200 上限但内容有合法结构 | 执行**最多 1 次**定向重试；结果按下节选择 | 不因单个事件直接让整批退出 1；记录降级 |
| `invalid_output` | 格式错误、Emotion 非法、回复空或 Schema 无法通过 | 按已有字段级降级机制处理；记录失败 | 可降级完成；不可假报原生输出成功 |
| `route_error` | 连接错误、服务退出、LoRA 不存在、Prompt Token 校验失败 | 记录明确错误，保留可用的另一模型输出 | 单次可按现有逻辑降级；服务整体故障属于硬失败 |
| `asset_or_protocol_mismatch` | 模型/配置/Prompt/Tokenizer SHA 或 Prompt IDs 不一致 | **停止**，不能继续生成 | 是 |

注意：`completion_tokens==1200` 且 `finish_reason=stop` 不应机械记为“确定截断”，只能在诊断中注明恰好命中预算。`finish_reason=length` 的事实不能覆盖掉。报告必须区分**Schema 合法、结构可解析、正常 EOS 完成、长度受限、重试恢复和最终剩余受限**；不能把它们合成一个成功率。

### 1. E03-B 长度受限的有界恢复

仅在 E03-B **实际返回** `finish_reason=length` 时执行一次重试（A8 保持原有规则）。重试必须满足：

- 使用同一个冻结 ER Adapter、相同 Prompt Token IDs、相同 Greedy / `temperature=0`、相同 `max_tokens=1200`、相同 Qwen Chat Template；不向 Prompt 追加“简短回答”，不增大 G。
- 重试次数最多 **1 次**，不得连环重试。两次返回均单独保存 `request_id`、`finish_reason`、`completion_tokens`、原文及哈希、Prompt Token 比对、耗时、解析结果。
- 优先使用**结构合法、情绪有效、回复非空且正常 `stop`** 的生成；若两次都 `length`，选择满足原解析器与官方 Schema 的结果作为**`length_limited_unresolved`**，不写成正常结束。若一条合法一条非法，则使用合法者；无法得到有效 ER 时按原有固定字段级降级策略处理，记录 `invalid_output`。
- 不为了“有个输出”而修改 `finish_reason`、截掉错误证据或编造回复；保留原始两次生成结果，最终只选一条进入官方 JSON。
- 加入**无 Gold 的自动异常文本诊断**（连续异常重复片段、明显空正文、生成 1200 Token 但未正常结束）；这些检测仅用于结构/安全性和统计，不能随意代替模型输出。若文本异常严重，标记 `degraded_response` 并按原协议降级；避免拿明显循环垃圾作为正常回复提交。

所有有效长度受限情况允许输出整条 JSON，但要在性能报告中标明 `degraded`/`warning`，并按下述预构建压力门槛控制其发生率。**不得用“重试碰巧成功”替换所有问题诊断。**

### 2. 路由计数、恢复和校验必须同步修改

如果一次 ER 请求发生重试，就会发生**21 次 ER 调用对应 20 条输入**。必须同步修订：

- `participant/final_dual_inference.py`：每样本 `route_attempts`、`prompt_token_ids_exact_match`、两次 `generation_seconds`、`generation_cap_hits`、输出 Raw 和 `run_progress.json`。区分 `initial_cap_hits`、`retry_attempts`、`retry_resolved`、`unresolved_cap_hits`、`degraded_responses`；不得把正常的重试次数计作路由失败。
- `performance_report.json`：保留老字段供兼容读取，但新增上述字段，并明确 `status=passed` / `status=failed` 与 `quality_warnings`；`complete=true` 只说明所有输入均处理。输入、唯一 ID、Schema、模型路由/Prompt 匹配和服务健康才是运行级主要门禁。单条合法长度受限以 warning 表示，不直接阻断整个官方脚本。
- `scripts/final_dual_docker_package.py::verify_output()`：LoRA alias **请求总数应该等于已处理样本数 + 对应路由重试次数**，不能死写 `{profile:20, emotion-response:20}`。Prompt Token IDs 必须对**全部尝试，包括重试**精确匹配，且报告明确分母；官方文件仍要求 20 条，而不是 21 条。
- `compare_reference_outputs()`：继续要求输入 ID/顺序、两路权重/Prompt 身份、画像和情绪稳定字段、Schema 正确及无路由错误；**不要求不同冷启动的回复逐字相同或截断次数严格相同**。不同运行各自的 cap、retry、degraded 等作为实测差异输出；如稳定字段出现差异或原生格式显著下降，必须诊断，不直接认为通过。
- Resume：恢复后只能产生一个最终 JSONL 行；保留同样的两次尝试与耗时事实。模拟“重试成功但文件写入中断”的故障，核对 `run_progress` / 哈希校验不会重复提交或丢弃已完成样本。

**最小改动范围：** `participant/final_dual_inference.py`、`src/inference/final_dual_vllm.py`（如需扩展返回结构）、`scripts/final_dual_docker_package.py`、相关 `tests/`；必要时增加一份小型纯函数 `src/inference/final_dual_recovery.py`。不要重构 A8、E03-B 的 Prompt/LoRA 或整体服务启动流程。

**版本锁同步处理（不可遗漏）**：当前 `model_lock.json` 同时锁定了部署配置 SHA；只要修改 `configs/deployment/final_dual.yaml` 或 Docker 版本配置，旧锁就会拒绝新运行。应为修订版在**新 Run 目录**生成新的 v1.1 配置锁、代码 SHA 和资产核验结果；旧锁与 v1 验收证据只读。`scripts/final_dual_docker_package.py::verify_previous_gates()` 必须区分“旧 A/B/C 对**不变的模型权重、Prompt、历史处理协议**的证据”和“新 v1.1 运行时容错逻辑的**新宿主 Smoke/官方入口证据**”，不能直接把旧 `passed` 记录当成新代码的运行通过，也不能因新锁 SHA 不同而偷偷绕过身份检查。若能保持原部署配置不变、将修复做在纯代码层，则优先减少配置改动，但仍必须更新代码身份与新验收记录。

## 三、正式 Docker 构建前：完成全部能提前做的验证

### Gate 0 — CPU 回归与模拟故障（**零镜像构建**）

预先构造确定性假的 vLLM 响应/Mock，覆盖下列分支：

1. 1200 Tokens 且 `finish_reason=stop`：不误计为确认截断。
2. 首次 `length` → 重试 `stop`：只提交正常结果，记录一次初始 cap 和一次恢复。
3. 首次 `length` → 重试仍 `length`：提交原协议允许的合法降级结果，标记 unresolved；整批在输入完整、Schema/身份通过时不因该单一事件退出 1。
4. 首次 `length` → 重试格式错误：保留首次合法结果，标记未恢复。
5. 两次均非法：按原协议降级，确保官方 JSON 字段完备；不得凭空产生 Emotion/画像。
6. E03-B 路由或 Prompt Token 校验失败、服务退出、A8 失败，必须正确区分独立字段降级与整 Run 硬错误。
7. 20 条中 1 次重试：实际请求 `{profile:20, emotion-response:21}`，Prompt 精确匹配 `20/21` 次，JSONL **始终** 20 条，重试延迟计入该条端到端耗时。
8. 对照宿主 `0 cap`、Docker `1 unresolved cap`：比较器不应只因 cap 次数差异错误认定镜像损坏；仍应暴露两次统计差异。
9. 旧版 `performance_report.json` 未新增字段时，兼容读取或明确报告版本边界；Resume 及两阶段写盘必须安全。

运行新增单测、原有 `tests/test_final_dual_inference.py`、`tests/test_final_dual_vllm.py`、`tests/test_final_dual_docker_package.py` 和其他 E02/Dual 回归；运行 `python -m compileall -q`、`git diff --check`、CI。**以上全部通过后才能跑 GPU。**

### Gate 1 — 宿主 vLLM 冷启动稳定性（**仍不构建镜像**）

使用两份**不变的** Adapter、Base、Prompt、vLLM 0.11.1，真实双路官方入口：

- 先只针对 `test_000005_t0` 及另外 4 个固定样本运行多次冷启动，确认能实际触发并正确记录 `length`、retry、`stop`、`unresolved` 分支；不要把“这轮没触发长度上限”当作容错代码有效性的证明，长度分支还要由 Gate 0 的 Mock 保证。
- 再在已冻结的 20 条 Smoke 输入上进行 **3 次独立启动、3 个全新 Run 输出目录**（合计 60 条完整双路样本），核对每次 20/20 Schema、两 Adapter 别名、每次每条 Prompt IDs 精确匹配、情绪/画像无异常漂移、无 OOM/启动失败、每次正常返回。
- 最后对**固定 100 条** target-free 输入做一次官方端到端压力测试，记录生成 Token、两路延迟 P50/P90/P95、首次 cap 次数、重试恢复次数、最终 unresolved、严重重复/无效回复、峰值显存。输出样本来自固定数据，不用 Gold 调参，不接受挑样本刷通过率。
- 建议的**预构建质量门槛**：100/100 官方 Schema、100/100 ID、Prompt Token 与双路资产身份正确；0 个系统性路由失败/崩溃/OOM；最终 `unresolved_cap_hits` **≤2/100** 且严重无效回复为 0。若未满足，**在宿主调试并重新执行此 Gate；此时绝不构建 Docker**。阈值用于部署风险控制，不代表统计可靠性保证。

### Gate 2 — 利用旧镜像做代码覆盖预验收（**不 build / 不 save**）

若旧 Docker 镜像仍可用，则创建临时只读代码覆盖目录，在 `docker run --network none --gpus all` 时只挂载**改动过的运行时代码文件**，沿用镜像内原 Base/Adapter/Prompt。该步骤仅用于在真实容器环境验证新的容错代码，不能代替正式镜像验收，也不修改已存在的镜像层。

- 运行相同的 20 条冻结输入，连续完成至少两次独立进程测试；记录容器日志、所有字段、容错计数、退出码、峰值显存。
- 若只读覆盖与容器文件身份校验冲突，使用**宿主 vLLM + 隔离 Conda**做等价预验收，并说明未能做容器覆盖；不可为了绕过代码身份验证而关闭模型/Prompt/权重哈希门禁。
- 所有覆盖文件哈希与后续新镜像要打入的文件相同。完成之后撤销临时挂载，不能当作正式交付包。

**Gate 0/1/2 的原则：所有有可能引起重新 build 的问题，都应尽量在这一轮解决。只要有一项未通过，不执行 Docker build。**

## 四、节省磁盘：只允许一次正式大镜像交付

此次不保留两份 Docker 镜像、两份 Docker tar，也不在每个中间阶段打包。**保留模型原件、代码 Git 提交、配置及旧镜像 SHA/Manifest 的小文件；不要保留旧大镜像或旧 tar。**

### 1. 最后构建前做空间审计

Codex 在 WSL 与 Docker Desktop 中分别测量，并将结果写入 `disk_preflight.json`：

```bash
# 在仓库根目录 / WSL
df -h .
docker system df -v
du -sh outputs/final_delivery/*/docker 2>/dev/null || true
docker image ls --digests
```

同时检查 Windows **E 盘实际可用空间**，因为 Docker Desktop VHDX 主要位于 E 盘；`docker system df` 的 reclaimable 不等于 Windows VHDX 立即缩小。粗略磁盘预算至少覆盖**新 Build Context + 新增镜像层/构建缓存 + 一份新 tar（上次约 11.77 GB）+ 安全余量**。不满足则停止并报告清理候选，绝不能跑到 `docker save` 中途才把磁盘耗尽。

只可在上述 Gate 0/1/2 通过后，按**精确的现有 E03 旧镜像 tag、旧 tar 路径、旧 Build Context 路径**清理当前项目旧 Docker 大文件。清理前保存它们的 Image ID、tar SHA、Dockerfile/环境锁/代码 Git SHA、模型 Lock 和部署结果报告（这些是小文件）；可继续保留 Git 版本。**严禁** `docker system prune -a --volumes`、无差别清理全部镜像或删除两份原始 LoRA/Base。若能保留旧镜像 tag 直到新镜像构建成功且空间足够，则优先到新镜像通过后再移除；空间不足时允许先删除旧 tar/旧镜像，但必须先完成上述预验收。

### 2. 一次打包、一次 build、一次 save

1. 代码修复完成并形成**冻结的 Git 提交**；`model_lock.json` 和所有模型权重/Prompt SHA 不变，**代码版本/交付配置版本**更新为 v1.1。生成干净、白名单 Docker Context，拷贝唯一 Base、两份 Adapter、固定 Prompt、已测试的运行代码及新版校验器；`package_manifest` 包含代码/环境/资产 SHA。
2. `docker build` 执行**一次**，产生新唯一 tag。共享原 Docker 基础层缓存以节省空间；Build 中遇到错误可修复具体构建配置，但大镜像未通过前不 `docker save`，不自动无意义重复 build。
3. 新镜像上先运行离线 GPU **20 条 Smoke**（`--network none`），再次核对模型身份/Prompt Token IDs/JSON ID/Schema，容错、路由、无 OOM、退出码；然后使用**相同镜像进行一次 100 条端到端运行**，核对 Gate 1 同口径指标、重试及降级情况。两者通过之后才允许导出 tar。
4. `docker save` **只执行一次**，写入 `outputs/final_delivery/<RUN_ID>/docker/image.tar`，生成 SHA256；校验文件完整性、`docker image inspect` 虚拟大小和 tar 均小于 `50,000,000,000` bytes。容量不足则不得开始 save。
5. 最后做**回导验证**：在磁盘预算允许的前提下移除新镜像 tag，再 `docker load` 此 tar，检查 Image ID 与 RootFS 层摘要一致，并运行一轮独立的 20 条离线 GPU Smoke。由于新容错规则已覆盖长度差异，仍发生合法 `length` 时应记录 warning，而不导致输入完整且 Schema 正确的整个任务退出 1。回导后不再保存第二份 tar；删除临时 Build Context 和明确可清理的项目中间文件。
6. 若最终镜像 Smoke 发现此前 CPU/宿主完全没有覆盖的真实错误，应暂停、保存日志并定位；**不允许为了强行“一次成功”而虚报验收通过**。修复后重新执行相关门禁，再视需要构建下一版。目标是把这种概率降到最低，而非保证不可能出现未知错误。

| 容器预验收 | 使用旧镜像代码覆盖或明确记录未支持的原因；真实离线 GPU 结果 |
| 正式新镜像 | Image ID、实际版本、vLLM 0.11.1 两别名、20/100 条、显存与双路端到端延迟 |
| 导出与回导 | 唯一 tar SHA、镜像虚拟大小、回导身份、回导后独立 20 条 Smoke 及 warnings |
| 官方接口 | `bash /root/participant/start.sh TEST_FILE RESULT_DIR` 两参数可用，`submission.jsonl` / `performance_report.json` 全量输出，错误与降级率按真实情况列明 |
| 磁盘控制 | 清理前后 Docker/WSL/E 盘空间、仅保留的最终镜像与 tar 路径、旧产物删减清单 |

**最终决策标准**：所有硬门禁通过、回复的 length 事件可被有界地处理而不崩溃、异常信息不被抹去、20/100 条在宿主及镜像内身份/格式/质量可接受、单一镜像完整导出并回导成功；此时标记 `ready_for_local_submission_review`，**不自动消耗官方提交次数**。

**最重要的执行顺序：先解决并证明运行时容错可靠，再动 Docker 的大文件。一次镜像构建和一次导出必须是全流程最后的工作，而不是调试工具。**
