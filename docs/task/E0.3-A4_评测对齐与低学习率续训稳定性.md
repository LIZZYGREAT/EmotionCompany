## 一、从当前问题出发

### 1. 当前已知的事实

E01-B Full Adapter 是冻结的可用模型基线；在 1,833 条完整 Dev 上，画像 33 标签 Micro-F1 为 `0.42227`。A3 已经在固定的 224 条/101 段完整会话上做了普通续训 Control 和短历史定向采样 Candidate，各训练 128 个 optimizer steps；相同 ID 上 E01-B Full 的画像 F1 约 `0.4223`，A3 Control 为 `0.4012`、Candidate 为 `0.3931`。A3 两组使用的学习率为 `1e-4`，不能单凭这些结果证明学习率是退化的原因。

新增的 `gpu-fast-only` 使用 E01-B Full Adapter，对同一冻结 224 点只生成情绪和画像前缀，报告画像 Micro-F1=`0.425787`、`224/224` 有效、224 次生成调用、生成耗时约 `381.52s`、模型加载约 `14.82s`。它不是完整 JSON 生成，也不能单独检查回复质量。较早的 16 点 `gpu-compare` 已验证完整生成与快评生成的前缀 Token 一致。

目前有两个尚未回答的问题：

1. **评分对齐问题**：同一批 224 点、同一 E01-B Adapter，历史完整评测约 `0.4223`，新快评约 `0.4258`。差异究竟来自 Raw/Submission 归一化、前缀解析、模型加载/数值路径，还是某些具体预测？
2. **续训稳定性问题**：从 E01-B Full Adapter 再执行少量普通 SFT 更新，在 `2e-5` 等较低学习率下，是否仍会像 A3 的 `1e-4` 普通续训一样出现画像质量退化？

这两个问题必须按顺序解决。否则使用快评比较新 Adapter 时，可能把评测差异误判为训练收益；若较低学习率续训仍不稳定，直接加 BCE 将很难辨别是辅助监督的问题还是普通续训的问题。

### 2. 本轮禁止做的事情

不改官方 Train/Val、标签 Schema、P0/F2/T1、已有 E01-B/A1/A3 Run 与权重；不修改赛事 `participant/start.sh` 的输出协议；不重跑 4,048 步训练，不生成 1,833 条完整 Dev，不依据官方 Val 调参。旧 A3 训练代码的硬性配置锁保持原状，禁止为支持 `2e-5` 而把历史校验直接删除。

## 二、阶段 A4-1：对齐 Fast-only 与历史 224 点完整评测

### 1. 先明确要对齐的三个对象

对 **同一份冻结 224 点 ID**，区分三个不同的数据来源：

| 记号 | 来源 | 数据含义 |
|---|---|---|
| `S` | E01-B Full 历史 `runner/submission.jsonl` | 已通过赛事解析、归一化或异常回退的最终预测；与 A3 的旧基线评分一致 |
| `R` | 同一 Run 的 `raw_predictions.jsonl` | 模型实际生成的原始文本；解析其 *已完成的情绪/画像前缀*，不查看回复内容来决定画像 |
| `F` | `gpu-fast-only` | 模型提前停止时直接获得的情绪和画像；当前汇总报告尚未持久化完整逐 ID 标签 |

不要把 `R` 的有效前缀和 `S` 的完整 JSON 有效性混为一谈。例如，模型已经正确生成画像、但后续回复过长导致整个 JSON 不合法时，`R` 可能有有效画像，而 `S` 会按旧 Runner 的异常策略回退。这样即使模型前缀完全不变，`R/F` 与 `S` 的 F1 也可能不同。

**需要分别计算 `F1(S)`、`F1(R-prefix)`、`F1(F)`，并解释每一对的差异。** 当前 `F1(S)≈0.4223`、`F1(F)=0.425787` 已有报告；`F1(R-prefix)` 必须重新从历史 Raw 的 224 点计算，不得猜测。

### 4. A4-1C：按 ID 对齐和归因

复跑后使用新生成的 `F`，在冻结 224 点上建立配对表：

- 每个 `id` 的三类预测 `S` / `R-prefix` / `F`；三个维度分别对比集合相等，标签顺序不影响评分。
- `S↔R` 差异数、`R↔F` 差异数、`S↔F` 差异数，各自对应标签级 TP/FP/FN 变化。
- 所有 `R↔F` 不一致案例优先核验：Prompt token ids 是否相同、Greedy 参数、量化和 Adapter 加载参数 dtype、模型/Tokenizer/权重 SHA、原始 Raw 合法性。旧完整 Run 未保存逐 Token ID 的情况下，**只能比对文本前缀和结构化画像，不能凭空声称旧 Run 的 Token IDs 逐项一致**。
- 当发现 `S` 因完整 JSON 失败而回退、但 `R/F` 画像前缀有效时，单独列为“下游 JSON/解析口径差异”，不要归结为模型标签判断差异。
- 若产生差异且无法证实根因，保持 `unresolved`：以后候选 **只在相同 Fast-only 评测协议下与重跑的 E01-B Fast-only 基线比较**，不得混入历史 `S` 分数。

验收门槛：

1. 224 点与 101 会话、Gold/输入/原始 Raw ID 全部对齐，无泄漏、无缺行与重复 ID。
2. `S` 和 `R-prefix` 可复算并解释相应差异；新 `F` 能逐 ID 比较，若 `R` 与 `F` 不一致则必须有可定位的证据和明确的是否采用结论。
3. 若本轮使用 GPU，只允许一次单独的固定 224 点快评（含模型加载 ≤900 秒），失败不自动重试。
4. 给出**后续候选的统一基线**：明确采用已核验的 Fast-only E01-B 重新生成结果作为 GPU 筛选参照，以及历史完整 Dev E01-B 作为最终正式指标参照。

## 三、阶段 A4-2：低学习率普通 SFT 续训稳定性

### 1. 研究问题与实验设计

A3 的 `1e-4` 普通续训 Control 在 224 点上从原 Full B 的约 `0.4223` 降至 `0.4012`。但是 A3 训练时的样本顺序、梯度更新及其他条件也会影响结果，因此不能直接将下降归因于学习率过高。

本轮只研究：**以现有 E01-B Full Adapter 为起点，在较低学习率下做少量标准 SFT 更新，实际画像、情绪是否出现明显退化？**

第一候选固定为：

| 项目 | A4 规定 |
|---|---|
| 训练起点 | 已冻结 `E01-B-FULL-20261028-133805/adapter`，只复制/读取，不覆盖 |
| 模型 | Qwen3-1.7B、NF4、BF16、相同 LoRA `r=8`、`alpha=16`、相同 target modules |
| 训练任务 | 原 Completion-only JSON SFT；**不新增** BCE、标签加权、Replay |
| 数据 | 16,192 条有效 SFT Train 中确定性均匀无放回抽取，按会话记录曝光，不读取 Dev/Val 作训练 |
| 采样数量 | **64 optimizer steps × 4 microbatch = 256 条**，每条 microbatch size=1 |
| 学习率 | `2e-5`，AdamW、constant scheduler、warmup=0、weight decay=0 |
| 参数更新 | 仅更新 LoRA A/B，重新创建空的 optimizer state，不恢复 Full B/A3 优化器或调度器 |
| 其他 | seed=42、P0/F2/T1、S=2048/P=1280、Greedy 评测 G=1200 |
| Checkpoint | 至少 final-step 64；可选 step 32 用于中途恢复，但不允许自动延长训练 |
| 评测 | A4-1 已锁定的同一批 224 点 Fast-only 基线与 A4-2 候选，逐 ID 配对 |

这里的 `2e-5` 是一个用于检验稳定性的候选值，**不是已有证据证明的最优学习率**。初始实验仅一组低 LR 候选。历史 A3 Control 作为次要观察参照，不可以当成“除了 LR 完全相同”的严格对照；如果之后要因果比较学习率，必须另起相同样本顺序与训练步数的 `1e-4` 对照 Run，并单独获得时间与资源批准。

建议新增：

- `configs/training/e03_a4_lr_stability.yaml`：明确新实验版本、Run 身份、来源 SHA、LR、训练步数、授权/预算及所需评测 IDs。
- `scripts/e03_a4_stability_train.py`：独立 A4 `preflight` / `gpu-preflight` / `train` CLI；仅在显式许可下启动 GPU 更新。
- `tests/test_e03_a4_stability.py`：CPU 合成回归；必要时新建轻量模块 `src/training/e03_a4_stability.py` 以存放采样和指标聚合。

1. **不放宽 `scripts/e03_a3_short_train.py::_verify_static_assets()` 对 A3 的 `optimizer.learning_rate==E01-B` 校验**，不直接把 A3 的 YAML 改为 `2e-5`。A3 保留完整历史可复现性。
2. 优先复用已测试的基础组件：`src/training/sampling.py::build_sampling_plan()`、`src/data/sft_collator.py::SFTDataCollator`、A3 中合法的 Base/Adapter 加载与 dtype 核验机制、E01-B 原始输入格式。只为 A4 写必要的薄封装；避免复制 1,500 行 A3 训练器，也避免大规模修改历史 `training_sft.py`。

6. 设置独立 `outputs/training/E03-A4-stability/<run-id>/`。所有配置、源码、Base/Adapter、Train、Tokenizer/P0/F2/T1、采样 Hash、GPU/显存事实和 optimizer steps 均写入不可变的 Run Manifest。

**特别注意：** 若仅做 CPU 实现，必须显式报 `gpu_not_run`，不能把 CPU 合成模型的梯度成功当成真实 QLoRA 成功。

### 3. A4-2B：先运行 CPU 预检和合成测试

在不加载真实 GPU 模型的情况下验证：

- 新实验 ID 不与 E01-B、A1、A2、A3 冲突；Run 根目录、授权票据、steps/LR/采样来源绑定；配置修改使预检失败，不能复用旧预检回执。
- 确认恰好 256 次 Train-only draw；同 seed 可重现、不同 seed 变动、未重复取样；不含 Dev/Val；按完整 optimizer step 对齐 4 个 microbatch。
- `2e-5` 为唯一允许的 A4 低 LR 值；若需其他值创建新实验，不在一次 Run 中试多个 LR。
- Prompt Mask、labels 及序列对齐；Trainer 不再隐式 shuffle；optimizer 在起点为空；只允许 LoRA 更新。
- Adapter 初始化时 rank/alpha/target modules、量化参数、dtype 和基线 SHA 核验失败应中止；保存和重载应使用相同 dtype 语义。
- 预算或中断停止的 Run 不得标为 `passed`，不得进入候选评分。

CPU 验收通过后先提交**代码/配置/测试**，不要立即自动启动 GPU。

### 4. A4-2C：受控 GPU 64 步 + Fast-only 224 点比较

只有 A4-1 评测口径验收通过，并且得到明确 GPU 执行批准后，按以下顺序执行：

1. `gpu-preflight`：CUDA/NF4/BF16/磁盘、Baseline 权重/Adapter Hash、最长 2048 Token dry forward/backward，确认 Loss/LoRA 梯度有限且非零、没有任何 optimizer update。
2. 训练一条独立 A4 Run：**最多 64 个 optimizer steps**；固定 `2e-5`，禁止自动变更 LR、采样或步数；保存 Adapter、训练轨迹、耗时、显存、Checkpoint 和独立重载结果。
3. 在同一冻结 224 点使用 `gpu-fast-only` 对 A4 候选评分，生成其专属、已绑定模型身份的 inference config snapshot；禁止修改原 E01-B inference config，确保仍为 P0/F2/T1、Greedy。
4. 与 A4-1 重新核验过的 **同协议 E01-B Fast-only 224 点基线**比较。同一 ID、同一 Gold、同一评分器，计算 33 标签 TP/FP/FN、Micro/Macro-F1、Precision/Recall、三维及短历史/长历史差值；并按 conversation cluster 给出配对不确定性区间。
5. 如资源许可，对少量预先固定的样本（例如 16–32 点）再跑完整 JSON，检查情绪、Raw A0、回复及重载一致性；**快评本身不能证明回复和完整 JSON 不退化**。

本阶段的资源红线：每次真实训练必须使用独立预算，建议 **最多 64 个 optimizer steps、实际训练阶段 ≤1 小时**；候选 Fast-only 另设独立 **≤900 秒** 上限。出现不可恢复错误不得自动重试、不得追加 128 步，更不得启动完整 Dev。

|---|---:|---:|---:|

实际决策采取审慎的**工程停止门槛**，不是声称 224 点能完成严格统计非劣性证明：

- 若画像 Micro-F1 相对基线下降超过 `0.01`，或 Precision 下降超过 `0.02`，或 FP 增加超过 `10%`，或情绪准确率下降超过 `0.02`，则标记 `stability_failed`，不启动 BCE，也不扩大步数。各项下降阈值是预先确定的资源决策规则，不是统计显著性证明。
- 若上述指标均未触发，且全部身份、重载/格式门禁通过，标记 `stability_preliminarily_passed`；这只表示**普通低 LR 续训没有在当前小样本上观察到明显退化**，不代表画像已提高。
- 只有画像 F1 与 FP/Precision 显示有意义的正向改善，且会话配对分析支持时，才建议后续向 BCE 候选申请预算。若只是“没变差”，可将 A4 作为 BCE 的基础对照，但不应宣称已优化画像。
- `64→128` 步的扩展属于**另行批准的新运行**；不能把已经结束且新建 optimizer 的 64 步 Run 偷偷当作优化器连续 128 步来描述。若希望真正从 step64 连续恢复，必须完整保留并验证 optimizer/scheduler/RNG 状态，制定独立门禁。
