# EmotionalCompany：A0 技术架构与实验方案

> 状态：第一阶段架构基线（A0），用于后续实现、实验对照与协作。
> 范围：数字人综合情感陪伴对话模型赛题的文本多任务建模、训练、评测及交付。不包含独立判别模型方案 B 的实现设计。

## 一、任务定义与已确定决策

### 1. 任务与评分目标

系统读取截至目标用户消息的多轮对话历史，输出当前用户的情绪类别、用户画像和情感陪伴回复。该赛题当前提供的是文本输入输出；数字人形象、语音与视觉模块不在现阶段实现范围内。

| 任务 | 输出 | 官方公布的自动评测指标 | 分值 |
|---|---|---|---:|
| 情绪识别 | 16 类情绪中选择 1 类 | Accuracy | 25 |
| 用户画像 | 3 个维度、共 33 个候选标签的多标签集合 | 画像维度平均准确率（具体实现待核实） | 15 |
| 回复生成 | 中文情感陪伴文本 | BLEU-4、ROUGE-L、BERTScore | 20 |
| 推理性能 | 端到端推理耗时 | 平均延迟（评分映射待核实） | 10 |

其余 30 分为技术方案与实验报告、代码规范与可复现性、训练/调优及平台运行记录。模型选择与实验设计同时服务于自动指标和可复现交付，不能仅根据回复的主观自然度判断模型质量。

### 2. A0 已确定内容

| 设计项 | 决策 |
|---|---|
| 主体架构 | **方案 A：单一自回归语言模型**，不额外训练分类器 |
| 初始基础模型 | **Qwen3-1.7B**，使用已完成后训练的模型，而非 Base 预训练版本 |
| 参数适配 | **4-bit QLoRA**：量化并冻结基础权重，仅训练 LoRA 参数 |
| 训练方法 | **Completion-only SFT**，每个预测点对应一条完整联合监督样本 |
| 监督任务 | 情绪分类、用户画像与参考回复共同构成输出目标 |
| 训练损失 | 首轮使用标准 Token 级交叉熵，不设字段损失权重 |
| 推理方式 | 单次生成结构化 JSON；**Non-thinking** 模式 |
| 输出顺序 | `emotion_label` → `user_profile` → `response_text` → `memory_refs` |
| 历史输入 | 仅使用目标预测点之前及当前用户消息；按 Token 预算保留最近合法历史 |
| 主实验 | **E00：未经微调的 Qwen**；**E01：A0 标准 QLoRA SFT** |
| 交付 | 自行构建可离线运行的 vLLM Docker 参赛镜像，导出文件 ≤ 50GB |

以上是架构与实验原则，不等于所有具体超参数已确定。最大序列长度、LoRA Rank、学习率、Epoch、解码长度等将在小规模验收和基线测试后固定。

### 3. 明确不在 A0 中实现的机制

暂不引入独立情绪/画像分类器、专用任务 Prompt 混合训练、字段加权损失、类别重采样、RAG、外部记忆数据库、多 Agent 或 DPO/RLHF。上述部分只有在 E00/E01 暴露出对应瓶颈时才作为独立实验候选，避免一次性修改多个因素后无法归因。

## 二、数据结构与训练样本定义

### 1. 原始数据的两个层次

训练/验证 JSONL 的**每一行是一段完整对话**，而不是一次独立问答：

```text
Conversation
├── conversation_id
├── turns[]
│   ├── turn_id
│   ├── role: user | assistant
│   └── content
└── prediction_points[]
    ├── target_user_turn_id
    ├── assistant_response_turn_id
    └── target
        ├── response_text
        ├── emotion_label
        ├── user_profile
        │   ├── personality_traits[]
        │   ├── interests[]
        │   └── style[]
        └── memory_refs[]
```

原始数据统计：Train 8,338 段对话、18,657 个监督预测点；官方 Val 900 段对话、2,354 个监督预测点。同一对话可能对应多个预测点，因此不同预测样本可能共享历史消息。

该原始 Train 数不是当前 D0.3 训练行数。D0.2 清理后，D0.3 规范化划分为 Train 16,312、Dev 1,833、官方 Val 2,354；D0.4.3 的 `S=2048/P=1280` 候选实际生成 SFT Train 16,192、Dev 1,821，Val 只交叉核对、不生成训练数据。详见 [E00 阶段总结与 E01 交接](../experiments/E00_阶段总结与E01交接.md) 和 D0.3/D0.4.3 报告。

定义第 $i$ 个预测样本：

$$
D_i=(x_i,e_i,p_i,r_i),
$$

其中 $x_i$ 是截至目标用户消息的合法对话前缀；$e_i$ 是情绪标签；$p_i$ 是画像的三个标签集合；$r_i$ 是目标 Assistant 参考回复。`memory_refs` 在当前赛题推理协议中按固定空数组处理，不单独作为记忆检索目标。

### 2. 训练样本转换

对每段对话逐个处理其 `prediction_points`，根据 `target_user_turn_id` 提取历史前缀，读取该预测点的监督答案，再组装为 `prompt` / `completion`：

```text
原始完整对话 + 一个 prediction_point
    ↓ 按 target_user_turn_id 定位
截至当前用户消息的合法历史
    ↓ 上下文预算与统一 Prompt 序列化
prompt
    +
该预测点的 emotion_label / user_profile / response_text
    ↓ 按固定字段顺序序列化
completion（标准 JSON）
```

训练输入**不得包含**对应的参考 Assistant 回复及该预测点之后的消息。`assistant_response_turn_id` 用于定位/校验监督回复，不是未来消息可被输入的许可。应检查角色、轮次顺序、字段类型、标签取值与参考回复一致性；不符合约束的样本记录原因并隔离处理，而非静默改写。

转换后的核心样本形式（仅示意，内容不是数据集原文）：

```json
{
  "prompt": "<统一任务指令 + 截断后的历史对话>",
  "completion": "{\"emotion_label\":\"anxiety\",\"user_profile\":{\"personality_traits\":[\"sensitive\"],\"interests\":[\"study_exam\"],\"style\":[]},\"response_text\":\"听起来最近的学习压力让你很难受……\",\"memory_refs\":[]}"
}
```

`prompt` 最终应按 Qwen Chat Template 编码；这里用字符串仅展示概念。训练和推理必须共用历史序列化与任务指令的规则，避免同一对话在两个阶段被解释成不同的输入。官方参考推理脚本是对齐依据；具体模板文本将在实现时固定并版本化。

### 3. 上下文截断约束

Token 预算针对**完整训练序列**，不只是历史。应满足：

$$
L_{\mathrm{prompt}}+L_{\mathrm{completion}}\leq L_{\max}.
$$

初始策略如下：

1. 始终保留系统/任务指令、当前目标用户消息和必要格式提示。
2. 对更早历史按**消息边界**从近到远选取；不得从未来获取摘要或画像信息。
3. 若当前用户消息本身超出预算，执行显式、可追踪的截断策略，不直接截掉标签或目标回复。
4. 统计截断样本占比、丢弃历史 Token 数量、目标输出长度及异常情况，并保存到数据分析报告。

第一轮先在 1,024～2,048 Token 范围内进行显存/截断率验证，**不预先冻结固定长度**。长上下文是否值得保留，交由后续消融实验判断。

### 4. 数据切分与泄漏防护

官方训练集与验证集互不混用。若从训练集进一步划分开发子集，必须按 `conversation_id` 分组，使同一对话派生的所有预测点只出现在一侧。不能按展开后的预测点随机切分，以免多个高度重叠的对话前缀进入不同子集。官方验证集主要用于阶段性评估，避免反复根据其结果调整细节造成过拟合。

## 三、模型与训练机制

### 1. A0 的单模型联合生成

在统一任务指令和历史 $x$ 给定时，模型预测一个完整结构化结果：

```text
合法历史 x
   ↓ Tokenizer + Qwen Chat Template（Non-thinking）
Qwen3-1.7B（4-bit 基础权重 + LoRA Adapter）
   ↓ 自回归生成
emotion_label → user_profile → response_text → memory_refs
   ↓ JSON 解析与字段校验
比赛预测结果
```

这不是三个独立的预测头。情绪、画像和回复在一个 Token 序列内顺次生成，后续字段可以条件化于已生成的前面字段。形式上可将其理解为：

$$
P_\theta(e,p,r\mid x)
=P_\theta(e\mid x)P_\theta(p\mid x,e)P_\theta(r\mid x,e,p),
$$

其中省略了 JSON 结构 Token。固定顺序是 A0 的控制变量，并不表示它在准确率上已被证明优于其他顺序。

### 2. QLoRA 的可训练参数

基础模型采用 4-bit NF4 量化加载，基础权重保持冻结。在选定的线性层加入低秩增量：

$$
W_{\mathrm{eff}}=W_{\mathrm{frozen}}+\Delta W,
\qquad \Delta W=\frac{\alpha}{r}BA.
$$

这里 $A,B$ 为可训练的 LoRA 矩阵，$r$ 为秩，$\alpha$ 为缩放系数；量化冻结权重在实际计算时由相应算子处理。反向传播只更新 LoRA 等明确允许训练的参数。采用 BF16 计算及按需要启用梯度检查点以控制显存。

当前 RTX 4060 Laptop GPU 具有约 8GB 显存；已验证 PyTorch CUDA/BF16、bitsandbytes NF4 前向计算和 Qwen3-1.7B 的 4-bit 推理。**尚未验证实际 QLoRA 反向传播和完整训练负载**，不能从推理显存直接推断训练显存。

### 3. Completion-only 监督目标

将一个样本的目标 JSON 编码为 $y=(y_1,\ldots,y_T)$，训练采用教师强制：预测位置 $t$ 时使用此前的正确目标 Token $y_{<t}$。只对 `completion` 中的目标 Token 计算交叉熵，`prompt` Token 作为条件输入而不进入损失：

$$
\mathcal L_{\mathrm{A0}}(x,y)
=-\frac{1}{T}\sum_{t=1}^{T}
\log P_{\theta,\phi}(y_t\mid x,y_{<t}),
$$

其中 $\theta$ 表示冻结的基础模型参数，$\phi$ 表示可训练 LoRA 参数。实现时需注意不同序列 padding、EOS 与批次损失归一化方式，确保只有预期的目标 Token 参与训练。精确平均方式应随训练实现记录，避免不同实验在未察觉的情况下改变损失定义。

完整 JSON 中回复通常占据更多 Token，标准 SFT **没有显式保证**情绪、画像与回复的优化强度和比赛分值成比例；这构成后续优化的研究假设，但不能仅按字段长度推断其实际梯度贡献。A0 保留标准损失，先测量实际结果。

### 4. 训练—推理差异

由于联合输出按情绪、画像、回复排列，训练时回复的前文包含真实标签（Teacher Forcing），推理时则包含模型自己预测的标签。前序标签错误可能向后传递；是否构成实际瓶颈，应通过验证集中「分类是否正确」与「回复指标」的分组分析判断。A0 不额外引入二阶段生成或纠错模型。

## 四、推理协议与输出控制

### 1. 一次推理的执行链

```text
测试样本（id, history, target_user_turn_id）
    ↓ 校验输入与角色顺序
共享上下文构建器（与训练同一套规则）
    ↓ Chat Template，关闭 Thinking
量化/部署版本 Qwen3-1.7B + 已训练参数
    ↓ 单次生成，限定输出长度
JSON 解析与枚举合法性校验
    ↓ 补齐固定字段、透传测试 id
submission.jsonl
```

统一输出字段结构为：

```json
{
  "id": "test_000001_t5",
  "emotion_label": "anxiety",
  "user_profile": {
    "personality_traits": [],
    "interests": [],
    "style": []
  },
  "response_text": "……",
  "memory_refs": []
}
```

模型生成三个核心任务的 JSON 字段；`id` 从测试输入透传，不由模型自由生成；`memory_refs` 按当前参考推理协议固定为空数组。上方 ID 仅为格式示例，实际运行中不能自行重写官方输入 ID。

输出合法性校验至少覆盖：情绪枚举、三个画像维度及其候选标签、字段数据类型、必填字段、非空回复和 JSON 语法。必须分别统计**原始模型输出合法率**与**最终提交结果合法率**，避免容错修补掩盖训练问题。约束解码是否引入，视初始 JSON 合法率与延迟实测决定。

### 2. 训练与部署的边界

本地训练环境使用 PyTorch/Transformers/TRL/PEFT/bitsandbytes；正式交付拟采用自建 vLLM Docker。两者可使用不同运行环境，但模型架构、权重导出方式、Tokenizer、Chat Template 与 Non-thinking 行为必须一致或经过一致性测试。

QLoRA Adapter 是否合并成 BF16 权重、采用何种部署量化格式，尚未确定；优先以 vLLM 是否可加载及推理结果是否稳定为依据。不得在离线测试时下载模型、依赖云端 API 或假设外网可用。

## 五、评测设计与实验基线

### 1. 公共评测接口

所有候选模型读取相同验证输入，生成相同 Schema 的预测文件，再调用同一评测器。评测器不依赖训练框架内部的损失值，直接比较预测与监督标签。

| 类型 | 必须记录 | 诊断性指标 |
|---|---|---|
| 情绪 | Accuracy | Macro-F1、逐类召回率、混淆矩阵 |
| 用户画像 | 3 个维度的预测结果与维度指标 | 标签级 Micro/Macro-F1、空集率、频次分布 |
| 回复 | BLEU-4、ROUGE-L、BERTScore | 回复长度、人工抽样与失败案例 |
| 推理 | 平均端到端延迟 | 生成 Token、峰值显存、输出合法率 |

当前缺少官方各文本指标的精确分词/权重细节、画像维度准确率定义及延迟到分数的映射。本地实现必须标记为**近似指标**；同时保存原始预测与每个子指标，不能据此宣称获得官方总分。官方参考脚本统计前 100 条样本的推理性能，正式延迟复现需以当期脚本和评测规则为准。

### 2. 首轮必须建立的基线

| 实验 | 训练方式 | 固定条件 | 回答的问题 |
|---|---|---|---|
| 简单任务基线 | 情绪多数类、画像空集合等 | 与模型使用相同的验证样本 | 多数类/稀疏标签能达到何种水平 |
| **E00** | 原始 Qwen3-1.7B，零微调 | 统一 Prompt、输出 Schema、历史规则、解码参数 | 基础模型已经具备多少赛题能力 |
| **E01** | 同一基础模型 + **A0 标准 QLoRA** | 尽量保持 E00 的推理配置一致 | 标准联合 SFT 对各任务及延迟的净影响 |

E00 与 E01 的主要差别应是 LoRA 训练后的模型参数。两者都在**一次生成完整 JSON**的正式推理模式下评测，不能用专项 Prompt 的单任务成绩替代联合推理成绩。

每次训练需保存：模型 ID 与具体修订版本、数据快照/构建规则、Prompt 版本、随机种子、训练配置、环境依赖版本、训练日志、权重产物、验证预测文件、评测结果及失败样本分析。

### 3. 后续候选实验（不属于 A0）

只有首轮结果提示具体问题时才安排：

| 候选 | 改动 | 启动条件与价值 |
|---|---|---|
| A0+：字段损失加权 | 保持完整 JSON 样本，单独调整情绪/画像/回复 Token 的损失比重 | 分类或画像明显落后，需检验训练目标竞争 |
| A1：混合专项监督 | 同一模型额外训练情绪、画像或回复专项指令样本 | 需要验证专项训练能否迁移到完整 JSON 推理 |
| 历史截断消融 | 修改上下文 Token 预算/保留策略 | 判断长历史是否改善画像与回复 |
| 基础模型对照 | 如 Qwen3.5-2B（未选定，需先做兼容性检查）等，在同一数据/评测协议下测试 | 测量模型架构与能力的收益和算力代价 |
| 方案 B | 独立判别模型 + 生成模型 | 联合模型在分类任务上存在可证实瓶颈且收益值得增加部署开销 |

A0+、A1 和方案 B 不应与 E01 的首次标准微调混在一起实现；实验中原则上一次改变一个主要因素。

EmotionalCompany/

├── src/

│   ├── training/                    # QLoRA SFT
│   ├── evaluation/                  # 统一生成评测与指标计算

### 2. 两人职责

| 范围 | 主要责任 | 协作要求 |
|---|---|---|
| 数据与评测 | 数据处理、无泄漏检查、Schema、指标、错误分析 | 训练侧审查样本生成结果 |

用 `main` + 短期功能分支维护代码；训练差异用版本化配置和实验 ID 管理，不为每个超参数组合创建长期 Git 分支。

### 3. Docker 交付约束

主办方已确认：**数字人情感陪伴赛道不提供统一基础 Docker 镜像；可自行构建 vLLM 镜像；导出的镜像文件大小须在 50GB 以内**。最终容器须离线加载模型，按官方 `start.sh` 接收测试文件与结果目录，输出 `submission.jsonl` 和 `performance_report.json`，并随镜像提交要求的技术与实验材料。

在模型训练达到可用状态后尽早完成一次最小 vLLM 加载和离线推理试运行，避免到最终提交阶段才发现权重格式或环境兼容问题。正式镜像只包含部署需要的一套模型权重、运行依赖和评审材料，不包含完整训练历史和无关缓存。

## 七、A0 的实施顺序与验收门槛

### 1. 已完成的准备

- WSL2 能识别 RTX 4060 Laptop GPU（约 8GB VRAM）。
- Python 3.10.12、PyTorch 2.10.0+cu128、CUDA 12.8、BF16 与 Autograd 已通过测试。
- Transformers、TRL、PEFT、bitsandbytes 均可导入；NF4 CUDA 前向已通过。
- Qwen3-1.7B 4-bit 非思考模式推理已通过：测试生成 57 Token、耗时 2.39 秒，PyTorch 记录峰值分配显存 1.28 GiB。该数值不是完整训练显存，也不是赛事标准延迟。

### 2. 原始规划与当前进度

以下顺序保留为 A0 方案制定时的原始规划，不代表这些事项现在仍是未开始状态。当前 D0 与 E00.1/E00.2/E00.2-D 小样本工程诊断已完成；E00.3 全量 Dev 未运行，E01 真实 QLoRA 训练也未开始。最新阶段事实与证据见 [E00 阶段总结与 E01 交接](../experiments/E00_阶段总结与E01交接.md)。下一步推荐先制定 E01 的真实 QLoRA micro-overfit 验收方案。

1. **冻结数据契约**：统一标签、Prompt/Completion 序列化、目标轮次检查和 Token 预算策略，建立针对未来信息泄漏的测试。
2. **建立 E00**：在一批代表性验证样本上完成原始 Qwen 联合 JSON 推理、解析、指标计算和错误分析；确认运行时间后扩展至全部验证集。
3. **QLoRA Smoke Test**：少量真实训练样本进行前向、反向与参数更新，核对哪些参数需要梯度、峰值显存、Adapter 保存和重新加载。
4. **运行 E01**：按固定配置完成完整数据 SFT，保存训练日志、配置和预测文件；用与 E00 相同的评测协议比较。
5. **诊断与选择实验**：依据分类、画像、回复和性能的真实瓶颈决定下一项单因素消融；不默认必须增加复杂模块。
6. **vLLM 离线试运行与正式交付**：验证模型导出兼容性、官方入口、JSON 文件、性能报告及镜像体积。

### 3. 当前仍需确定但不阻碍架构冻结的事项

| 未定项 | 如何确定 |
|---|---|
| 训练最大 Token 长度与截断细则 | 统计 Token 长度/截断率并在 8GB GPU 上运行训练 Smoke Test |
| LoRA Rank、Alpha、Dropout、Learning Rate、Epoch 等 | 先确定能稳定训练的初始配置，再通过 E01 验证和单因素实验调整 |
